# 智能吸附优化实施任务清单

> **执行约定：** 每完成一个顶层任务，必须先完成该任务的验收条件和验证命令，再把对应的 `- [ ]` 改为 `- [x]`，并在“完成记录”中填写日期、改动文件和验证结果。未完成真实应用复测的任务不得标记为完成。

**目标：** 在不削弱 VSCode、PyCharm 现有窗口元素吸附能力的前提下，补齐浏览器标签页/书签栏/地址栏识别、小元素识别和悬停响应速度。

**架构：** 保留现有“快速 Win32/已知内容 + 后台 UIA/MSAA + 局部视觉 + 候选评分/稳定器”的分层结构。浏览器外壳采用独立适配策略；UIA 明确控件优先，视觉检测只做有限 ROI 兜底；重型 OCR/视觉模型不得进入默认的每次鼠标移动路径。

**技术约束：** Windows、C++17、现有 Win32/UIA/MSAA 实现、固定容量候选数组、RAII 资源管理；不整体合并 `backup/smart-region-stage1-9`，不引入未经性能验证的第三方运行时。

## 保护性验收基线

- VSCode：编辑器、终端、侧栏、标签页、底部面板。
- PyCharm：编辑器、项目树、终端、工具窗口、标签页。
- Chrome/Edge：网页内容、图片卡片、列表行、标签页、书签栏、地址栏、浏览器按钮。
- GitLab：单条提交、提交正文、按钮、侧栏和宽横条。
- Windows Terminal、记事本、资源管理器、普通 Qt/Win32 应用。
- 靠近窗口边缘、高 DPI、多显示器、快速移动、快速点击、手动拖拽覆盖智能候选。

## 阶段一：基线、诊断和测试设施

- [x] **任务 1：建立可复现的智能吸附基线**

  记录当前分支、构建配置、专项测试结果、真实应用矩阵、首帧响应时间和连续移动体验；明确区分自动化证据与人工复测结果。

  验收：基线文件包含每个应用的目标元素、最终来源、矩形、是否识别、响应问题和回退结果；VSCode/PyCharm 当前能力被单独记录。

- [x] **任务 2：补充候选链路诊断信息**

  诊断中记录进程名/窗口类名、鼠标所在窗口、候选来源、语义、尺寸、评分、拒绝原因、UIA/MSAA/视觉耗时、异步结果年龄和是否使用缓存。

  验收：能够回答“小元素没有识别”属于 UIA 未提供、候选被过滤、候选被低分淘汰、视觉边界失败还是异步结果过期。

- [x] **任务 3：补齐小元素和浏览器外壳的自动化夹具**

  增加可控的 Win32/UIA 测试窗口和图像夹具，覆盖 12～24 像素控件、图标按钮、TabItem、窄行、书签样式链接、弱边界卡片和文本碎片。

  验收：测试夹具不依赖真实浏览器即可稳定复现关键候选策略；现有专项测试仍可运行。

## 阶段二：候选容量、语义和小元素识别

- [x] **任务 4：为回退候选预留固定容量**

  调整 UIA 候选收集和总候选合并策略，确保 UIA 层级过多时仍保留已知内容、视觉、Client、Window 等回退候选。

  验收：至少保留一个 UIA 局部候选、一个内容/视觉候选、Client 和 Window；容量超限行为有测试覆盖；VSCode/PyCharm 不因候选过多退化为无响应。

- [ ] **任务 5：实现按来源分级的最小尺寸策略**

  UIA 明确的 Button、TabItem、MenuItem、ListItem 等允许更小尺寸；MSAA 需要更强语义；视觉候选继续使用更严格的尺寸、边界和置信度规则。

  验收：小型真实控件可以进入候选；代码字符、孤立图标、纹理和文本碎片不会频繁形成吸附框；全局规则不被简单放宽。

- [ ] **任务 6：保留和增强 UIA 控件质量元数据**

  在候选中保留或转换 `IsControlElement`、`IsContentElement`、`IsEnabled`、`IsKeyboardFocusable`、Name、ControlType 及可用控件模式等信息，形成稳定的控件质量等级。

  验收：无名称但可操作的图标控件、命名 TabItem、禁用控件、泛化 Pane/Custom 容器分别有明确的接受或拒绝结果。

- [x] **任务 7：优化小控件候选评分和层级切换**

  保持“可操作控件 -> 父容器 -> 内容区 -> Client -> Window”顺序，避免小控件仅凭面积获胜，也避免大型 Document/Pane 抢走局部候选。

  验收：候选循环、鼠标滚轮切换、Tab/Shift+Tab 切换和点击确认均保持稳定；候选评分诊断能够解释最终选择。

- [x] **任务 8：增强局部视觉对弱边界和紧凑控件的判断**

  继续使用冻结截图和有限 ROI，补充圆角、浅色/暗色弱对比、只有上下边界、只有左右边界、贴近 Owner 边缘和带内部纹理的控件规则。

  验收：视觉候选至少有足够独立边界证据；不能把文字笔画、图片内部线条和纯色背景当成小控件。

## 阶段三：浏览器标签页、书签栏和地址栏

- [ ] **任务 9：增加 Chromium 浏览器外壳识别上下文**

  在 Chrome/Edge/Brave 进程或窗口识别基础上区分网页渲染区与浏览器外壳；优先使用 UIA 元素路径和 Chromium `IsWebContentRoot` 等信息，不依赖脆弱的完整窗口子树结构。

  验收：鼠标在网页内容区时保留现有内容区吸附；鼠标在标签栏、书签栏、地址栏时不再直接落到网页内容区或整窗。

- [ ] **任务 10：识别浏览器 TabItem 和标签操作按钮**

  识别当前标签、非当前标签、标签关闭按钮、新建标签按钮及标签栏整体；支持同一点父子候选切换。

  验收：标签内容、标签关闭按钮和标签栏可以分别作为候选；快速经过多个标签时不出现持续闪烁或长期停留在整窗。

- [ ] **任务 11：识别浏览器书签栏、地址栏和工具栏控件**

  覆盖书签链接、书签文件夹、地址栏、刷新/返回/前进/扩展按钮等常见元素；UIA 不可用时只启用受约束的局部视觉兜底。

  验收：书签链接可以局部吸附；地址栏和工具栏不会被误判为网页内容；无法确认单个控件时安全回退到对应浏览器外壳区域。

- [ ] **任务 12：处理浏览器弹出菜单和临时窗口**

  覆盖右键菜单、书签下拉菜单、地址栏建议列表、工具提示和扩展弹窗等临时窗口；检查 `WindowFromPoint` 得到的 Owner/Root 关系。

  验收：临时窗口可识别时选中其局部元素；临时窗口关闭或失效后不会留下悬空候选，也不会影响下一次截图。

## 阶段四：响应速度和异步结果质量

- [ ] **任务 13：消除一次悬停更新中的重复窗口定位**

  让快速路径产生的 Root HWND、Owner 矩形和窗口快照可直接传给 UIA 请求，避免同一鼠标位置重复调用窗口检测。

  验收：诊断日志中单次悬停更新只产生一次窗口定位；Window/Client/已知内容结果保持不变。

- [ ] **任务 14：增加局部视觉候选缓存**

  以 Root HWND、背景截图版本、量化鼠标区域和候选矩形作为缓存键；鼠标仍在同一可信区域时不重复执行完整边界扫描；窗口切换、模式切换、截图背景变化时清空缓存。

  验收：连续移动时视觉扫描调用次数下降；候选矩形变化和靠近边界时仍能重新检测；VSCode/PyCharm 不因缓存返回旧区域。

- [ ] **任务 15：改进 UIA 结果复用和过期判断**

  在同一 Root HWND、候选矩形仍覆盖鼠标或鼠标只发生小范围移动时，允许复用最近结果；结果跨窗口、跨代际、超时或候选不再覆盖鼠标时必须丢弃。

  验收：快速移动不会长期显示旧候选；慢速移动不因严格 request ID 丢失所有局部候选；拖拽和点击确认仍优先于晚到的 UIA 结果。

- [ ] **任务 16：重新测量并调整悬停节流与稳定延迟**

  分别测量窗口回退、UIA 局部候选、视觉局部候选和候选切换的 P50/P95；只根据重复测量结果调整 16ms 节流、8ms 轮询和 48ms 稳定延迟。

  验收：首帧不等待 UIA；第一次可信局部候选不额外等待完整稳定周期；两个可信候选之间切换不抖动；响应改善超过运行噪声。

## 阶段五：兼容性和回归保护

- [ ] **任务 17：建立 VSCode/PyCharm 专用回归门禁**

  为编辑器、终端、侧栏、标签页、项目树、工具窗口和底部面板记录目标矩形、来源、候选层级和点击结果；所有后续任务都必须通过该门禁。

  验收：任何阶段导致 VSCode/PyCharm 从局部元素退化到 Client/Window，必须停止后续任务并先修复回归。

- [ ] **任务 18：完成 Windows Terminal、记事本、资源管理器和普通 Qt/Win32 回归**

  验证 UIA/MSAA 失败时的安全回退、已知内容定位、手动框选优先、快速移动和临时窗口行为。

  验收：已有记事本/资源管理器能力无回退；Terminal 无 UIA 时仍有稳定 Client/Window 回退；普通应用不会大量产生视觉误吸附。

- [ ] **任务 19：完成高 DPI、多显示器和边缘场景回归**

  覆盖不同缩放比例、负坐标显示器、显示器交界、窗口贴边、任务栏附近、浏览器外壳边缘和截图裁剪边缘。

  验收：屏幕坐标、截图坐标、Overlay 坐标和候选矩形始终一致；没有越界、偏移或跨屏错误。

- [ ] **任务 20：验证资源生命周期和线程安全**

  检查 UIA COM 对象、MSAA 接口、线程退出、定时器、HANDLE、GDI/USER 对象和 Overlay 销毁期间的晚到结果。

  验收：连续打开/关闭截图、快速切换模式、取消拖拽和销毁 Overlay 后无崩溃、死锁、悬空结果或资源计数持续增长。

## 阶段六：可选增强能力和交付

- [ ] **任务 21：评估浏览器 DOM/扩展增强方案**

  单独评估 Chrome DevTools Protocol、浏览器扩展或 Native Messaging 对网页 DOM 元素的帮助；明确它们不能覆盖浏览器标签栏和书签栏，并评估权限、稳定性和分发成本。

  验收：形成“采用/不采用”的决策记录；默认截图流程不依赖扩展或远程调试端口。

- [ ] **任务 22：评估按需 OCR/视觉模型增强模式**

  以 OmniParser、OCR 或轻量图标检测为参考，只在用户显式触发、鼠标停留或规则识别失败时运行；禁止放入默认每帧悬停路径。

  验收：有独立性能预算、模型加载失败回退和隐私说明；增强模式关闭时主流程行为不变。

- [ ] **任务 23：建立智能吸附专项性能验收**

  记录首帧、局部候选出现、候选切换、视觉扫描、UIA 查询和 Overlay 重绘的 P50/P95；同时检查工作集、线程、HANDLE、GDI 和 USER 计数。

  验收：响应改进有前后对比数据；自动化测试通过；未测量的性能结论不得写入交付说明。

- [ ] **任务 24：更新技术文档和最终验收矩阵**

  更新架构说明、候选来源说明、浏览器限制、诊断开关、人工复测矩阵、回退策略和已知限制；记录所有未完成或仅待验证的场景。

  验收：文档与代码行为一致；VSCode/PyCharm 保护条件、浏览器能力边界和性能数据均可追溯。

# 智能吸附当前基线修复计划

## 目标

以当前能够基本识别 VSCode、PyCharm 元素的代码为开发基线，不整体合并 `backup/smart-region-stage1-9`。选择性吸收资料和备份分支中经过验证的 UIA、MSAA、局部视觉、候选评分、层级切换与模式设计，提升 Chrome/Edge、VSCode、PyCharm、终端、WPS/Office、资源管理器、GitLab 等常见场景的小元素识别能力。

项目级交付指标：

- Release 交付包不超过 20 MB。
- 空闲工作集不超过 40 MB。
- 热键到 Overlay 首帧 P95 不超过 300 ms。
- 当前已经能够识别的 VSCode、PyCharm 元素不得回退。
- 手动拖拽始终优先，不影响截图、复制、长截图和标注流程。

## 实施原则

- 保留 `backup/smart-region-stage1-9` 作为参考和问题复现分支，不整体合入当前分支。
- 每项能力独立实现、独立测试、独立提交，发生回退时可以准确撤销。
- 先建立真实场景证据，再调整算法和分值。
- UIA、MSAA、视觉检测按需执行，不无条件并行调用。
- 视觉检测复用冻结桌面截图，只分析鼠标附近 ROI，不重复截取全屏。
- 暂不引入完整 OpenCV、OCR、AI 模型、浏览器扩展或 DOM 注入。
- 所有跨进程 COM、GDI、HANDLE 和线程资源必须使用 RAII 管理。

## 推荐检测链路

```text
Win32 窗口定位
  -> UIA 有效局部候选
  -> UIA 无有效局部候选时尝试 MSAA
  -> 已知应用内容区域
  -> 局部视觉候选
  -> Client 区域
  -> 整个窗口
```

“UIA 返回了候选”不等于“UIA 返回了有效局部候选”。大型 `Document`、`Pane`、`Group` 或接近整个 Client 的区域不能阻止 MSAA 和视觉兜底。

## 第一阶段：固定基线与建立诊断能力

### 任务 1：建立真实软件基线矩阵

记录当前版本在以下应用中的实际吸附结果：

- Chrome/Edge：图片、按钮、输入框、卡片、列表项、网页内容区。
- VSCode：编辑器、终端、侧边栏、标签页、面板。
- PyCharm：编辑器、项目树、终端、工具窗口。
- WPS/Office、记事本、资源管理器、传统 Win32/Qt 程序。
- GitLab：单条提交、提交正文、按钮和侧栏。

验收条件：

- [ ] 每个场景标记为“可识别”“只能整窗”“识别错误”或“不稳定”。
- [ ] 保存典型成功点和失败点的截图及坐标。
- [ ] 后续每个阶段都与该基线对比，VSCode/PyCharm 已有能力不得回退。

依赖：无。

### 任务 2：补充可开关的候选诊断

为一次鼠标定位记录候选来源、语义、矩形、面积、UIA 层级、视觉边界证据、最终评分、拒绝原因、回退原因和耗时。

验收条件：

- [ ] 能明确解释一次检测为什么最终选择 Client 或整个窗口。
- [ ] 诊断默认关闭，Release 默认路径无日志和明显额外开销。
- [ ] 不记录控件文本、文档正文等可能包含隐私的内容。

依赖：任务 1。

### 检查点 A：基线可解释

- [ ] 自动化测试和 Release 构建保持通过。
- [ ] 至少收集 Chrome、VSCode、PyCharm、终端和 GitLab 的真实样本。
- [ ] 能区分“未发现候选”“候选被拒绝”“候选评分失败”和“候选出现过晚”。

## 第二阶段：修复候选选择与回退链路

### 任务 3：定义有效局部候选

建立统一候选有效性规则：包含鼠标、矩形有效、位于目标窗口范围内、尺寸合理，并对接近整个窗口面积的泛化容器降权。

验收条件：

- [ ] 零尺寸、屏幕外、超出 Owner 的异常矩形被拒绝。
- [ ] 大型 `Document`、`Pane`、`Group` 不再被视为已经找到小元素。
- [ ] 合理的按钮、输入框、标签页和列表项优先于大型内容容器。

依赖：任务 2。

### 任务 4：修复 UIA、MSAA 和视觉回退条件

将 MSAA 的触发条件从“UIA 候选数量为零”改为“UIA 没有有效局部候选”。高质量 UIA 命中时不额外调用 MSAA；UIA 只有大型内容容器时继续尝试 MSAA 和视觉检测。

验收条件：

- [ ] 大型 UIA 候选不会阻止 MSAA 和视觉兜底。
- [ ] 高质量 UIA 小控件命中时不产生无意义的 MSAA 调用。
- [ ] 所有来源失败时稳定回退到 Client，再回退到 Window。

依赖：任务 3。

### 检查点 B：回退路径正确

- [ ] 增加“大型 UIA 候选 + 有效 MSAA/视觉候选”的排序测试。
- [ ] Chrome、VSCode 和 PyCharm 不因回退链路调整而只剩整窗候选。
- [ ] 手动拖拽和现有截图动作无回退。

## 第三阶段：增强 UIA 小元素识别

### 任务 5：完善 UIA 候选层级和语义映射

从鼠标命中元素向上收集有限层级候选，覆盖可操作控件、内容容器、Client 和 Window。扩展 Button、Edit、ComboBox、ListItem、TreeItem、TabItem、MenuItem、Hyperlink、CheckBox、RadioButton、Document、List、Table、DataGrid 等语义；`Pane`、`Group` 和自定义控件结合面积及属性判断。

验收条件：

- [ ] 当前 VSCode/PyCharm 已识别元素保持正常。
- [ ] 浏览器输入框、按钮和标签页等 UIA 元素优先于网页整体。
- [ ] 不因支持 `Pane`、`Group` 和自定义控件而大量生成错误小框。

依赖：任务 3、任务 4。

### 任务 6：优化 UIA 查询性能和生命周期

评估并实现专用 MTA 工作线程、`ElementFromPointBuildCache` 或等效缓存请求、查询预算、失败冷却及短期位置缓存。Overlay 首帧不得等待跨进程 UIA。

验收条件：

- [ ] UIA 提供方卡顿或无响应时不阻塞 Overlay 交互。
- [ ] 连续移动期间不重复创建 UIA COM 对象。
- [ ] COM 和线程资源通过 RAII 管理，无引用泄漏和悬空回调。
- [ ] 热键到 Overlay 首帧 P95 不超过 300 ms。

依赖：任务 5。

## 第四阶段：修复和增强局部视觉检测

### 任务 7：修复 ROI 与 Owner 边界语义不一致

统一 ROI 边界、Owner 边界和缺失边界的坐标含义。区分“被 ROI 裁剪”与“确实贴近窗口边缘”，避免候选边缘位于 ROI 外时被错误拒绝。

验收条件：

- [ ] 靠近 ROI 或窗口边缘的 Chrome 图片卡片仍可识别。
- [ ] 横向较宽的 GitLab 提交记录不会因超出 ROI 被错误拒绝。
- [ ] 不会把 ROI 自身边缘误判为控件边界。

依赖：任务 2。

### 任务 8：增强小部件和弱边界识别

综合内外颜色差异、连续边界长度、矩形完整度、圆角容忍、浅色/暗色边框、阴影及填充一致性；降低文字笔画、代码字符、道路纹理、图片内部线条和表格细线的误识别概率。

验收条件：

- [ ] Chrome 图片、卡片和列表项命中率相对基线提高。
- [ ] VSCode/PyCharm 代码文本不会频繁形成碎片小框。
- [ ] 浅色和暗色主题均有稳定结果。
- [ ] 不引入完整 OpenCV 动态库。

依赖：任务 7。

### 检查点 C：小元素与边缘能力

- [ ] 合成测试覆盖完整四边、三边、弱边、圆角、暗色、浅色和 ROI 裁剪场景。
- [ ] 真实 Chrome 图片卡片、GitLab 提交记录和终端内容区域完成回归。
- [ ] 单次视觉检测只访问局部 ROI，不重复抓取全屏。

## 第五阶段：重新设计候选评分与层级

### 任务 9：拆分候选评分维度

评分拆分为来源、控件语义、鼠标位置、面积适配度、边界证据、父子层级和历史稳定性。大型 UIA 内容区不能只依赖来源分值获胜，高置信度视觉区域可以优先于泛化容器。

验收条件：

- [ ] 图片卡片、按钮等合理局部区域能够胜过整个网页或 Client。
- [ ] 低置信度视觉碎片不能胜过可信内容区。
- [ ] 每个降权和拒绝均有可诊断原因。

依赖：任务 3、任务 5、任务 8。

### 任务 10：候选去重和层级整理

合并高度重叠、面积接近的重复候选，保留控件、父容器、内容区、Client 和窗口等有意义层级。初始选择按最终评分，循环顺序按层级关系，而不是只按面积。

验收条件：

- [ ] UIA、MSAA 和视觉返回相近区域时不会反复切换。
- [ ] 候选层级稳定遵循“小控件 -> 父容器 -> 内容区 -> Client -> Window”。
- [ ] 候选集合固定容量且超限行为确定。

依赖：任务 9。

## 第六阶段：修复延迟与稳定策略

### 任务 11：避免候选长期停留在整窗

Overlay 首帧允许先显示窗口候选，但第一次有效局部候选不额外等待完整稳定周期。迟滞只用于两个可信局部候选之间的抖动，点击时使用已经完成的最新详细候选。

验收条件：

- [ ] 正常移动后不会长期停留在 Client 或整个窗口。
- [ ] 快速移动时没有明显闪烁和持续掉帧。
- [ ] 用户点击时不会因详细候选晚到而错误选择整窗。

依赖：任务 6、任务 9。

### 任务 12：确保手动选择优先

开始拖拽后立即退出智能候选状态；标注、长截图、复制等后续状态不重新触发智能吸附；晚返回的异步候选不得覆盖已确定选区。

验收条件：

- [ ] 手动框选始终优先于智能检测。
- [ ] 智能任务晚返回时不修改已确认选区。
- [ ] 现有复制、长截图、保存和标注流程保持可用。

依赖：任务 11。

### 检查点 D：交互稳定

- [ ] 首个有效局部候选及时显示。
- [ ] 相邻候选之间切换稳定但不迟钝。
- [ ] 快速移动、立即点击和拖拽场景均有状态回归测试。

## 第七阶段：候选切换与吸附模式

### 任务 13：增加候选层级切换

选择性移植备份分支的候选循环能力，保存鼠标位置下多个有效候选，支持 Tab 或不冲突的滚轮操作在候选层级间循环。

验收条件：

- [ ] 可在按钮、卡片、内容区、Client 和窗口之间循环。
- [ ] 鼠标明显移动后重新建立候选链。
- [ ] 不与箭头、线条、字体等已有滚轮交互冲突。

依赖：任务 10、任务 12。

### 任务 14：增加吸附模式

提供“检测元素”“仅窗口”“关闭吸附”三种模式，默认使用“检测元素”。配置读取不得阻塞 Overlay 首帧。

验收条件：

- [ ] 模式切换后清理旧候选、异步任务和定时器。
- [ ] 不因历史配置意外进入“仅窗口”状态。
- [ ] 三种模式均不影响手动截图流程。

依赖：任务 12、任务 13。

## 推荐执行顺序

1. 任务 1～4：建立证据并修复错误回退。
2. 任务 7：优先修复视觉 ROI 边界问题。
3. 任务 9～11：修复评分和整窗延迟。
4. 任务 5～6：增强 UIA 覆盖及查询性能。
5. 任务 8、任务 10：提升小部件、复杂边缘和候选层级能力。
6. 任务 12～14：完善交互、候选切换和模式。
7. 任务 15～16：完成真实应用与交付验收。

## 提交与回退策略

- 每个任务或紧密相关的小任务组单独提交。
- 提交前只暂存本任务相关文件，不使用 `git add .` 或 `git add -A`。
- 每个检查点记录自动化结果、真实应用结果和性能数据。
- 任一阶段导致 VSCode/PyCharm 已有识别能力回退时，停止后续任务，先定位该阶段变化。
- 不将 `backup/smart-region-stage1-9` 整体合并；只移植能够通过当前基线回归的独立实现。

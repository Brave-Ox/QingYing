## 1. 系统架构

### 1.1 交付形态

当前是 **1 个 Windows EXE + 10 个 static lib**，使用 C++17 + Win32，不依赖 Qt / Electron。

| 目标 | 当前职责 | 状态 |
|---|---|---|
| `qingying_action` | Action 契约 + Dispatcher | 完成 |
| `qingying_capture` | GDI 区域截图；DXGI / 截窗 / 中央裁切预留 | 部分完成 |
| `qingying_export` | CF_DIB / WIC PNG | 完成 |
| `qingying_ui` | 选区条 / 标注底栏共用 ModernToolbar、GDI+ 与 SVG 图标 | 完成 |
| `qingying_overlay` | 遮罩、框选、调区、吸附、ModernToolbar、长截图预览、就地标注入口 | 完成但偏重 |
| `qingying_annotate` | 文档、引擎、渲染器、编辑会话和编辑 Overlay | 已接线，窗口冒烟单列 |
| `qingying_pin` | 多 Pin、排布、缩放、独立导出、捕获排除 | 代码基本完成 |
| `qingying_longshot` | 记事本固定选区滚动拼接 | 记事本路径完成 |
| `qingying_command` | 本地口令 | Stub |
| `qingying_mcp` | MCP Bridge | Stub |

### 1.2 当前调用关系

```text
                       qingying_action
                 Request / Result / Image
                    Dispatcher / Handler
        ┌──────────┬──────────┬──────────┬─────────┐
        ▼          ▼          ▼          ▼         ▼
     capture     export      pin      command      mcp
        ▲                                  (stub)   (stub)
        │
     longshot

app/Application
  ├── 组合并注册 Handler
  ├── 调用 SelectionOverlay
  ├── 管理 CaptureSession
  ├── 管理长截图 worker
  └── 处理少量直接 Capture / Export 调用
```

`annotate` 已有完整代码链路；`window_detector.cpp` 物理上位于 `src/window`，但被编入 `qingying_overlay`。
选区 Edit 路径由 Overlay 隐藏遮罩、重抓选区后进入 `AnnotationOverlay`，确认结果再回到 Application。

### 1.3 普通截图数据流

```text
Hotkey
  → Application
  → 捕获虚拟桌面背景（直接 CaptureEngine，表现层快照）
  → SelectionOverlay
  → SelectionResult
  → ModernToolbar：Copy / Save / LongShot / Edit / Pin
  → Copy / Save / Pin：dispatch(CaptureRegion) → CaptureEngine
                              → Image → CaptureSession → 消费结果
  → Edit：Overlay 隐藏后直接重抓选区 → AnnotationOverlay
          → annotated_image → Application 写回 Session 并自动 Copy
```

### 1.4 长截图数据流

```text
SelectionOverlay / LongShot action
  → Application worker
  → Notepad profile
  → CaptureEngine 固定矩形取帧
  → ImageStitcher
  → Overlay preview
  → 托盘 UI 线程完成消息
  → CaptureSession
  → dispatch(Copy)
```

## 2. 已采用的设计模式

1. **Command**：`ActionRequest`、`IActionHandler`、`ActionDispatcher` 形成单步命令分发。
2. **Composition Root / 依赖注入**：`Application::registerHandlers` 组装 Capture、Export、Session 和 Pin。
3. **State Machine**：`SelectionController` 以 Creating / Resizing / Moving 模式管理纯选区逻辑。
4. **PIMPL**：Capture、LongShot、MCP 隐藏平台实现；当前仍需把裸 `Impl*` 改成 `unique_ptr`。
5. **RAII**：GDI deleter、Pin `CaptureGuard` 和容器所有权控制资源生命周期。
6. **值对象**：`Image` 不共享 HBITMAP / HDC，模块间传递稳定。
7. **Callback / Message Passing**：Overlay 回调、Pin 操作回调、长截图进度回调与 Win32 完成消息解耦反向依赖。
8. **Application Profile**：长截图用 Notepad profile 校验内容区和滚动目标，不改变用户选区。

## 3. 高耦合与优先改进项

### 3.1 `selection_overlay.cpp` 已成为上帝文件

当前约 1,325 行，同时负责：

- HWND 注册、创建、销毁和嵌套消息循环；
- 桌面背景与遮罩渲染；
- F1 鼠标路由、手柄和光标；
- F2 悬停检测与高亮；
- ModernToolbar 工具栏按钮创建、状态和命令分发；
- F6 捕获透传、预览、暂停、停止和收尾状态。
- F3 就地编辑前隐藏遮罩、重新抓取选区和 AnnotationOverlay 入口。

虽然 SelectionController、MaskRenderer、WindowDetector 等纯逻辑已抽出，但 Win32 壳仍继续膨胀。F3 已接入，后续 Save / Pin 回流和更多编辑能力会继续放大选区与标注生命周期耦合。

建议优先拆出：

```text
SelectionToolbar         描述表驱动按钮和命令
OverlayRenderer          背景 / 遮罩 / 选区 / 预览合成
OverlayPhase             显式阶段转换
SelectionOverlay         只保留窗口和消息路由
```

### 3.2 工具栏是硬编码分支

选区条按钮 ID、创建顺序、启用条件和 `WM_COMMAND` switch 仍分散在同一文件；“编辑”按钮现在已启用并可进入就地标注。标注底栏虽已共用 ModernToolbar，但编辑器的工具和属性栏仍有独立命令表。

建议借鉴成熟截图产品的“命令描述表 + Toolbar Builder”思想，但不引入 Qt Action：

```text
ToolbarCommandDescriptor
  → SelectionToolbar
  → local UI command / SelectionAction
```

局部工具命令与系统 `ActionType` 保持分离。

### 3.3 Overlay 用多组 bool 表达阶段

`selection_confirmed`、`has_hover`、`longshot_active`、`longshot_paused`、`longshot_finishing`、`closed`、`capture_passthrough` 等状态可以组合出无效情况。

建议引入显式 `OverlayPhase`，至少区分：

```text
Sniffing / Creating / Selected / LongShotRunning /
LongShotPaused / LongShotFinishing / Closing
```

悬停候选等正交状态可保留为数据，但长截图生命周期不再依赖多个互相约束的布尔量。

### 3.4 原架构硬规则与代码已经漂移

原文档曾写：

- “消息循环只在 app”；
- “业务能力只经 ActionDispatcher”。

当前实际：

- `SelectionOverlay::show` 有同线程嵌套模态 `GetMessage`；
- `AnnotationOverlay::showInPlace` 也有同线程嵌套模态 `GetMessage`；
- Application 直接捕获桌面背景；
- SelectionOverlay 在就地编辑前隐藏遮罩并直接重新调用 `CaptureEngine`；
- 交互式长截图直接调用 `LongShotEngine`；
- GUI 保存对话框选择路径后直接调用 `ExportService`；
- `LongShotRegion` 枚举存在但没有 Handler。

这些并不意味着所有调用都必须机械包成同步 Action。应明确区分：

- 单步、可复用、可由外部入口调用的 **Action**；
- 选区、标注、长截图等有 UI 生命周期的 **Workflow**；
- 背景快照和预览等 **Presentation Infrastructure**。

### 3.5 Application 同时承担组合与工作流状态

`Application` 当前约 386 行，持有所有服务，又管理：

- 普通截图分支；
- 保存对话框；
- 长截图 worker、atomic 控制、完成消息和错误文案；
- owner window、pending request、结果就绪状态。

作为 Composition Root，持有依赖是合理的；但继续接入 F3 / F8 / F9 会让工作流条件迅速增加。

建议抽 `CaptureWorkflow`，Application 保留启动、组合和消息转发。

### 3.6 ActionRequest 是胖结构体

当前所有动作共用 `x/y/width/height/window_handle/window_query/crop_w/crop_h/save_path`。新增 F8/F9 参数会继续膨胀，并依赖 `type` 才知道字段含义。

建议在 F8/F9 前改成类型安全 payload：

```cpp
using ActionPayload = std::variant<
    StatusRequest,
    CaptureRegionRequest,
    CaptureWindowRequest,
    CropCenterRequest,
    SaveRequest,
    PinRequest>;
```

如果暂不引入 variant，至少为每类请求建立命名结构体和验证函数。

### 3.7 CaptureSession 是隐式时序通道

Capture Handler 写入，Copy / Save / Pin Handler 读取，调用者必须知道“先捕获再消费”。这是有意表达“最近结果”的 UI 语义，但也形成隐式共享状态。

建议：

- GUI 当前结果继续保留 Session；
- 外部 MCP 请求使用显式 `capture_id` 或操作上下文；
- F3 明确原始图、编辑文档和最终图的覆盖时机；
- 不把大 Image 直接塞进通用字符串 `ActionResult.data`。

### 3.8 构建依赖存在无效耦合

`qingying_overlay` 当前公开链接 `qingying_capture`，且 SelectionOverlay 在就地编辑前直接使用 `CaptureEngine` 重抓选区；背景快照仍由 Application 传入。若以后由 Workflow 统一产生源图，再考虑删除该公开链接。

建议删除该链接，使依赖变为：

```text
overlay → action + dwmapi
app → overlay + capture
```

### 3.9 WindowDetector 的目标归属可能变化

当前编入 overlay 是合理的局部实现。但 F8 截窗和更多长截图 profile 若需要相同发现 / 过滤逻辑，应拆 `qingying_window`，避免复制规则。

不要仅为目录好看提前拆库；以第二个真实消费者出现为触发条件。

### 3.10 PIMPL 与跨线程消息仍有裸 new/delete

- `CaptureEngine::Impl*`；
- `LongShotEngine::Impl*`；
- `McpBridge::Impl*`；
- 长截图完成和预览消息临时 `new` 后通过 Win32 消息转移所有权。

前三项应直接改为 `std::unique_ptr<Impl>`。跨线程消息可保留所有权转移，但需要统一封装，确保 `PostMessage` 失败和窗口退出时都释放。

### 3.11 坐标语义仍靠约定

物理屏幕、Overlay 客户区、Image 像素、标注视图坐标即将同时存在。仅用 `int x/y` 容易在 F3/F8/F9 中混用。

建议先为矩形建立命名类型：

```text
ScreenPhysicalRect
OverlayClientRect
ImagePixelRect
AnnotationViewRect
```

不必为每个整数做强类型，但跨模块接口必须携带坐标空间名称。

## 4. 低耦合、应继续保持的部分

### 4.1 action 层不依赖 Win32

Action、Image、Dispatcher 和 Handler 接口不包含 `<Windows.h>`，是 command / mcp 未来复用的基础。

### 4.2 纯选区逻辑可独立测试

`SelectionController`、`selection_handles`、`coordinate_transform` 与大部分 MaskRenderer 逻辑可自动测试，F1 变化不会强迫启动 UI。

### 4.3 WindowDetector 内聚

窗口提升、候选过滤和 DWM 边框规则集中在一个类，没有散落到 SelectionController。

### 4.4 ExportService 独立

只依赖 Image 和 ActionResult；Pin 通过回调复用导出，而不是建立 pin → export 编译依赖。

### 4.5 Pin 窗口拥有自己的 Image

多个 Pin 不共享“当前 Session 图片”，避免一张 Pin 的复制 / 保存串到另一张图。

### 4.6 LongShotEngine 不拥有 UI

引擎只做 profile、滚动、捕获、拼接和回调，不创建 Overlay、不写 Session、不导出图片。

### 4.7 ImageStitcher 是纯图片算法

它不知道 Win32、滚轮或目标应用，能够用人工构造图片覆盖重叠、无重叠、容差和异常尺寸。

### 4.8 失败清理已有明确方向

长截图失败清空输出，Application 只有成功才覆盖 Session；Pin CaptureGuard 用 RAII 恢复窗口。这些失败语义应继续写进新模块测试。

## 5. 优先级结论

| 优先级 | 调整 | 原因 |
|---|---|---|
| P0 | 抽 SelectionToolbar + 命令描述 | F3 已接线，必须阻止 Save / Pin 回流和后续能力继续把 Overlay 做大 |
| P0 | 引入 OverlayPhase | 当前多布尔状态已有 F6 复杂度 |
| P1 | 让 Workflow 产出编辑源图，收紧 overlay → capture 依赖 | 当前就地编辑仍需 Overlay 直接重抓选区 |
| P1 | 新增 CaptureWorkflow | 给 F3 和后续交互式能力一个明确编排位置 |
| P1 | 非模态化 Overlay | 消除嵌套消息循环与退出边界复杂性 |
| P1 | PIMPL unique_ptr | 小改动，统一 RAII |
| P2 | Action payload 类型化 | F8/F9 前完成，避免外部协议固化胖结构体 |
| P2 | Session / operation id 边界 | MCP 与异步工作流需要显式上下文 |
| 条件触发 | 拆 qingying_window | 等出现第二个真实复用者 |

详细迁移步骤与验收标准见 [架构如何调整.md](架构如何调整.md)。

## 6. 一句话结论

现有骨架仍然健康：Action 契约、纯逻辑选区、Image 值对象、Export、Annotation、Pin 与 LongShot 算法边界都可复用。主要问题不是模块数量，而是 **Overlay 和 Application 在接入 F2/F3/F5/F6 后承担了过多交互状态，原先两条硬规则也已不再准确**。应先做小步、可回归的结构收敛，再补齐 F3 动作回流并进入 F8/F9；不需要重写成 Qt、插件 DLL 或多进程架构。

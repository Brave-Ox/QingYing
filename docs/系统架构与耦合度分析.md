## 1. 系统架构

### 1.1 交付形态

当前是 **1 个 Windows EXE + 11 个 static lib**，使用 C++17 + Win32，不依赖 Qt / Electron。

| `qingying_export` | CF_DIB / WIC PNG | 完成 |
| `qingying_ui` | 选区条 / 标注底栏共用 ModernToolbar、GDI+ 与 SVG 图标 | 完成 |
| `qingying_overlay` | 遮罩、框选、调区、吸附、SelectionToolbar、OverlayPhase、OverlayRenderer、长截图预览 | Renderer 已拆出，消息循环仍偏重 |
| `qingying_annotate` | 文档、引擎、渲染器、编辑会话和编辑 Overlay | 已接线，窗口冒烟单列 |

### 1.2 当前调用关系

```text
                       qingying_action
                 Request / Result / Image
                    Dispatcher / Handler
        ┌──────────┬──────────┬──────────┬─────────┐
        ▼          ▼          ▼          ▼         ▼
     capture     export      pin      command      mcp
        ▲                                  (stub)   (stub)
        │
     longshot

app/Application
  ├── 组合并注册 Handler / CaptureWorkflow
  ├── 托盘、热键与顶层消息泵
  └── 转发开始捕获和长截图完成消息

qingying_workflow/CaptureWorkflow
  ├── Selection / Annotation / 结果操作编排
  ├── 背景与编辑源图获取
  ├── 管理 CaptureSession 和保存对话框
  └── 请求 LongShotController 并处理其业务结果

qingying_workflow/LongShotController
  ├── 单个长截图 worker 与 pause / stop token
  ├── Overlay 预览转发
  └── 完成 payload 投递、UI 接管与 join / shutdown
```

`annotate` 已有完整代码链路；`window_detector.cpp` 物理上位于 `src/window`，但被编入 `qingying_overlay`。
选区 Edit 路径只由 Overlay 上报意图；CaptureWorkflow 在选区窗口结束后抓取源图并进入 `AnnotationOverlay`，确认后恢复同一选区的结果操作条。

### 1.3 普通截图数据流

```text
Hotkey
  → Application
  → CaptureWorkflow
  → 捕获虚拟桌面背景（直接 CaptureEngine，表现层快照）
  → SelectionOverlay
  → SelectionResult
  → SelectionToolbar：Copy / Save / LongShot / Edit / Pin
  → Copy / Save / Pin：dispatch(CaptureRegion) → CaptureEngine
                              → Image → CaptureSession → 消费结果
  → Edit：Overlay 返回意图 → CaptureWorkflow 捕获源图 → AnnotationOverlay
          → annotated_image → 写回 Session 并自动 Copy
          → 合成桌面预览 → 恢复结果操作条 → Save / Pin / 再编辑
```

### 1.4 长截图数据流

```text
SelectionOverlay / LongShot action
  → CaptureWorkflow 请求 LongShotController
  → LongShotController worker
  → Notepad profile
  → CaptureEngine 固定矩形取帧
  → ImageStitcher
  → Overlay preview
  → 托盘 UI 线程完成消息
  → CaptureSession
  → dispatch(Copy)
```

## 2. 已采用的设计模式

1. **Command**：`ActionRequest`、`IActionHandler`、`ActionDispatcher` 形成单步命令分发。
2. **Composition Root / 依赖注入**：`Application::registerHandlers` 组装 Capture、Export、Session 和 Pin。
3. **State Machine**：`SelectionController` 管理纯选区几何；`OverlayPhase` 管理 Sniffing / Creating / Selected / LongShot / Closing 顶层阶段并拒绝非法转换。
4. **PIMPL**：Capture、LongShot、LongShotController、MCP 隐藏平台实现，均已改为 `std::unique_ptr<Impl>`，并在 `.cpp` 中定义析构函数。
5. **RAII**：GDI deleter、Pin `CaptureGuard` 和容器所有权控制资源生命周期。
6. **值对象**：`Image` 不共享 HBITMAP / HDC，模块间传递稳定。
7. **Callback / Message Passing**：Overlay 回调、Pin 操作回调、长截图进度回调与 Win32 完成消息解耦反向依赖。
8. **Application Profile**：长截图用 Notepad profile 校验内容区和滚动目标，不改变用户选区。

## 3. 高耦合与优先改进项

### 3.1 `selection_overlay.cpp` 的拆分结果

当前约 780 行，仍负责：

- HWND 注册、创建、销毁、消息路由和嵌套消息循环；
- F1 鼠标路由、手柄和光标；
- F2 悬停检测与高亮；
- F6 捕获透传、暂停、停止和收尾消息路由。

`SelectionToolbar`、`OverlayPhase`、`OverlayRenderer` 和 F3 捕获 / 编辑职责已经移出；SelectionController、MaskRenderer、WindowDetector 等纯逻辑也保持独立。剩余主要集中在模态窗口壳。

建议优先拆出：

```text
SelectionToolbar         已完成：描述表驱动按钮和命令
OverlayPhase             已完成：显式阶段转换
OverlayRenderer          已完成：背景 / 遮罩 / 选区 / 预览合成
SelectionOverlay         目标：只保留窗口和消息路由
```

### 3.2 选区工具栏分支已收口

选区条按钮 HWND、命令映射、Tooltip、绘制与命中测试已移入 `SelectionToolbar`；`buildSelectionToolbarItems(OverlayPhase)` 是可独立测试的纯状态映射。`selection_overlay.cpp` 只消费 `SelectionToolbarCommand`，局部命令仍与系统 `ActionType` 分离。

当前实现沿用“命令描述 + Toolbar Builder”思想，但不引入 Qt Action：

```text
SelectionToolbarItemModel
  → SelectionToolbar
  → local UI command / SelectionAction
```

局部工具命令与系统 `ActionType` 保持分离。

### 3.3 OverlayPhase 已替代互斥阶段 bool

`selection_confirmed`、`longshot_active`、`longshot_paused`、`longshot_finishing`、`closed` 已由单一 `OverlayPhase` 替代，非法阶段转换由 `canTransitionOverlayPhase` 拒绝。

当前显式阶段为：

```text
Sniffing / Creating / Selected / LongShotRunning /
LongShotPaused / LongShotFinishing / Closing
```

`has_hover`、`capture_passthrough`、拖拽模式和预览 Image 是正交数据；它们不再承担选区 / 长截图 / 关闭阶段本身的含义。

### 3.4 原架构硬规则与代码已经漂移

原文档曾写：

- “消息循环只在 app”；
- “业务能力只经 ActionDispatcher”。

当前实际：

- `SelectionOverlay::show` 有同线程嵌套模态 `GetMessage`；
- `AnnotationOverlay::showInPlace` 也有同线程嵌套模态 `GetMessage`；
- CaptureWorkflow 直接捕获桌面背景；
- CaptureWorkflow 在 SelectionOverlay 返回 Edit 后直接调用 `CaptureEngine` 产生编辑源图；
- 交互式长截图由 `LongShotController` 管理异步生命周期，再调用 `LongShotEngine`；
- GUI 保存对话框选择路径后直接调用 `ExportService`；
- `LongShotRegion` 枚举存在但没有 Handler。

这些并不意味着所有调用都必须机械包成同步 Action。应明确区分：

- 单步、可复用、可由外部入口调用的 **Action**；
- 选区、标注、长截图等有 UI 生命周期的 **Workflow**；
- 背景快照和预览等 **Presentation Infrastructure**。

### 3.5 CaptureWorkflow 与长截图控制已分层

`Application` 已从约 409 行降至约 105 行，只保留对象组装、Tray / Hotkey、顶层消息泵和 Workflow 消息转发。新建的 `qingying_workflow` / `CaptureWorkflow` 负责：

- 普通截图分支；
- 选区 → 标注 → 结果操作条的顺序编排；
- 保存对话框与错误文案；
- owner window、pending request、结果就绪状态；
- 长截图结果状态与业务错误处理；

同步工作流边界已经建立并有 6 个纯路由测试；`LongShotController` 另有 4 个生命周期测试，负责 worker、atomic 控制、预览转发、完成 payload 与 join。下一步将 Selection / Annotation Overlay 改成由 Application 顶层消息泵驱动的非模态窗口。

### 3.6 ActionRequest 是胖结构体

当前所有动作共用 `x/y/width/height/window_handle/window_query/crop_w/crop_h/save_path`。新增 F8/F9 参数会继续膨胀，并依赖 `type` 才知道字段含义。

建议在 F8/F9 前改成类型安全 payload：

```cpp
using ActionPayload = std::variant<
    StatusRequest,
    CaptureRegionRequest,
    CaptureWindowRequest,
    CropCenterRequest,
    SaveRequest,
    PinRequest>;
```

如果暂不引入 variant，至少为每类请求建立命名结构体和验证函数。

### 3.7 CaptureSession 是隐式时序通道

Capture Handler 写入，Copy / Save / Pin Handler 读取，调用者必须知道“先捕获再消费”。这是有意表达“最近结果”的 UI 语义，但也形成隐式共享状态。

建议：

- GUI 当前结果继续保留 Session；
- 外部 MCP 请求使用显式 `capture_id` 或操作上下文；
- F3 明确原始图、编辑文档和最终图的覆盖时机；
- 不把大 Image 直接塞进通用字符串 `ActionResult.data`。

### 3.8 overlay 构建依赖已收口

`qingying_overlay` 已删除对 `qingying_capture` 和 `qingying_annotate` 的链接；SelectionOverlay 只上报 Edit 意图，背景和编辑源图都由 CaptureWorkflow 产生。

当前依赖已变为：

```text
overlay → action + dwmapi
workflow → overlay + capture + annotate + export + pin + longshot
app → workflow（并作为 Composition Root 持有具体服务）
```

### 3.9 WindowDetector 的目标归属可能变化

当前编入 overlay 是合理的局部实现。但 F8 截窗和更多长截图 profile 若需要相同发现 / 过滤逻辑，应拆 `qingying_window`，避免复制规则。

不要仅为目录好看提前拆库；以第二个真实消费者出现为触发条件。

### 3.10 PIMPL 已 RAII 化，跨线程消息仍有裸 new/delete

`CaptureEngine`、`LongShotEngine`、`LongShotController`、`McpBridge` 的 PIMPL 已统一为 `std::unique_ptr<Impl>`，并保留 `.cpp` 内析构以满足不完整类型要求。长截图完成和预览消息仍会临时 `new` 后通过 Win32 消息转移所有权；后续需要统一封装，确保 `PostMessage` 失败和窗口退出时都释放。

### 3.11 坐标语义仍靠约定

物理屏幕、Overlay 客户区、Image 像素、标注视图坐标即将同时存在。仅用 `int x/y` 容易在 F3/F8/F9 中混用。

建议先为矩形建立命名类型：

```text
ScreenPhysicalRect
OverlayClientRect
ImagePixelRect
AnnotationViewRect
```

不必为每个整数做强类型，但跨模块接口必须携带坐标空间名称。

## 4. 低耦合、应继续保持的部分

### 4.1 action 层不依赖 Win32

Action、Image、Dispatcher 和 Handler 接口不包含 `<Windows.h>`，是 command / mcp 未来复用的基础。

### 4.2 纯选区逻辑可独立测试

`SelectionController`、`selection_handles`、`coordinate_transform` 与大部分 MaskRenderer 逻辑可自动测试，F1 变化不会强迫启动 UI。

### 4.3 WindowDetector 内聚

窗口提升、候选过滤和 DWM 边框规则集中在一个类，没有散落到 SelectionController。

### 4.4 ExportService 独立

只依赖 Image 和 ActionResult；Pin 通过回调复用导出，而不是建立 pin → export 编译依赖。

### 4.5 Pin 窗口拥有自己的 Image

多个 Pin 不共享“当前 Session 图片”，避免一张 Pin 的复制 / 保存串到另一张图。

### 4.6 LongShotEngine 不拥有 UI

引擎只做 profile、滚动、捕获、拼接和回调，不创建 Overlay、不写 Session、不导出图片。

### 4.7 ImageStitcher 是纯图片算法

它不知道 Win32、滚轮或目标应用，能够用人工构造图片覆盖重叠、无重叠、容差和异常尺寸。

### 4.8 失败清理已有明确方向

长截图失败清空输出，CaptureWorkflow 只有成功才覆盖 Session；Pin CaptureGuard 用 RAII 恢复窗口。这些失败语义应继续写进新模块测试。

## 6. 一句话结论

现有骨架仍然健康，第一批收敛也验证了可以小步调整：SelectionToolbar、OverlayPhase、OverlayRenderer、CaptureWorkflow、LongShotController、编辑源图上移和 F3 结果回流均已完成；CaptureWorkflow 路由测试 6/6、LongShotController 生命周期测试 4/4 通过，整体测试中的 4 个 `BitBlt` 失败属于当前环境既有问题。当前主要问题转为 **Selection / Annotation Overlay 仍有嵌套消息循环**。下一步应进行非模态化，再进入 F8/F9；不需要重写成 Qt、插件 DLL 或多进程架构。

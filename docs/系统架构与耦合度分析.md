# 轻映 QingYing — 系统架构与耦合度分析

> 分析基线：`master` / `40d22e21`（104 条提交）
> 分析日期：2026-09-07
> 范围：仓库文档、CMake、`src/`、`include/`、现有测试与最近提交。
> 本文区分“已经落地的架构收口”和“实现 F9 前仍需补齐的边界”，不把历史整改计划误写成当前缺陷。

## 1. 当前架构结论

当前的模块化方向可以保留：一个 Windows EXE、多个 static lib、`ActionDispatcher` 负责单步动作、`Application` 负责组合与顶层消息泵。长截图运行时已经增加受控的 profile DLL ABI，但 DLL 只承载内置适配器，不改变应用层的单进程业务边界。

```text
Application / 顶层消息泵
  ├── CaptureWorkflow ── SelectionOverlay / AnnotationOverlay
  │     ├── Capture / ResultStore / ResultActionService / Pin
  │     └── LongShotController ── LongShotEngine ── ProfileRegistry / DLL Host
  └── ActionDispatcher ── app_handlers ── Capture / Export / Pin
                                   ▲
                    command / mcp（当前仍为 Stub）
```

已经落地且不需要重新设计的部分：

- `SelectionToolbar`、`OverlayPhase`、`OverlayRenderer` 已从选区主窗口中抽出；Selection 和 Annotation Overlay 使用顶层消息泵，创建后立即返回，不再自建嵌套消息循环。
- `LongShotController` 已接管 worker、暂停/停止、完成通知、cancel/join/drain；跨线程 payload 由 `UiMessageChannel` 持有，窗口消息只携带 token。
- `ResultStore` 与 `ResultActionService` 已统一截图结果及 Copy / Save / Pin；`CaptureSession` 仅作为兼容门面保留。
- `ActionRequest` 已使用 `std::variant` 类型化 payload，并带 request / operation id、取消、超时和 `ResultSelection`。
- `ScreenPhysicalRect`、`OverlayClientRect`、`ImagePixelRect` 等命名坐标类型已建立；F6 已有通用 runtime、插件宿主和 Notepad / Explorer / Chromium profile DLL。
- `AnnotationEditorHost` 已拆分为多个内部组件，`Application`、`qingying_app_handlers` 和测试的编译边界已收窄。

## 2. 仍需处理的耦合与缺口

### 2.1 P0：F9 尚无可用的应用入口

`src/mcp/mcp_bridge.cpp` 中 `McpBridge::start()` 仍返回 `false`，`submit()` 只是同步调用 Dispatcher；`Application` 尚未构造、启动或停止 Bridge。当前没有 Named Pipe、JSON-RPC session、Tool catalog、主线程调度、鉴权边界或外部操作注册表。

F9 应在 `McpBridge` 与 GUI 之间增加中立的 `AutomationEndpoint`，由 `UiActionScheduler` 把请求投递到 UI 线程，再进入现有 `ActionDispatcher` 或受控 `CaptureWorkflow`。协议层不应 include `Application`、Overlay、GDI、DXGI 或插件私有头。

### 2.2 P0：结果仍是单槽位，不能直接作为外部租约

当前 `ResultStore` 只保留一个 current 结果，替换、工作流结束、取消或退出时会释放旧像素；`get()` 还会深拷贝图片。这满足 GUI 的“最近结果”语义，但不能满足 MCP 的并发作用域、`result_id`、过期和释放契约。

F9 需要在现有 Store 之上增加作用域、不可变结果元数据、有限租约和字节预算。`ActionResult` 也需要返回类型化的 result metadata，不能只依赖 Handler 写入 Store 后再猜测 current。该层应保持与 GUI 的 current 兼容语义隔离。

### 2.3 P0：交互式工作流缺少外部异步契约

`CaptureWorkflow` 仍是选区、标注、结果发布和交互式长截图的编排器，这是当前 GUI 所需的职责，但 `beginSelection` 等接口只表达“是否启动”，没有稳定的 operation 状态、完成回调、取消和超时契约。F9 的 `longshot_select` 必须立即返回 `operation_id`，后续通过 registry 查询或取消，不能阻塞 Pipe 线程等待窗口。

### 2.4 P1：UI 消息所有权已有基础，仍缺代际与准入

`UiMessageChannel` 已统一 token、payload 所有权、take/discard/drain；这解决了裸指针跨 HWND 投递和 shutdown 回收问题。它目前没有 operation generation、队列准入上限和自动化请求的公平调度。F9 接入前应在此之上增加连接代际、过期 token 拒绝、队列上限和关闭时批量终止规则。

### 2.5 P1：窗口查询与窗口截图仍是桩

`WindowDetector` 目前提供按点检测和候选过滤，`CaptureEngine::captureWindow`、`cropCenter` 仍返回 `kNotImplemented`，`action_handlers.cpp` 也只注册 Status / CaptureRegion / Copy / Save / Pin。`capture_window(query)` 需要单独的 `WindowResolver`，负责唯一匹配、进程过滤、DWM 边界和歧义错误，再复用现有物理像素捕获。

### 2.6 P1：Dispatcher 的完成后取消语义仍需明确

当前 Dispatcher 在 Handler 返回后才检查取消/超时，可能把已经完成的 Save、Copy 或 Pin 改报失败。F9 应区分“未开始可取消”“执行中不可回滚”“已完成”，并让 operation registry 记录最终事实，不能让客户端看到与实际副作用相反的状态。

### 2.7 P2：平台绘制边界可继续收窄，但不是 F9 前置阻塞

`AnnotationRenderer`、`ModernToolbar` 仍是明确的 Win32/GDI UI 基础设施；`AnnotationEditorHost` 虽已拆分组件，内部仍共享编辑状态。除非出现第二个真实消费者，不应为了形式上的分层建立新的窗口基础库或重写绘制后端。

## 3. 保持、不应过早拆分的边界

- `LongShotEngine → ProfileRegistry / Profile → CaptureEngine / ImageStitcher` 的方向已经清楚；不要把应用识别逻辑带回 Engine。
- `LongShotPluginHost`、Registry 和 `DllLongShotProfile` 的生命周期约束应继续通过 shutdown 和 ABI 测试保证，不要为 F9 重写插件 ABI。
- `WindowDetector` 当前只有 Overlay 一个真实消费者；`WindowResolver` 建成并出现第二个消费者后，再评估是否拆 `qingying_window`。
- 矩形工具、撤销/重做、暂停/继续/停止、Toolbar hover 等局部 UI 命令不应塞进 `ActionType`。
- GUI 的 `ResultStore` current 语义可以保留；外部作用域通过 ResultId/lease 适配，不要让 MCP 直接持有 `CaptureSession` 或裸 `Image*`。

## 4. 实现 F9 的建议顺序

1. 先实现 `AutomationEndpoint`、`OperationRegistry` 和 `UiActionScheduler`，打通 `status` 的本机管道闭环。
2. 在 `ResultStore` 上增加作用域、ResultId、租约和类型化输出；接入 `capture_region`、`copy`、`save`、`pin`。
3. 实现 `WindowResolver` 与 `capture_window` / `crop_center`，明确无 Overlay 的静默动作。
4. 为 `CaptureWorkflow` 增加 operation 生命周期，接入 `longshot_select`、查询、取消和释放；仅该交互工具显示原生 Overlay。
5. 最后补 Pipe 鉴权、连接代际、并发限制、协议兼容和异常恢复测试。

完整接口、用户是否看到遮罩、结果租约和 Named Pipe 方案见 [F9 MCP 架构与实施方案](F9-MCP-架构与实施方案.md)。

## 5. 当前验证基线

- 当前 Release 构建目录可发现 382 个 CTest 用例，实际执行 382 个，378 个通过，4 个为当前环境下的 `BitBlt` 失败；没有显式 Disabled 用例。
- 本次 `build.bat Release test` 在 MSBuild `FileTracker` 阶段遇到 `E_ACCESSDENIED`，未进入编译，因此不能把该次命令当作源码回归结论。
- `build/bin/Release/qingying.exe` 为 313,856 字节；`plugins/longshot` 已部署 Notepad、Explorer、Chromium 三个 DLL。
- 真实混合 DPI、窗口视觉交互、多 Pin、三类应用长截图和 F9 IPC 仍需人工或集成验收。

一句话结论：当前核心 GUI 与 F6 的模块边界已达到可以承载 F9 的程度；下一步应围绕“应用入口、异步 operation、结果租约、窗口解析”补齐外部契约，而不是继续搬动截图和 LongShot 内部实现。

# 轻映 QingYing — 系统架构与耦合度分析

> 分析日期：2026-09-03
> 分析范围：仓库文档、CMake、`src/` 与 `include/` 下各功能模块实现，以及当前桌面版长截图架构文档。
> 本文只记录仍需处理的边界问题；已完成的拆分只保留结论，不再重复实施过程。

## 1. 当前架构结论

当前的模块化方向可以保留：一个 Windows EXE、多个 static lib、`ActionDispatcher` 负责单步动作、`Application` 负责组合和顶层消息泵。CMake 依赖图没有明显的库级循环，但运行时协议存在反向回调、隐式共享状态和 HWND 消息所有权风险。

当前主链如下：

```text
Application
  ├── 顶层消息泵、Tray、Hotkey、依赖组装
  ├── CaptureWorkflow ── SelectionOverlay / AnnotationOverlay
  │                    ├── Capture / Export / Pin / Session
  │                    └── LongShotController ── LongShotEngine
  └── ActionDispatcher ── Capture / Export / Pin handlers
```

已完成且不需要重新设计的部分：

- `SelectionToolbar`、`OverlayPhase`、`OverlayRenderer` 已从选区主窗口中抽出；
- Overlay 和 AnnotationOverlay 使用顶层消息泵，已经没有嵌套消息循环；
- `LongShotController` 已接管 worker、暂停/停止、完成通知和 join；
- Overlay 已不再直接依赖 Capture / Annotate，编辑源图由 Workflow 产生；
- LongShotEngine、ImageStitcher 和插件 ABI 的职责方向基本清楚。

## 2. 仍需解耦的问题

### 2.1 P0：CaptureWorkflow、CaptureSession 和 PinManager 形成运行时闭环

`CaptureWorkflow` 的构造函数注入 Dispatcher、Capture、LongShotController、Export、Session、PinManager 和 SelectionOverlay，内部同时处理窗口生命周期、截图、标注、导出、错误提示和异步阶段：

- [include/qingying/app/capture_workflow.hpp](../include/qingying/app/capture_workflow.hpp)：39-43 行；
- [src/app/capture_workflow.cpp](../src/app/capture_workflow.cpp)：64-78、140-295、521-544 行。

同时存在反向运行时依赖：Workflow 持有 `PinManager`，而 `Application` 又把 `CaptureWorkflow::saveImage()` 注册成 PinManager 的保存回调：

```text
CaptureWorkflow ──持有──> PinManager
PinManager ──保存回调──> CaptureWorkflow::saveImage()
```

证据：

- [src/app/application.cpp](../src/app/application.cpp)：60-69 行；
- [src/pin/pin_manager.cpp](../src/pin/pin_manager.cpp)：151-157 行。

这使 Pin 模块间接知道 App Workflow 的保存对话框和错误策略。Save 也有三条不同路径：`SaveHandler`、Workflow 直接调用 `ExportService`、PinWindow 回调 Workflow。

建议拆出 `ResultStore` 和 `ResultActionService`：Workflow 只编排阶段，Copy / Save / Pin 统一消费明确的结果；PinManager 只管理钉图，不再回调 Workflow，也不负责保存对话框。

### 2.2 P0：CaptureSession 是隐式时序通道，并存在失败语义问题

`CaptureSession` 表达“最近一张图”，Capture Handler 写入，Copy / Save / Pin Handler 读取，调用方必须隐含知道先执行 CaptureRegion：

- [include/qingying/app/capture_session.hpp](../include/qingying/app/capture_session.hpp)：9-27 行；
- [src/app/action_handlers.cpp](../src/app/action_handlers.cpp)：57-143 行。

捕获开始时先调用 `ResultStore::clear()`，因此新捕获失败会清掉旧的有效结果；这是为了避免长期常驻时保留上一张大图：

- [src/app/action_handlers.cpp](../src/app/action_handlers.cpp)：42-49 行；
- [docs/architecture.md](architecture.md)：150-153 行已同步记录新的失败和释放契约。

GUI 可以保留“当前结果”语义，但 `ResultStore` 只保留一张当前图，并在工作流结束、取消或退出时释放。外部入口和异步操作仍应改用 `capture_id` / `operation_id`；失败后不恢复旧结果。

### 2.3 P0：AnnotationEditorHost 仍是共享上帝对象

标注代码虽然已经拆成多个 cpp，但 Chrome、InlineText、StrokePopup、ColorPicker 和 Paint 仍然通过同一个 `AnnotationEditorHost*` 访问全部可变状态。Host 同时持有 Session、Controller、Renderer、文字状态、工具栏状态、弹窗 HWND、GDI 对象和回写 Overlay 的观察指针：

- [src/annotate/annotation_editor_host.hpp](../src/annotate/annotation_editor_host.hpp)：106-217 行；
- 同文件：219-342 行声明了大量以 Host 指针为上下文的跨组件函数；
- [src/annotate/annotation_color_picker.cpp](../src/annotate/annotation_color_picker.cpp)：137-155、983-1141 行；
- [src/annotate/annotation_editor_paint.cpp](../src/annotate/annotation_editor_paint.cpp)：119-186 行。

当前文件拆分没有形成真正的依赖边界。应先保证 `AnnotationOverlay` 唯一持有 `unique_ptr<AnnotationEditorHost>`，再把 Host 内部状态收敛为 `Chrome`、`InlineText`、`StrokePopup`、`ColorPicker` 和只读 Paint View。各组件只通过窄接口修改 Controller / Session，不直接读取整个 Host。

### 2.4 P0：窗口与跨线程消息的所有权协议不完整

SelectionOverlay 的窗口状态通过裸指针交给 HWND，并在 `WM_NCDESTROY` 中删除；长截图预览、完成通知和 Controller 完成 payload 也通过裸 `new` 投递：

- [src/overlay/selection_overlay.cpp](../src/overlay/selection_overlay.cpp)：637-644、736-770 行；
- [src/app/longshot_controller.cpp](../src/app/longshot_controller.cpp)：64-78、97-107 行。

`PostMessage` 失败时已有局部回收，但消息成功入队后若窗口在消费前销毁，当前没有统一 drain 机制，payload 可能遗留。应统一 UI 消息所有权协议：使用 token 或明确的 owner-thread pending queue，并在窗口销毁和应用 shutdown 时回收所有未消费消息。worker 停止、窗口销毁和 DLL 卸载必须有固定顺序。

### 2.5 P1：SelectionResult 把 Overlay、标注和长截图语义混在一起

`SelectionResult` 除了选区几何，还携带 `annotated_image`；纯逻辑的 SelectionController、MaskRenderer 和 OverlayRenderer 又通过 `selection_overlay.hpp` 引入这个 UI 外观协议：

- [include/qingying/overlay/selection_overlay.hpp](../include/qingying/overlay/selection_overlay.hpp)：11-37 行；
- [include/qingying/overlay/selection_controller.hpp](../include/qingying/overlay/selection_controller.hpp)：3-4 行；
- [include/qingying/overlay/mask_renderer.hpp](../include/qingying/overlay/mask_renderer.hpp)：6-20 行；
- [include/qingying/overlay/overlay_renderer.hpp](../include/qingying/overlay/overlay_renderer.hpp)：8-24 行。

建议建立中立类型：`ScreenPhysicalRect`、`OverlayClientRect`、`ImagePixelRect`、`SelectionIntent`、`AnnotationFinishResult` 和 `LongShotControl`。`annotated_image` 应属于标注/Workflow 结果，不应成为基础选区协议的一部分。

`ActionType` 与 `SelectionAction` 对 Copy、Save、Pin、LongShot 存在重复语义：

- [include/qingying/action/types.hpp](../include/qingying/action/types.hpp)：8-18 行；
- [include/qingying/overlay/selection_overlay.hpp](../include/qingying/overlay/selection_overlay.hpp)：11-18 行。

两套枚举可以保留，但必须只有一个明确的 `UI Intent → Action` 转换点。

### 2.6 P1：坐标空间仍依赖注释，而不是类型

物理屏幕、Overlay 客户区、Image 像素和标注视图目前都使用裸 `int x/y/width/height`。`LongShotRequest` 和 `ActionRequest` 无法在编译期区分这些坐标：

- [include/qingying/longshot/longshot_profile.hpp](../include/qingying/longshot/longshot_profile.hpp)：7-17 行；
- [include/qingying/action/types.hpp](../include/qingying/action/types.hpp)：35-58 行；
- [include/qingying/overlay/coordinate_transform.hpp](../include/qingying/overlay/coordinate_transform.hpp)：6-18 行。

跨模块接口至少应携带坐标空间名称，优先用命名矩形类型，避免多屏负坐标、混合 DPI 和标注回流时误传。

### 2.7 P1：ActionRequest 过胖，F8/F9 会继续放大耦合

当前一个结构体同时承载区域截图、窗口查询、中央裁切、长截图和保存路径：

- [include/qingying/action/types.hpp](../include/qingying/action/types.hpp)：35-58 行。

在实现 F8/F9 之前改成命名 payload 或 `std::variant`，并增加 request id、operation id、取消、超时和结果选择语义。不要让 MCP 直接依赖全局 Session。

### 2.8 P2：平台绘制基础设施边界不一致

`AnnotationRenderer` 的公共注释声称无 Win32 依赖，但实现直接使用 GDI 和 `DrawTextW`：

- [include/qingying/annotate/annotation_renderer.hpp](../include/qingying/annotate/annotation_renderer.hpp)：8-16 行；
- [src/annotate/annotation_renderer.cpp](../src/annotate/annotation_renderer.cpp)：1-7、595-631 行。

`ModernToolbar` 也同时服务 SelectionToolbar、Annotation 和 Tray，并公开大量 HDC/HBITMAP 接口：

- [include/qingying/ui/modern_toolbar.hpp](../include/qingying/ui/modern_toolbar.hpp)：86-117 行；
- [src/app/tray_controller.cpp](../src/app/tray_controller.cpp)：1-7、165-168 行。

这不是当前首要的业务耦合，但后续应拆出平台绘制后端与 Toolbar Model，或明确这些类型就是 Windows UI 基础设施。

## 3. 需要保持、不应过早拆分的边界

- LongShotEngine → ProfileRegistry / Profile → CaptureEngine / ImageStitcher 的方向基本清楚，不要把应用识别逻辑带回 Engine。
- DLL Host、Registry 和 `DllLongShotProfile` 之间有明确的生命周期约束；当前依赖 `Application` 的成员声明顺序保证 Host 晚于 Engine 销毁，先补测试和 shutdown 检查，不要优先重写插件 ABI。
- `WindowDetector` 当前只有 Overlay 一个真实消费者，等 F8 窗口截图或第二个 LongShot profile 复用后再拆 `qingying_window`。
- 不要把矩形工具、Undo/Redo、Pause/Resume/Stop、Toolbar hover 等局部 UI 命令塞进 `ActionType`。

## 4. 解耦顺序

1. **先锁定失败和退出契约**：补充 Capture 失败后结果为空、结果释放、Overlay 销毁、worker shutdown 和未消费消息的测试。
2. **拆结果流**：引入 `ResultStore / ResultActionService`，统一 Copy / Save / Pin，移除 `PinManager → CaptureWorkflow` 回调闭环。
3. **收口所有权**：修复 AnnotationHost 的唯一所有权，统一 SelectionOverlay 和 LongShotController 的跨线程消息回收。
4. **抽中立协议**：分离 Selection、Annotation、LongShot 的结果/意图类型，并为跨模块矩形标注坐标空间。
5. **类型化 Action**：在 F8/F9 前改造 `ActionRequest`，增加异步 operation 上下文。
6. **收窄编译依赖**：Application 使用 PIMPL；测试不直接编译生产 cpp；Workflow 不再向外暴露 Overlay 具体类型。
7. **最后处理平台基础设施**：整理 AnnotationRenderer、ModernToolbar 和 CaptureExclusion；按真实复用情况决定是否拆 `qingying_window`。

一句话结论：当前最需要解的不是 LongShot 核心，而是 Workflow 过重、Session 隐式共享、Annotation Host 过胖以及 Win32 消息所有权不完整。

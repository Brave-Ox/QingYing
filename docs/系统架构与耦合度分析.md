# 轻映 QingYing：系统架构与耦合度审查

> 审查基线：当前 HEAD a21f2ac4，2026-09-14。审查对象是当前源码和 CMake 构建图，不把旧进度文档中的功能状态当作事实。
>
> 审查范围：模块职责与 CMake target、公共头、Application 组装、普通截图与标注、智能选区、长截图插件、结果生命周期、MCP/Named Pipe、线程和退出路径、测试分层、Windows 安全边界。
>
> 结论等级说明：CRITICAL 表示必须停止发布并立即修复；HIGH 表示发布前应关闭或明确接受风险；MEDIUM 表示应在近期迭代收口；LOW 表示维护性债务，不值得为此重写架构。

## 1. 总体结论

整体架构是合理的，适合当前产品形态：一个常驻托盘截图工具，使用 Win32 消息泵，普通截图以交互工作流为主，并可选地开放同机 Agent/MCP 接口。当前没有发现必须全面重写的 CMake target 循环，也没有发现必须引入微服务、跨进程 UI 或通用事件总线才能解决的问题。

现有设计中值得保留的部分包括：

- 单 EXE 作为托盘、热键、窗口消息和依赖组装根，符合绿色桌面工具的启动和部署模型。
- CaptureWorkflow 承担选区、标注、长截图和结果动作的多步编排，Application 主要承担组装和消息转发，职责比把所有流程塞进窗口过程更清楚。
- ActionRequest 使用类型化 payload；AutomationEndpoint 通过连接、作用域、opaque handle、operation 状态和幂等规则保护外部入口；ResultStore 通过租约和预算管理大块像素。
- Pipe/MCP 的 I/O、协议解析、UI 投递和业务执行有明确分层，Named Pipe 使用同一用户/会话身份校验、限流和有界帧，外部请求不会直接调用 GDI、DXGI 或窗口私有实现。
- LongShotEngine 的滚动、稳定性判断、拼接和应用 profile 分开，LongShotController 管理 worker 与 UI 完成消息；RAII、unique ownership 和 token channel 的方向正确。
- 智能选区已经有快速回退、UIA、MSAA、视觉检测、缓存、generation、候选选择和诊断等机制，说明产品问题被真实地转化为可测试状态，而不是简单堆叠设计模式。

当前最需要收口的三项是：

- HIGH：相邻插件目录中的所有 DLL 在主进程内加载，但生产模式没有可信来源策略。
- HIGH：智能选区的视觉/窗口快速路径和若干普通截图动作仍在 UI 线程执行，重活边界尚未按实际 UI affinity 划分。
- HIGH：Pipe、Export、LongShot、UIA 查询 worker 等退出路径最终都可能无上限等待。

因此，本项目的架构判断是：**继续演进，不推倒重来；先解决三个 HIGH，再处理 target 归属、智能选区边界、自动化分层和测试分层。**

## 2. 当前实际架构

### 2.1 运行时数据流和控制流

下图中的箭头表示调用或消息依赖方向：

    MCP stdio 进程（同一程序的 --mcp-stdio 模式）
      → StdioTransport
      → McpBridge / McpProtocolSession
      → PipeAutomationClient
      ⇄ Named Pipe
      → PipeServer（身份校验、握手、限流、I/O worker）
      → Application 的维护消息和 UiActionScheduler
      → AutomationEndpoint（连接、权限、operation、result scope、commit）
      → ActionDispatcher（单步 Action）
      → CaptureService / ResultActionService / ResultStore
      → CaptureWorkflow（需要 GUI 状态或多步交互的流程）

    托盘进程 qingying.exe
      → Application（组合根、DPI、托盘、热键、顶层消息泵）
      → CaptureWorkflow
         → SelectionOverlay
            → WindowDetector / KnownContent / Visual fallback
            → UiaRegionQueryWorker → UIA / MSAA
         → AnnotationOverlay
         → LongShotController → LongShotEngine
            → LongShotProfileRegistry → 内置 profile DLL
         → ResultStore → Copy / Save / Pin

普通截图的主路径是“背景快照 → 非模态 SelectionOverlay → SelectionIntent → CaptureWorkflow → ResultStore/ResultActionService”。长截图是“固定物理像素选区 → LongShotController worker → 预览/完成 token → UI 线程提交 ResultStore”。外部自动化则是“传输线程 → UI 消息投递 → Endpoint/Dispatcher → 异步完成再回传”，没有把像素或 HWND 直接穿过协议边界。

### 2.2 CMake target 依赖方向

当前 target 关系可以概括为：

    qingying_action
      ← qingying_window
      ← qingying_capture / qingying_export / qingying_pin
      ← qingying_longshot / qingying_command
      ← qingying_overlay
      ← qingying_annotate
      ← qingying_workflow

    qingying_automation_contract
      → qingying_action
    qingying_automation
      → qingying_automation_contract
      → qingying_workflow
    qingying_ipc
      → qingying_automation_contract
    qingying_mcp
      → qingying_automation_contract
      → qingying_ipc
    qingying_app_runtime
      → qingying_automation / qingying_ipc / qingying_mcp
    qingying.exe
      → 上述能力库和组合层

没有看到 target A → B → A 的直接循环。需要特别注意的是，qingying_automation 虽然名字像中立自动化层，但其 AutomationEndpoint 实现实际上依赖 qingying_workflow；这是分层偏移，不是链接循环，详见 A08。另一个问题是 qingying_overlay 直接编译 src/window 下的智能选区实现，详见 A05。

### 2.3 状态和所有权

当前主要状态边界如下：

- UI 线程拥有 CaptureWorkflow、ResultStore、PinManager、OperationRegistry、UiActionScheduler 和 AutomationEndpoint 的状态。
- ResultStore 按 GUI scope 和外部连接 scope 保存当前结果；外部结果有 TTL，句柄是 opaque 的，断开连接会清理 scope。
- ResultLease 通过共享控制块让像素可以短暂越过 Store 的清理点；预算 Reservation 与 RetainedImage 绑定，因此 lease 未释放时像素预算仍然有效。
- OperationControl 使用取消、deadline、tryCommit 和 settlement 约束不可回滚副作用；外部 Save/Copy/Pin 先做授权/准入，再提交真实副作用。
- UIA 查询 worker 采用 latest-wins、generation、缓存和适用性检查；Overlay 通过 8 ms 轮询获取结果，当前根窗口失效时清理悬挂候选。
- Overlay 的图像载荷在 WM_NCDESTROY 时主动释放，避免窗口生命周期记录长期保留完整桌面图。

这些设计已经解决了旧架构中“所有东西都是 current、所有回调都直接回 UI、所有结果都没有作用域”的主要问题。但连接状态、能力发现和执行事务仍有多处事实源，不能继续无边界扩展。

## 3. 问题清单

### A01：生产插件没有可信来源策略

**严重程度：HIGH**

**问题位置**：src/app/application.cpp:50-69；src/longshot/longshot_plugin_host.cpp:254-345；src/longshot/CMakeLists.txt:24-82。

**当前设计**：Application 从 EXE 相邻的 plugins\longshot 目录枚举全部 DLL，LongShotPluginHost 使用 LoadLibraryExW 加载，并校验入口符号、结构大小、ABI 版本、插件 ID 和回调是否齐全。当前部署脚本固定复制三个内置 profile DLL，但宿主本身仍接受目录中其他 ABI 合法 DLL。

**存在的问题**：ABI 合法只代表“能调用”，不代表“来源可信”。如果安装目录、便携目录或其父目录可被低权限进程/当前用户替换，恶意 DLL 会直接进入拥有截图、剪贴板、文件和窗口权限的主进程。LoadLibraryExW 的 DLL 搜索选项降低了依赖 DLL 搜索劫持风险，但没有替代插件文件本身的信任策略。

**为什么是架构问题**：这是一个 in-process 扩展边界，而不是普通配置文件目录。插件边界同时就是代码执行边界和故障传播边界；如果没有信任模型，扩展能力和主进程安全模型互相矛盾。

**可能造成的后果**：本机代码执行、截图或剪贴板泄露、任意文件操作、插件故障拖垮托盘进程，以及插件回调阻塞导致关机卡住。

**推荐修改方案**：生产模式采用显式 PluginLoadPolicy，只允许三个内置文件名和固定部署根；检查最终规范化路径、目录 ACL、reparse point 和签名/发布者。签名链尚未建立时使用构建生成的 SHA-256 allowlist，并记录版本和哈希。测试模式单独允许 test fixture，不能把测试目录规则带入生产。只有在未来明确支持第三方插件且无法建立强信任时，才考虑把插件移到独立 broker 进程；当前不需要先做多进程化。

### A02：智能选区和部分普通动作仍可能阻塞 UI 线程

**严重程度：HIGH**

**问题位置**：src/overlay/selection_overlay.cpp:567-624、745-785；src/window/smart_region_detector.cpp:1406-1621；src/window/visual_region_locator.cpp；src/window/known_content_locator.cpp；src/app/capture_service.cpp:102-190。

**当前设计**：智能选区把 UIA/MSAA 放到 UiaRegionQueryWorker，但 UI 线程的 updateHover 仍同步执行 WindowDetector、已知内容查找和冻结背景视觉扫描，并按约 16 ms 合并鼠标更新。普通 CaptureService 的窗口解析、区域捕获和 CropCenter 也由 UiActionScheduler 最终投递到 UI 线程；剪贴板和 Pin 的提交同样保留在 UI 路径。

**存在的问题**：WindowFromPoint、DWM 属性读取、EnumChildWindows、OpenProcess/QueryFullProcessImageName、GDI/DXGI 捕获和视觉扫描都可能受系统状态或目标进程影响。视觉模块对 Electron Workbench 有 16 ms 的专用预算，但标准视觉路径没有统一的全局硬预算。高分辨率、多显示器或目标窗口繁忙时，首帧和后续悬停更新可能超过消息泵可接受的时间；UIA 虽然异步，8 ms 的结果轮询仍会增加 UI 消息负载。

**为什么是架构问题**：当前线程边界按“请求从哪里进入”划分，而不是按“哪些操作具有 UI affinity”划分。只要捕获、窗口发现或视觉算法仍同步占用消息泵，取消、托盘、关闭和 control lane 都无法获得独立的响应保证。

**可能造成的后果**：遮罩掉帧或假死，托盘菜单和取消延迟，外部请求超时后真实副作用仍继续，多屏和 4K 场景响应时间不可预测。

**推荐修改方案**：先定义快速路径预算：UI 线程只保留坐标转换、已有快照/缓存读取、InteractionGate、预算预留、窗口/剪贴板/Pin 的最终提交和状态发布。窗口快照、像素捕获和标准视觉扫描放入有界 executor；队列满返回 Busy。每个异步任务携带 generation、deadline、cancel token 和输入快照，回 UI 后再次校验窗口身份和提交条件。保留 tryCommit 处理不可回滚边界，不要因为这一项引入通用 task graph。

### A03：关闭顺序基本正确，但等待没有统一上限

**严重程度：HIGH**

**问题位置**：src/app/application.cpp:133-185；src/app/automation_runtime.cpp:27-40；src/ipc/pipe_server.cpp:279-299；src/app/export_executor.cpp:28-45；src/app/longshot_controller.cpp:102-120；src/window/uia_region_query_worker.cpp:415-434。

**当前设计**：退出时先停止自动化准入，再停止/取消业务生产者，等待 Pipe、Export、LongShot 和 UIA worker，之后销毁托盘窗口和其他资源。Pipe I/O 通过 stop event、CancelIoEx 和 overlapped wait 尝试唤醒，LongShot/Export 使用线程 join，UIA worker 的 stop 也最终无条件 join。

**存在的问题**：插件 shutdown 回调、编码器、文件系统、无障碍 provider、驱动捕获或第三方窗口调用都可能不按预期返回。现有各个组件有局部 timeout 或取消检查，但 Application 没有统一的“停止请求、唤醒、最大等待、降级”契约；只要某一个 join 不返回，UI 线程就可能无限等待。WM_ENDSESSION 场景也不能依赖用户继续操作消息泵来完成善后。

**为什么是架构问题**：生命周期所有权不仅要回答“谁负责 join”，还要回答“producer 在多长时间内必须停止、停止失败时谁隔离风险”。当前所有权链是明确的，但停止 SLA 和退出降级策略没有成为跨模块契约。

**可能造成的后果**：退出、注销或关机卡住，Windows 最终强杀进程，临时文件和设置状态不确定；如果过早销毁 HWND，还可能留下迟到消息访问已失效对象。

**推荐修改方案**：为 PipeServer、PipeAutomationClient、ExportExecutor、LongShotController、UiaRegionQueryWorker 和插件宿主逐一定义 stop signal、可唤醒点、join owner、最大等待和完成状态。优先把所有阻塞等待改成 event/CancelIoEx/条件变量可唤醒，并对慢 provider、慢插件和慢写入做故障注入。普通退出可以等待一个明确上限；WM_ENDSESSION 只做安全最小收尾，不弹 UI。不能安全停止的 in-process 第三方代码应当成为独立进程的理由；不要常规使用 TerminateThread，也不要用 detach 掩盖未完成的业务线程。

### A04：Pipe 客户端使用 detached reader，线程所有权与其他模块不一致

**严重程度：MEDIUM**

**问题位置**：src/ipc/pipe_automation_client.cpp:101-145、174-187。

**当前设计**：连接成功后用 std::thread 启动 reader 并 detach。PipeAutomationClient::close 会设置 accepting=false、取消 PipeStream，并等待 reader_done；reader 线程捕获 shared state，因此当前实现不会简单地因为对象析构立即悬空。reader 自己触发 close 时还通过 on_reader 分支避免自 join。

**存在的问题**：该模块没有可 join 的线程句柄，线程完成依赖 shared state 的条件变量和约定好的 reader_done 时点；它与 LongShotController、ExportExecutor、PipeServer、UIA worker 的显式 owner/join 模式不一致。未来在 reader_done 设置前后增加回调、指标或资源操作，很容易误把“协议已关闭”当成“线程已完全退出”。同时，close 的自调用、EOF、同步回调和异常路径需要靠隐含约束维持。

**为什么是架构问题**：传输线程属于业务生命周期的一部分，不是可以独立放任的后台任务。不同模块使用不同的终止语义，会让上层无法统一定义 shutdown、超时和线程泄漏检查。

**可能造成的后果**：当前版本主要是可维护性和未来回归风险；后续改动可能引入回调重入、资源释放竞态、线程计数不稳定或无法诊断的退出延迟。

**推荐修改方案**：优先改为有明确 owner 的 joinable reader。若必须支持 reader 回调自身关闭，则把线程句柄交给独立的 join owner 或采用“线程运行体 shared state + 明确的 close 完成屏障”，并把 close 的完成定义为线程函数真正返回。补充 EOF、读失败、写超时、回调内 close、析构内 close 和取消竞态测试。不要因为避免 self-join 就把所有传输线程 detach。

### A05：源码目录、公共 API 与 CMake target 的所有权不一致

**严重程度：MEDIUM**

**问题位置**：src/overlay/CMakeLists.txt:2-18；src/window/CMakeLists.txt:1-11；include/qingying/window/smart_region_detector.hpp；src/window/smart_region_detector.cpp、uia_region_query_worker.cpp、uia_region_locator.cpp、msaa_region_locator.cpp、visual_region_locator.cpp、known_content_locator.cpp。

**当前设计**：qingying_window 只编译 window_catalog、window_detector、window_resolver。智能选区的七个实现文件实际由 qingying_overlay 直接加入并编译，公共头却位于 qingying/window，私有 locator 头也位于 src/window。

**存在的问题**：从命名和 include 看，消费者会认为智能选区属于 window；从构建图看，它却是 overlay 的实现细节。qingying_window 的链接者可以看到基础 Window API，却不能从该 target 获得 SmartRegionDetector 的实现；如果未来把同一 cpp 加回 window 或另一个 target，就会产生重复定义、选项漂移或不同实现被测试/生产分别使用。

**为什么是架构问题**：CMake target 是 C++ 模块边界的一部分。源码目录、公共头和 target 对同一归属给出不同答案，会直接破坏依赖方向、增量构建和独立测试的可靠性。

**可能造成的后果**：链接错误、重复编译、隐藏的跨目录依赖，或者将来为了复用智能选区而反向链接 overlay/UI，形成真正的循环。

**推荐修改方案**：当前智能选区已经达到七个实现文件、约 4000 行平台代码和独立测试的规模，建议建立 qingying_smart_region target：公开稳定的候选/选择契约，私有持有 UIA、MSAA、视觉、已知内容和 worker 实现；overlay 只依赖该 target。若近期不希望新增 target，最低限度也要把实现全部移到 overlay 私有目录，并禁止跨目录直接加入别人的 cpp。无论选择哪条路径，必须保证公共头由所属 target 提供实现。

### A06：SmartRegion 公共接口和实现承担了过多职责

**严重程度：MEDIUM**

**问题位置**：include/qingying/window/smart_region_detector.hpp:1-413；src/window/smart_region_detector.cpp:1-1624；src/window/uia_region_locator.cpp；src/window/msaa_region_locator.cpp；src/window/visual_region_locator.cpp；src/overlay/selection_overlay.cpp:44-89、567-707。

**当前设计**：SmartRegion 公共头同时暴露候选模型、UIA/MSAA 元数据、诊断事件、固定容量集合、视觉缓存、窗口快照、候选选择、悬停稳定、渲染门控、更新门控和检测策略。SmartRegionDetector::detectAt 通过多个可选裸指针把诊断、视觉上下文、集合、窗口快照和缓存一次性传入。OverlayWindowData 也同时持有这些算法状态、UI 状态、定时器状态和图像载荷。

**存在的问题**：这不是“类多”本身的问题，而是平台适配、候选评分策略、诊断协议、缓存、悬停交互和 Win32 窗口状态共享同一个变更边界。新增一个浏览器规则可能改动公共头、Overlay 和多个异步测试；调用方需要理解多个可选指针的组合合法性。SmartRegionVisualContext 还以不拥有的 Image 指针表达输入，当前调用是安全的，但生命周期约束主要靠注释。

**为什么是架构问题**：稳定的领域值、纯算法和易变的平台查询不应以同一公共接口耦合。否则产品规则、Windows provider 差异和 UI 交互状态会互相放大，测试只能用大而全的夹具验证。

**可能造成的后果**：编译依赖扩大、候选规则回归难以定位、UI 线程和 worker 的状态边界不清，未来很难在不影响 Overlay 的情况下替换 UIA/MSAA 或视觉实现。

**推荐修改方案**：分成三层即可，不要引入重型框架：一是无 Win32 行为的 SmartRegionCandidate/SelectionPolicy/纯选择器；二是私有 RegionSource 适配器，分别承载 Window、KnownContent、Visual、UIA、MSAA；三是 Overlay 侧的 HoverSession，拥有稳定候选、timer、generation 和渲染门控。诊断在边界转换为快照，不让诊断字段反向污染所有调用者。保留固定数组和最新请求合并，它们是热路径的合理优化。

### A07：action/types.hpp 正在成为跨域大契约

**严重程度：MEDIUM**

**问题位置**：include/qingying/action/types.hpp:1-418；include/qingying/automation/automation_contract.h；各 action、workflow、automation、ipc、mcp 公共头。

**当前设计**：一个公共 action 头承载 Image 相关结果、窗口候选、导出和 Pin 结果、状态信息、错误码、取消 token、ActionRequest、LegacyActionRequest、结果选择和 ActionResult variant。Automation contract 再在其上增加连接、作用域、句柄、operation、请求和响应。

**存在的问题**：稳定的核心值类型与产品用例 DTO、兼容入口和外部自动化语义同步演进。新增一个外部状态字段、结果 variant 或兼容字段，会扩大大量 static library 的重编译和理解范围；ActionResult 也容易被迫承载本来属于协议层的状态。

**为什么是架构问题**：不相关领域共享同一个变更和 include 边界，改变的是模块耦合图，而不仅是文件长度。公共头越宽，编译成功越不能证明模块职责仍然独立。

**可能造成的后果**：MCP 新能力触碰截图/渲染模块，Pin/Status 的 scope 语义泄漏到普通捕获，增量编译变慢，开发者为了复用类型而引入更多跨层 include。

**推荐修改方案**：随真实需求渐进拆分为 core（Image、几何、稳定错误码、取消）、action requests、action results 和 automation contract。先用 include-what-you-use 视角识别实际消费者，再迁移一个边界并保持 wire 编码不变。不要为了文件整洁同时重写 Dispatcher、Handler 和所有测试。

### A08：自动化 target 对应用工作流存在分层反向依赖

**严重程度：MEDIUM**

**问题位置**：src/automation/CMakeLists.txt；src/automation/automation_endpoint.cpp:1-321；include/qingying/automation/automation_endpoint.h；src/app/CMakeLists.txt。

**当前设计**：qingying_automation 内包含 OperationRegistry、UiActionScheduler 和 AutomationEndpoint；其中 AutomationEndpoint 使用 CaptureWorkflow、ResultStore、Dispatcher 和 InteractionGate，CMake 以 PRIVATE 方式链接 qingying_workflow。app_runtime 再依赖 qingying_automation、ipc 和 mcp。

**存在的问题**：automation_contract 是中立契约，但 automation target 不是中立运行时。自动化层直接依赖带 Overlay、Annotation、Capture、Export、LongShot 和 Pin 的应用工作流，导致一个协议控制层实际上站在应用编排层之上。当前没有循环，但层次方向已经偏离，自动化单元测试也必须组装大量 UI 工作流协作者。

**为什么是架构问题**：依赖方向决定可复用性和变化传播。外部传输变化应依赖稳定的自动化核心；连接控制如何调用本产品工作流则属于组合/适配层。把二者放在同一 target，未来增加另一个入口时容易出现反向依赖。

**可能造成的后果**：修改 Workflow 或 Overlay 会重编译 automation；自动化核心无法脱离桌面能力测试；若未来把新的 GUI/CLI 适配器放入 workflow，可能形成循环或重复控制逻辑。

**推荐修改方案**：保留现有 qingying_automation_contract；将 registry、scheduler、operation/session state 放入不依赖 workflow 的 automation core；把 AutomationEndpoint 的产品适配实现移到 qingying_app_runtime 或单独的 app automation adapter。只抽取少量真正稳定的能力端口，不要为每个服务机械创建接口，也不要为了理论上的跨产品复用做大型 DI 容器。

### A09：AutomationEndpoint 是第二个高密度组装点

**严重程度：MEDIUM**

**问题位置**：include/qingying/automation/automation_endpoint.h；src/automation/automation_endpoint.cpp:32-321；src/app/application.cpp:101-126。

**当前设计**：Endpoint 同时处理连接认证后的上下文、scope、权限、ready_actions、请求验证、Get/Cancel/Release、operation 分配、幂等重试、InteractionGate、Dispatcher 提交、ResultStore 结算、等待者回放和 shutdown；Scheduler 又通过 settlement hooks 回调 Endpoint。

**存在的问题**：它兼具 facade、controller、事务协调器和 handle repository。正确性分散在 Endpoint、Scheduler、Registry、Workflow 和 ResultStore 之间，声明/销毁顺序以及 before/after settlement hook 成为隐含不变量。

**为什么是架构问题**：连接级不变量没有集中在一个可独立验证的状态对象中。新增一个工具时，开发者必须同时修改路由、权限、scope、operation、结果和清理路径，容易出现“能执行但不能查询/取消/释放”的半成品。

**可能造成的后果**：外部操作状态不一致、断连后资源残留、回调重入时 settlement 顺序错误，测试 fixture 继续变大。

**推荐修改方案**：内部抽取无线程、无窗口的 AutomationSessionState，集中保存 connection、scope、opaque handle、幂等 key 和 operation 索引；Endpoint 保留 transport-independent facade 与明确的事务顺序。将真实业务调用和状态存储用最小接口隔离，先用单线程 fake 验证“准入 → 执行 → commit → 发布 → settlement → 清理”。

### A10：Action、Workflow、Policy 和 MCP tool catalog 存在多份能力事实源

**严重程度：MEDIUM**

**问题位置**：src/automation/automation_endpoint.cpp:20-29、91-98；src/app/application.cpp:112-120；src/app/action_handlers.cpp；src/mcp/tool_catalog.cpp:56-110。

**当前设计**：普通 Action 的 handler 注册在 ActionDispatcher；长截图和交互流程由 CaptureWorkflow 处理；Endpoint 维护 ready_actions 和 capability 字符串；MCP 再维护九个 tool 的名称、schema、decode/encode 和 Action 映射。

**存在的问题**：能力是否存在、是否允许外部访问、是否有 handler、是否能返回正确结果由多处手工同步。当前已经出现 ActionType 中有 LongShotRegion/SuggestName 占位但没有对应稳定外部 payload 的情况；这本身可以接受，但如果没有一致性检查，status、tools/list 和真实执行会逐渐漂移。

**为什么是架构问题**：能力发现是产品契约的一部分，不是几个字符串列表。多份事实源会使编译器无法发现集成遗漏。

**可能造成的后果**：外部客户端看到不可执行的工具，已注册动作不在 status 中，或一个工具能 decode 却在 Endpoint 中被 policy 拒绝；问题会延迟到真实 MCP 集成时才暴露。

**推荐修改方案**：让 Dispatcher 暴露只读 ActionDescriptor；Workflow 工具有并列 descriptor registry；MCP tool 只负责协议 schema 和 adapter。启动时检查“descriptor → policy → handler/entrypoint → result encoder”一致，不满足时 fail closed 并记录诊断。局部 Selection/Annotation UI 命令继续留在 Workflow，不要为了统一列表把所有 GUI 命令都变成 Action。

### A11：250 ms timer 与 PostMessage 共同推进自动化运行时

**严重程度：MEDIUM**

**问题位置**：src/app/application.cpp:39、155-159、241-244；src/app/automation_runtime.cpp:22-30；src/ipc/pipe_server.cpp:203-277。

**当前设计**：请求进入时由 Scheduler 投递 WM_QINGYING_AUTOMATION_REQUEST；完成时投递 WM_QINGYING_AUTOMATION_COMPLETE；Application 另设 250 ms maintenance timer，调用 PipeServer::drain 和 Endpoint::tick，负责握手、断连清理、TTL 和 registry sweep。

**存在的问题**：有工作时依赖消息，无工作时依赖固定轮询，形成两套推进模型。握手、断连和结果清理的响应上限至少带一个 timer 周期；应用忙时 timer 又和普通 UI 消息竞争。常驻托盘进程即使没有连接，也会产生固定唤醒。

**为什么是架构问题**：这是自动化 runtime 的调度策略，决定了连接生命周期、UI 负载和延迟，而不是单纯把 250 改成 100 的微优化。

**可能造成的后果**：首次连接和断连清理额外延迟，空闲功耗增加，UI 繁忙时会积压待清理 scope 或过期 operation。

**推荐修改方案**：PipeServer 从“无工作到有工作”时投递合并后的 wake message；UI 每次 drain 只处理投递前的有限快照，避免生产者持续供给造成无限循环。timer 降为低频 TTL/丢消息兜底，并在没有连接和任务时停止或放宽频率。保留现有 token channel，不引入全局事件总线。

### A12：故障隔离存在，但 UI 边界和诊断出口不完整

**严重程度：MEDIUM**

**问题位置**：src/ipc/pipe_server.cpp:152-160、178-213；src/automation/ui_action_scheduler.cpp:146-193；src/action/action_dispatcher.cpp:45-61、192-259；src/longshot/longshot_plugin_host.cpp:250-369；src/app/tray_controller.cpp:413-461。

**当前设计**：Pipe worker、ActionDispatcher 和部分回调边界使用 catch-all，异常通常转成失败、断开或单次完成；MCP session 也会在解析/协议异常时关闭。另一方面，TrayController 的 message_filter 直接调用 automation_runtime.tick、scheduler.dispatch 和 CaptureWorkflow，WndProc/消息过滤层没有统一的最外层异常保护；PipeServer::drain 对 UI hook 的调用也没有逐个 hook 的故障隔离。插件加载失败数目前被宿主静默忽略。

**存在的问题**：跨线程隔离与 UI 线程异常隔离没有同一层级的契约；Win32 错误、HRESULT、插件路径、request/operation correlation 和失败阶段没有统一落到可查询的诊断上下文。catch-all 避免了线程逃逸，却可能把真正原因压成 Unknown。

**为什么是架构问题**：可靠边界必须同时具备“不会越界”和“出了问题能定位”两个属性。没有消息泵最外层保护时，低概率 bad_alloc、hook 异常或未覆盖的 COM 异常可能直接从窗口过程逃逸。

**可能造成的后果**：一个 UI 消息使进程异常退出，或现场只看到 Unknown；损坏插件、UIA provider 不可用和 Pipe 断开难以区分，无法判断是能力降级还是实现错误。

**推荐修改方案**：在消息过滤/窗口过程适配层加最终 fail-closed 边界：记录诊断、返回安全错误、必要时停止自动化入口，而不让异常离开 WndProc。PipeServer::drain 对 connect/submit/revoke/disconnect 逐个隔离，并确保 pending 状态最终 settle。增加可关闭的结构化诊断 sink（ETW 或滚动日志），至少记录 subsystem、稳定错误码、Win32/HRESULT、request/operation、插件标识和 failure_stage；外部协议仍只返回裁剪后的稳定信息。

### A13：测试数量充足，但测试层次与真实桌面边界仍不完整

**严重程度：MEDIUM**

**问题位置**：tests/CMakeLists.txt；tests/smart_region_detector_test.cpp；tests/visual_region_locator_test.cpp；tests/selection_overlay_test.cpp；tests/mcp_process_integration_test.cpp；现有 build/CTestTestfile.cmake。

**当前设计**：测试源中约有 842 个 TEST/TEST_F 宏，覆盖 Action、Operation、Pipe、MCP、ResultStore、LongShot、Overlay、UIA worker、视觉选择和 Win32 fixture。MCP 还有 process fixture；智能选区有 latest-wins、generation、缓存、候选评分、浏览器样式和诊断测试。

**存在的问题**：当前主要是纯规则测试、合成窗口测试和进程级 MCP 测试，不能替代真实 Chrome/Edge/Brave、VS Code/Electron、Notepad、Explorer、混合 DPI、多显示器和真实 UIA/MSAA provider 验收。工作区现有 build 的 CTest 元数据已损坏：执行 ctest --test-dir build -N 时引用了缺失的 qingying_tests[1]_include-.cmake，因此不能把旧文档中的通过数量继续作为当前基线。

**为什么是架构问题**：可测试性取决于模块是否有稳定 seam。当前很多状态已可注入 clock、capture callback、UIA query function 和 process fixture，但生产 Overlay、真实 provider、关机和故障注入仍没有独立层；这会迫使开发者用单元测试假设代替系统事实。

**可能造成的后果**：本地单测全绿但真实浏览器候选、DPI 坐标、首帧时延或关机行为回归；环境失败和源码失败混在一起，无法给发布做清晰结论。

**推荐修改方案**：按四层报告测试结果：纯算法/状态单测；Win32 desktop integration（窗口、DPI、GDI、DWM、UIA/MSAA fixture）；真实应用 provider 验收矩阵；Pipe/MCP/process/shutdown e2e。为 executor、clock、slow capture、slow provider、plugin throw、pipe EOF 和 WM_ENDSESSION 增加可控故障注入。修复或重新生成 build CTest 元数据后再记录数字，不能继续引用 2026-09-07 的旧统计。

### A14：像素缓冲的在途峰值没有被完整建模

**严重程度：MEDIUM**

**问题位置**：include/qingying/action/image.hpp；src/app/result_store.cpp:43-110；src/longshot/longshot_engine.cpp；src/app/capture_workflow.cpp；src/annotate；src/export；src/pin。

**当前设计**：Image 以 vector<uint32_t> 拥有 BGRA 像素；ResultStore 对 capacity 进行预算，发布时 move 到 RetainedImage，ResultLease 共享其生命周期。长截图 worker 还会持有当前帧、累计拼接图和预览图；标注、ResultStore、Export、Pin 和 MCP 编码可能在相邻阶段同时持有图像或产生按值副本。

**存在的问题**：ResultStore 的 retained/reserved 预算是正确方向，但它只覆盖已经进入 Store 的结果；长截图中间帧、拼接扩容、Overlay 预览、标注合成和 WIC/剪贴板中间缓冲的峰值没有统一计费。ResultStore::get 等兼容接口还可能复制整张 Image。

**为什么是架构问题**：像素是系统最大的资源，其生命周期跨越 capture、workflow、annotation、export、pin 和 automation；只在一个 Store 内做预算，无法保证整个产品的峰值安全。

**可能造成的后果**：4K 截图或长截图瞬时内存激增，分配失败、页面抖动、首帧和导出延迟增加；常驻进程虽然空闲释放结果，但工作瞬间仍可能超出机器可接受范围。

**推荐修改方案**：先用 telemetry/benchmark 记录首帧、每个长截图阶段、标注合成、Copy/Save/Pin 的峰值和副本次数，结合产品目标决定是否改造。确认复制热点后，再引入不可变 PixelBuffer/lease，让 Store、Export、Pin 共享已提交像素，并把 in-flight frame 纳入统一预算。没有数据前不要预建复杂全局 buffer pool。

### A16：Annotation/Toolbar 内部仍共享较大的可变 UI 状态

**严重程度：LOW**

**问题位置**：src/annotate/annotation_editor_host.cpp、annotation_editor_*.cpp、annotation_overlay.cpp；src/ui/modern_toolbar.cpp。

**当前设计**：Annotation 已拆成 document、engine、session、interaction、paint、chrome、inline text、color picker 等文件，ModernToolbar 也抽出了共享模型；但子组件仍围绕 Host data、Win32 control HWND、编辑阶段和绘制状态协作。

## 4. 十三个维度的裁决

### 4.1 模块职责与边界

主干职责是清楚的：Application 组装，Workflow 编排，Dispatcher 处理单步动作，Capture/Export/Pin/LongShot 提供能力，Overlay/Annotation 提供 UI。A05 的 target 归属、A06 的智能选区高密度接口和 A09 的 Endpoint 需要收口，但没有必要重构为几十个更小的类。

### 4.2 模块依赖方向与循环依赖

从 CMake target 看没有直接循环依赖，且 public/private link 大体表达了传播意图。问题不是“有循环”，而是 qingying_automation → qingying_workflow 的分层反向依赖，以及 overlay 直接编译 window 源码造成的隐含依赖。优先修 A05、A08。

### 4.3 数据流、控制流和状态管理

ResultScope、opaque handle、operation、generation、deadline、tryCommit、ResultLease 和固定容量候选集合已经形成较成熟的状态管理。剩余风险在于 capability 多事实源、MCP/Endpoint/Dispatcher 三段映射，以及智能选区异步结果与窗口身份的持续复核。

### 4.4 接口设计与耦合程度

typed variant 比全字段万能 request 更安全，MCP 也没有把 JSON 依赖扩散进核心。公共 action 头和 SmartRegion 头已经接近可接受复杂度上限；A06、A07 应按真实变化渐进拆分，不应为抽象而抽象。

### 4.5 扩展性与过度设计

对当前产品而言，MCP session、Pipe 限流、结果租约、预算、幂等和长截图 profile 都是有需求依据的设计，不属于过度设计。真正需要防止的是继续泛化插件市场、通用 task graph、全局事件总线和全套 DI。A01 说明插件“可扩展”不能等同于“任意 DLL 可加载”。

### 4.6 对象生命周期和资源所有权

unique_ptr、RAII、token channel、ResultLease 和明确的 GUI/外部 scope 是优点。A03 的停止 SLA、A04 的 detached reader、插件 callback 的退出行为是主要缺口。生命周期修复的目标是更明确的 owner 和可验证的停止协议，不是到处增加 shared_ptr。

### 4.7 UI 线程、工作线程和并发模型

MCP/Pipe I/O、Save、LongShot、UIA/MSAA 已经有分工，latest-wins 和 generation 也处理了高频悬停。但 A02 表明 UI 线程仍承载窗口/视觉/捕获重活，A11 表明自动化还有消息与轮询双推进。应先收窄 UI 临界区，再考虑更复杂的线程池。

### 4.8 错误处理与故障隔离

稳定错误码、一次性 completion、跨线程 catch 和安全协议错误是正确基础。A12 说明最外层 WndProc/消息 hook 和结构化诊断还不足，尤其要避免异常直接离开窗口过程，也要保留 Win32/HRESULT 和 operation correlation。

### 4.9 可测试性

测试数量和纯逻辑覆盖较好，SmartRegion worker、候选评分、协议 session 和结果生命周期已经具备可注入 seam。A13 的缺口是环境分层、真实 provider、真实应用和 shutdown/fault injection；不能用单元测试数量代替产品验收。

### 4.10 性能、内存和启动开销

真正的风险是 A02 的 UI 热路径、A11 的固定 timer、A14 的像素峰值和启动时插件枚举/加载。static library 数量本身不是性能问题。应以首帧 P95、悬停检测 P95、空闲工作集、线程/GDI/HANDLE 增量和长截图峰值做测量。

### 4.11 可维护性

Application PIMPL、模块化 target 和 Workflow 收口已经降低维护成本；A05/A06/A07/A08/A09 仍增加认知负担，A15 的旧入口和文档会放大误解。先把边界和事实源理顺，比引入新的设计模式更有效。

### 4.12 安全性和健壮性

同用户/会话 Pipe 身份、PIPE_REJECT_REMOTE_CLIENTS、opaque handle、scope 隔离、路径/reparse 检查、资源上限和固定容量结构值得保留。A01 是最高优先级安全问题；A03、A12 影响故障健壮性。当前没有证据表明必须立即把全部业务改成多进程。

### 4.13 是否符合产品需求

符合。托盘截图工具需要低启动复杂度、即时 UI、Windows 原生窗口/剪贴板能力、少量应用适配和可选的本机 Agent；当前单进程 + 静态库 + 非模态 Workflow 正好覆盖这些需求。不能因为存在几个高密度类或 target 边界问题，就把产品改成微服务、跨平台 UI 或通用自动化平台。

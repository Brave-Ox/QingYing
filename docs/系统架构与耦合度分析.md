## 1. 系统架构

### 1.1 形态

**一个 EXE + 10 个 static lib**（方案 B，Windows 原生 C++17 + Win32，无 Qt/Electron）。

```text
qingying.exe
  └── src/app        组装层：单实例 / 托盘 / 热键 / Win32 消息循环
```

### 1.2 模块划分（CMake 目标）

| 目标 | 类型 | 职责 | 实际依赖 |
|---|---|---|---|
| `qingying_action` | static | Action 契约 + Dispatcher | （无，纯头文件契约） |
| `qingying_capture` | static | GDI 区域截图（DXGI 预留） | action + d3d11/dxgi |
| `qingying_export` | static | 剪贴板 CF_DIB / WIC PNG | action + windowscodecs/ole32 |
| `qingying_overlay` | static | 遮罩、框选、八点调整、移动、窗口吸附 | action + capture + dwmapi |
| `qingying_annotate` | static | 标注（当前仅 stub） | action |
| `qingying_pin` | static | 钉图窗口与多钉管理 | action + user32/gdi32/dwmapi |
| `qingying_longshot` | static | 长截图（当前仅 stub） | action + capture |
| `qingying_command` | static | 本地口令 → ActionRequest（stub） | action |
| `qingying_mcp` | static | MCP Bridge（stub） | action |
| `qingying` | **EXE** | 组装 Handler、托盘热键、消息循环 | 上述全部 |

### 1.3 依赖关系

```text
                       ┌─────────────────────────┐
                       │      qingying_action    │  （稳定契约：ActionType/
                       │  ActionRequest/Result/  │   Image/Dispatcher/Handler）
                       │  Image + Dispatcher     │
                       └───────────┬─────────────┘
         ┌──────────┬──────────┬───┴────┬──────────┬──────────┬──────────┐
         ▼          ▼          ▼        ▼          ▼          ▼          ▼
      capture    export    overlay   annotate    pin     longshot  command   mcp
         ▲                     │                            ▲
         └──── overlay→capture ┘          longshot→capture ──┘
                            └───────────────┬───────────────┘
                                            ▼
                                     qingying (EXE)  只经 ActionDispatcher 调用能力
```

**关键点：** 所有引擎模块都只依赖 `action`（契约），只有 `overlay` / `longshot` 额外依赖 `capture` 的公共头。`mcp` / `command` 严格遵守「只 → action，不 → capture/DXGI」。

### 1.4 主路径数据流

```text
热键 Ctrl+Shift+Q
  → HotkeyManager → Application::beginCaptureFlow
  → SelectionOverlay::show（全屏遮罩；自由框选 / 窗口吸附）
  → SelectionResult（物理像素）
  → dispatch(CaptureRegion) → CaptureEngine → Image → CaptureSession
  → dispatch(Copy / Save / Pin) → ExportService / PinManager
```

## 2. 总体设计模式

核心是 **「单一命令分发中心 + 多个独立能力模块」的分层架构**，落到具体模式上：

1. **命令模式（Command）** —— 这是全系统骨架。`ActionRequest` 是命令对象，`IActionHandler` 是命令处理器，`ActionDispatcher` 是调用者。GUI / 口令 / MCP 三条入口统一走 `dispatch`，与具体能力解耦。

2. **分层架构（Layered）** ——
   - 表现/组装层：`app`
   - 契约/分发层：`action`
   - 能力层：`capture / overlay / export / pin / ...`
   上层只认识 `action`，不认识能力层实现细节。

3. **PIMPL（编译防火墙）** —— `CaptureEngine` 用 PIMPL 隐藏 DXGI/COM，头文件不污染调用方。

4. **依赖注入 + Composition Root** —— `Application::registerHandlers` 作为唯一组装点，把 `CaptureEngine` / `ExportService` / `CaptureSession` / `PinManager` 通过构造函数注入各 Handler。

5. **状态机（State Machine）** —— `SelectionController` 显式状态机（创建 / 八点调整 / 整体移动），纯逻辑可单测。

6. **回调解耦反向依赖** —— `SelectionOverlay` 的 `SelectionCallback`、`PinManager::setActionCallbacks`、`PinWindow::ClosedCallback`，用回调把「UI 壳 → 业务」的反向依赖从编译期耦合变成运行期注入。

7. **RAII** —— GDI 句柄（HDC/HBITMAP）用 `unique_ptr` + 自定义 deleter；`PinManager::CaptureGuard` 用 RAII 保证「截图前隐藏 Pin → 截图后恢复」。

8. **值对象传递** —— `Image`（width/height/pixels）是纯值类型，capture → export/pin 全程值传递，不共享句柄或指针。

## 3. 耦合度偏高、建议改进的方面

### 3.1 `ActionRequest` 是「上帝结构体」

所有 Action 的字段堆在一个 `ActionRequest` 里：`x/y/width/height`（CaptureRegion）、`window_query`（CaptureWindow）、`crop_w/crop_h`（CropCenter）、`save_path`（Save）。每加一个 Action 就往里塞字段，字段语义靠 `type` 隐式分派。

- **影响**：所有 Handler 依赖同一个胖结构体，字段归属不清晰，新增能力时契约文件持续膨胀。
- **建议**：改用 `std::variant` 按 Action 拆分 payload，或至少用「基类 + 子类」让每个 Action 自带类型安全的参数。

### 3.2 `CaptureSession` 是隐式共享状态通道

`Copy` / `Save` / `Pin` Handler 都不从 `ActionRequest` 拿图片，而是从 `CaptureSession` 这个「共享当前截图」里取。数据流是隐式的：`CaptureRegion` 写入 → 其它 Handler 读取。

- **影响**：Handler 之间通过共享可变状态耦合，时序依赖隐晦（必须先 CaptureRegion 再 Copy），且天然非线程安全。
- **建议**：把 `Image` 显式放入 `ActionResult`（或引入专门的「带载荷请求」），减少侧信道；`CaptureSession` 只保留给「最近一张图」的 UI 语义。

### 3.3 `selection_overlay.cpp` 是「上帝文件」

单文件 600+ 行，同时承担：遮罩渲染、窗口创建、操作条工具栏、方向光标、窗口吸附悬停高亮、鼠标交互状态机、DPI 缩放。纯逻辑已抽出（`SelectionController` / `WindowDetector` / `mask_renderer` / `selection_handles`），但 Win32 壳本身职责仍高度集中。

- **建议**：拆出 `OverlayToolbar`、`HoverHighlight`（或 `overlay_render`）等薄封装，让 `selection_overlay.cpp` 只做消息路由。

### 3.4 坐标 / DPI 约定靠命名与文档传递

「进入 Capture 的矩形必须是物理像素」「Overlay 负责逻辑↔物理换算」这些约定目前是口头/文档约定，散落在 `main.cpp`（DPI 感知）、`coordinate_transform`（虚拟桌面/客户区转换）、`window_detector`（投影修正）里。

- **影响**：新增模块（尤其 `longshot` 滚屏拼接、`F8/F9` 按名截窗）时容易踩「逻辑 vs 物理」的坑。
- **建议**：引入强类型坐标（如 `PhysicalPx` / `ScreenPx` / `ClientPx`）或一个集中的坐标门面，把换算收口。

### 3.5 `window_detector` 挂在 `overlay` lib 下

`window_detector.{hpp,cpp}` 物理上被编进 `qingying_overlay`。但「窗口发现 / 过滤 / 投影修正」是独立职责，未来 `F8/F9` 按名截窗、`F6` 长截图定位前台窗口都可能复用。

- **建议**：拆成独立的 `qingying_window` static lib，让 `overlay` 依赖它，而非把它塞进 overlay。

### 3.6 `CaptureEngine` 仍用裸 `new/delete`（资源管理瑕疵）

`impl_` 是裸指针 + 手写 `new/delete`，违反项目「禁止裸 new/delete」的红线（PROGRESS 已列为待办）。严格说是资源管理问题，但它让 PIMPL 的 RAII 不彻底。

- **建议**：改为 `std::unique_ptr<Impl>`，与 `PinManager` / `ActionDispatcher` 里的 `unique_ptr` 用法保持一致。

## 4. 耦合度低、无需改进的方面

### 4.1 `action` 契约层零 Win32/DXGI 依赖

`types.hpp` / `image.hpp` / `action_dispatcher.hpp` / `i_action_handler.hpp` 全是纯 C++ 头文件，不含 `<Windows.h>`。这是全系统解耦的根基：`mcp` / `command` 可以只依赖 action，完全不碰 Win32。

### 4.2 `CaptureEngine` PIMPL 干净

`capture_engine.hpp` 只暴露 3 个方法 + 一个 `Impl*`，GDI/DXGI 全在 `.cpp`。其它模块 include 它不会引入 DXGI 污染。（唯一瑕疵是 3.6 的裸指针，属资源管理而非耦合。）

### 4.3 `SelectionController` 纯逻辑状态机

与 Win32/GDI 完全解耦，创建 / 八点调整 / 移动 / 钳制 / 命中测试全部可单测（16 个用例）。UI 壳只喂鼠标事件。

### 4.4 `WindowDetector` 类本身内聚

窗口发现、`GA_ROOT` 提升、自身/最小化/工具/DWM 隐藏/桌面外壳/屏外窗口过滤、投影修正全部内聚在一个类里，没散落到 `selection_overlay` 或 `selection_controller`。

### 4.5 纯函数模块可单测

`mask_renderer` / `selection_handles` / `coordinate_transform` 的几何与坐标计算是纯函数（Win32 封装如 `getVirtualScreen` 单独放 `.cpp`），测试覆盖充分。

### 4.6 `ExportService` 干净独立

`copyToClipboard` / `savePng` 只依赖 `Image` + `ActionResult`，不反向依赖任何上层模块，可被 Pin、MCP 复用。

### 4.7 依赖方向遵守架构约束

`mcp` / `command` 只 → `action`（不碰 capture/DXGI）；引擎模块不反向依赖 `app`；跨模块不 include 对方私有头。文档声明的边界与实际 CMake 依赖一致。

### 4.8 `Image` 值对象传递，无句柄共享

`Image` 是简单的值类型（宽高 + `vector<uint32_t>`），capture → export/pin 全程值传递或 `std::move`，没有共享句柄/裸指针，天然避免了跨模块生命周期纠纷。

### 4.9 `SelectionOverlay` 对外接口极简

对外只有 `show(callback)` / `hide()`，复杂的 `OverlayWindowData` 状态、工具栏、光标、吸附逻辑全藏在 `.cpp` 匿名命名空间，调用方（app）看不到任何细节。

### 4.10 RAII 与回调解耦到位

GDI 句柄、`CaptureGuard` 用 RAII；Pin 通过 `setActionCallbacks` 从 `Application` 注入 `ExportService` 的 copy/save，而不是直接 include `export_service.hpp`，保持了 pin → export 的松耦合。

## 5. 一句话结论

**架构骨架是健康的**：命令分发（ActionDispatcher）+ 契约层（action）+ PIMPL + 纯逻辑状态机 + 值对象传递，这条主线把模块间耦合压得很低，为后续 `F3 标注` / `F6 长截图` / `F8 口令` / `F9 MCP` 留好了扩展位。**主要风险集中在「契约层和组装层的细节」**：`ActionRequest` 胖结构体、`CaptureSession` 隐式共享状态、`selection_overlay.cpp` 上帝文件，以及坐标/DPI 约定缺乏强类型约束——这些是后续加功能前最值得优先收敛的点。

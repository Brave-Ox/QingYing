01

这个项目到底是什么

轻映 QingYing 是一个 Windows 原生轻量截图工具， 用 C++17 + 纯 Win32 写，不用 Qt / Electron。

它有两副面孔：

  1. 给人用：全局热键 → 全屏遮罩 → 框选 / 窗口吸附 → 标注 → 复制 / 保存 / 钉图 → 长截图
  2. 给 Agent 用：通过本地口令（F8，未做）和 MCP（F9，已接线），把同一套截图能力暴露出去

核心指标

指标目标
绿色交付包体积≤ 20 MB
常驻内存≤ 40 MB
热键到遮罩首帧≤ 300 ms
主路径耗时约 15 秒

理解这个项目时最重要的定位：轻映不是要做一个“什么都能自动化”的桌面平台，而是先把截图这件事做成一套边界清晰的本地能力。GUI、长截图和 MCP 只是不同入口，真正的截图、结果管理和导出能力应该复用同一套实现。这样做的价值是：功能可以扩展，但 GDI、窗口句柄、UI 线程状态这些平台细节不会被外部入口随意穿透。

02

物理形态：构建出来是什么东西

这是理解整个架构的第一个关键点。CMake 构建产物不是一个 EXE 而已：

qingying.exe                          ← 唯一的 EXE（WIN32 子系统，无控制台）
  + 17 个 static lib                  ← 编译期融进 EXE，不是独立文件
  + 1 个 INTERFACE target             ← qingying_automation_contract，纯头文件契约
  + 3 个 longshot 插件 DLL            ← 部署到 plugins/longshot/
        qingying_notepad_longshot_plugin.dll
        qingying_explorer_longshot_plugin.dll
        qingying_browser_longshot_plugin.dll

为什么是「一个 EXE + 一堆静态库」这种形态？

不是为了发多个文件，而是为了用编译期边界强制约束模块之间的依赖方向。 静态库在运行时不存在，但在编译期，A 库想用 B 库的符号就必须在 CMake 里显式声明 target_link_libraries——这就把「谁能调谁」写进了构建系统，改错了直接编译失败。

为什么 Application 要做“组合根”，而不是“大总管”

Application::Impl 的核心职责是创建对象、连接依赖、安装消息路由并控制销毁顺序；真正的多步骤业务交给 CaptureWorkflow，单步动作交给 ActionDispatcher 和各能力服务。这样理解后，看到 application.cpp 里对象很多并不代表“业务都堆在这里”，它更像整个程序的接线板。

这也是 PIMPL 在这里的实际意义：把大量 Windows 类型和实现细节压在 .cpp 中，公共头保持稳定，同时把对象的创建与析构顺序集中管理，特别适合这个拥有 UI、worker、插件和 IPC 的原生应用。

一句话记忆：Application 负责组装 → CaptureWorkflow 负责编排 → ActionDispatcher 负责单步命令 → 各能力模块干活。

05

依赖方向：项目的「宪法」

这是整个架构最值得理解的部分。docs/architecture.md §4 明确写死了依赖箭头： 

action      ← capture / export / pin / annotate / command / mcp
action + ui ← overlay
authority_contract ← automation / ipc / mcp / app_runtime
action + capture   ← longshot
action + overlay + capture + annotate + export + pin + longshot ← workflow
app → workflow + 上述服务 + app_runtime          （组合根）
longshot runtime ← 受控 profile 插件 DLL

四条硬性红线

违反任何一条，就是架构 bug：

  1. command / mcp 只能依赖稳定契约， 绝不能 include DXGI、GDI 或 *Impl 私有头。
  2. 引擎模块不得反向依赖 app。
  3. 跨模块不得 include 对方 .cpp 旁的私有头。
  4. UI 背景快照、文件对话框、长截图预览这类表现层行为可以留在 workflow， 但必须明确标注「这是例外」，不能假装「一切都走了 Dispatcher」。

三条核心链路

6.1　普通截图主链路（最常用）

1
Ctrl+Shift+Q

HotkeyManager 收到 WM_HOTKEY，Application::onCaptureHotkey() 只是 PostMessage(WM_QINGYING_BEGIN_CAPTURE) 就返回。

关键：热键回调必须快，不能阻塞在这。

2
消息路由 → capture_workflow_.beginSelection()
  • InteractionGate 抢占「交互占用」（防重入）
  • ResultStore.clearScope() — 释放上一张大图，避免常驻大内存
  • 记录原前台顶层窗口（GetForegroundWindow → GetAncestor(GA_ROOT)）
  • PinManager.temporarilyHideForCapture() — RAII，隐藏自己的钉图
  • CaptureEngine 抓整个虚拟桌面 → selection_background
3
SelectionOverlay.show(background, callbacks...) — 非模态！创建后立即返回
  • 用户自由框选 / 悬停窗口高亮吸附 / 八点调整
  • 底部 SelectionToolbar：复制 / 保存 / 长截图 / 编辑 / 钉图
4
用户点某个按钮 → overlay 回调写 pending_selection

关闭时 postContinuation() → PostMessage(WM_QINGYING_WORKFLOW_CONTINUE)

5
消息路由 → capture_workflow_.continueWorkflow()

decideCaptureWorkflowRoute() — 纯函数决策，可单测！ 然后按分支走：

  • 复制 / 保存 / 钉图 → CaptureService.capture() → dispatch(CaptureRegion) → ResultStore.publish() → ResultActionService.copy/save/pin
  • 编辑 → beginAnnotation() → 抓选区源图 → AnnotationOverlay.showInPlace()（同样非模态）→ 确认后 publish + 自动 Copy → composeCapturePreview() 把结果贴回桌面快照 → 恢复同一选区的结果操作条（选区锁定只读，防止物理矩形与标注栅格失配）
  • 长截图 → LongShotController.start() → 见下一节

这里有几个非常值得学的设计点

非模态 Overlay + 顶层消息泵续接

以前 Overlay 自己跑消息循环（模态），会导致一堆嵌套问题。现在改成 show() 创建窗口后立即返回，所有交互由 Application::run() 里唯一的 GetMessageW 循环驱动， 完成 / 取消通过 WM_QINGYING_WORKFLOW_CONTINUE 回到 CaptureWorkflow 续接。

文档原话：「Win32 消息循环只在 app」。

decideCaptureWorkflowRoute() 是纯函数

include/qingying/app/capture_workflow.hpp
CaptureWorkflowRoute decideCaptureWorkflowRoute(
    const SelectionIntent& selection,
    bool longshot_result_ready,
    bool annotated_result_ready = false) noexcept;

分支优先级：Edit > AnnotatedResult > StartLongShot > ExistingLongShotResult > CaptureRegion。

拆出来就能不建窗口直接跑单测。

WS_EX_NOACTIVATE

遮罩窗口刻意不激活，否则原前台窗口的 owned popup（下拉菜单、tooltip）会立刻消失。

这是踩过坑的修复（commit 615c2f2a）。

再补一个容易忽略、但直接决定“截得准不准”的基础：程序在创建窗口前就启用 Per-Monitor V2 DPI 感知，并把遮罩、鼠标位置、窗口矩形和截图区域统一看成物理像素坐标。因此在 125% / 150% 缩放、多显示器甚至负坐标副屏场景下，UI 看到的选框和 GDI 真正截取的区域仍属于同一坐标系，不需要在业务层反复猜缩放比例。

6.2　长截图链路（最复杂）

1
用户框选 → 点「长截图」

Overlay 保留在屏幕上，选区孔洞切换为「捕获透传」。

2
LongShotController.start(request) — 启动独立 worker 线程
  • LongShotProfileRegistry 挑 profile — 从 plugins/longshot/*.dll 通过受控 C ABI 加载
  • profile.resolve(request, out) — 定位滚动控件与内容边界。返回 true 同时意味着「这个 profile 接受该选区」，兼作能力探测，所以没有单独的 probe()
  • profile.scrollDown() — 向目标发一次向下滚动输入
  • profile.queryScrollState() — 读滚动位置；返回 false 表示自绘控件读不到， 引擎退回图像重叠兜底
  • profile.cancel() — 可选协作式取消（默认空实现，保旧插件 ABI）

接口只有这五个虚函数：name / resolve / scrollDown / queryScrollState / cancel。没有 probe() 或 open()——「支不支持」和「建会话」都由 resolve() 一并回答。

3
循环
  • CaptureEngine.captureRegion(同一矩形)
  • ImageStitcher 重叠匹配去重拼接
  • 向 Overlay postLongShotPreview()（实时预览）
  • profile.scroll_down() 驱动滚轮
  • profile.query_scroll_state() 判断是否到底
4
停止条件（任一命中）
  • 已到垂直滚动条底部
  • 新帧与累计图完全重合 / 无新增内容
  • max_frames = 30
  • max_output_height = 30000
  • 用户暂停 / 停止、应用退出
  • 目标窗口 / 选区 / 捕获失败
5
worker 完成 → 把 token PostMessage 到托盘窗口

WM_QINGYING_LONGSHOT_COMPLETE → capture_workflow_.handleLongShotCompletion(token) → 结果写 ResultStore + 自动 Copy。

两个值得单独说的设计

跨线程预览的所有权模型

worker 复制预览图后写进 UiMessageChannel， Windows 消息只携带一个 token（不携带指针）， UI 线程凭 token 取出并接管所有权。

这样避免了跨线程裸指针的经典坑。

3 个插件 DLL 的加载是受控的

longshot_plugin_api.h 是唯一的 ABI 契约， 里面只有 C 兼容类型——没有 STL、没有 C++ 类、没有异常、没有所有权转移 API。

连 HWND 都用 uint64_t 表示，就是为了让 Windows.h 不跨越 ABI 边界。

还带了 static_assert 锁死结构体大小。

插件“能加载”不等于“可以随便操作桌面”。长截图开始前会保存原始 owner window，插件只能解析这个 owner 及其子孙窗口；host 在真正发送滚动输入前还会重新校验父子关系。这个边界把“应用适配能力”限制在用户刚刚选中的那块上下文里，避免插件因为拿到 DLL 身份就向任意窗口广播输入。

6.3　F9 MCP / Agent 外部接入链路

这是最「分布式」的一条链路——同一个 EXE 的两种运行模式：

▸
MCP 客户端（如 Cursor / Codex）

标准 MCP / stdio（逐行 UTF-8 JSON-RPC）

▸
qingying.exe --mcp-stdio — 客户端拉起的轻量协议进程

不建托盘、不建热键、不建单例 Mutex、不建插件宿主。

▸
私有、版本化 IPC / Named Pipe

连到已在运行的托盘主进程。

▸
PipeServer（worker 线程做 I/O）
  • 端点：\\.\pipe\QingYing.Automation.v1.<logon-sid>
  • PIPE_REJECT_REMOTE_CLIENTS + 显式登录 SID DACL
  • 双向 token 校验（真实进程 / 会话 / 用户 SID）
  • 最多 4 个槽位，握手 3 秒期限
▸
UI 线程 drain() → UiActionScheduler（有界队列）
▸
AutomationEndpoint（可信组合边界）
  • connectAuthenticated() 分配 ResultScopeId — 绝不从客户端 JSON 构造 scope
  • OperationRegistry 管操作状态、随机句柄、幂等
  • InteractionGate 仲裁「用户正在交互」vs「Agent 要截图」
▸
分流
  • 单步动作 → ActionDispatcher → Handler → 能力模块
  • 交互长截图 → CaptureWorkflow → LongShotController

把 crop_center 看成一条完整链路，会更容易理解 F9

外部 JSON 并不会“解析完就直接调用截图函数”。它先经过 MCP 会话校验和 tool schema，转换成内部类型化请求；随后通过有界 Named Pipe 写队列进入托盘主进程，Pipe worker 只负责传输和身份校验，再把 payload 放入 UiMessageChannel，Windows 消息本身只携带 token。UI 线程拿到 token 后，由 AutomationEndpoint 建立可信 scope、登记 operation，再进入 ActionDispatcher / CaptureService。完成结果沿同一路径返回。

这条链路看起来比“直接调 GDI”长，但它换来了三个关键边界：协议和业务解耦、I/O 线程不碰 UI 状态、外部连接不能伪造内部结果作用域。而且返回的是尺寸、状态和不透明句柄，不是把整张 BGRA 像素塞进 JSON。

07

几个必须理解的横切抽象

7.1　Image — 极薄的像素契约

struct Image {
  int width, height;
  std::vector<std::uint32_t> pixels;  // 每像素 uint32（BGRA 通道序）
};

全项目统一为 BGRA32 / 行优先 / 物理像素。注释里写得很清楚： 「刻意保持极薄：不携带算法 / 句柄；P0 以值传递（单区域，≤ 4K 屏）」。

所有坐标都是物理屏幕像素——这是 main.cpp 里必须在建窗口前声明 PMv2 DPI 感知的原因：不声明的话鼠标坐标是虚拟化逻辑像素，而 BitBlt 按物理像素取样，选区会和实际截到的区域整体偏移。

7.2　Action 契约 — 单步业务命令的统一入口

struct ActionRequest {
  RequestId request_id;            // 请求 ID
  OperationId operation_id;        // 操作 ID
  CancellationToken cancellation;  // 取消令牌
  std::chrono::milliseconds timeout;
  std::chrono::steady_clock::time_point submitted_at;
  ActionPayload payload;           // std::variant 类型化 payload
  ActionContext context;           // 结果作用域（由可信入口设置）
  std::shared_ptr<IOperationControl> operation_control;  // 提交仲裁
};

关键点：

  • payload 是 std::variant 而不是「全字段万能 request」—— 类型安全，改错了编译不过
  • ActionContext.result_scope 注释明确写： 「它不是客户端可控的动作参数」
  • cancel / timeout / tryCommit() 构成了完整的异步操作生命周期
  • ActionDispatcher::submit() 保证 at-most-once completion： 无论校验失败、取消、无 Handler 还是抛异常，完成回调恰好投递一次

7.3　ResultStore — 结果生命周期的核心

这是 F9 之后重构最重的地方。核心模型：

每个「可信作用域」(ResultScopeId) 一个槽位
  · kGuiResultScopeId = 1   ← GUI 自己
  · >= 2                    ← 每个 MCP 连接一个，由 Endpoint 分配

GUI 清理不影响外部结果（scope 隔离）
外部结果有固定 TTL + 字节预算
ResultLease 是 shared_ptr<const Image>，可以比 Store 活得更久，能被 worker 线程消费

几个关键行为（都写在 result_store.h 注释里）：

  • 新截图开始时先 clearScope()，失败后不恢复旧结果—— 避免常驻进程长期持有大块像素
  • get() 会深拷贝整张图，acquire() 才是零拷贝租约—— 性能敏感路径要用后者
  • tombstones_ 记录已失效的 ID， 让重复 release_result 能幂等返回

7.4　ResultActionService — Copy / Save / Pin 的唯一出口

无论 GUI、Dispatcher 还是 PinWindow 右键菜单，都走这一个服务。 这解决了「Pin 的复制保存错误地读到了最新 ResultStore」这类串图 bug。

它还把保存拆成两半：prepareSave()（准备 + 路径授权 + lease）和 executeSave()（实际 I/O），中间夹着 CommitAuthorization —— 这是为了支持 取消竞争：编码完成后才去抢 tryCommit()，抢不到就不写文件。

7.5　InteractionGate — 防止「人和 Agent 抢屏幕」

一个全局互斥门。GUI 截图、MCP 截图、模态保存对话框都要先 gate.acquire(InteractionKind::...)。 这就是为什么 MCP 的 capture_window 不会在你正在框选时插入进来。

7.6　CaptureWorkflow 状态机

enum class WorkflowStage { Idle, Selecting, Annotating };

配上一组布尔标记：active / longshot_result_ready / annotated_result_ready / selection_closed / selection_result_ready / annotation_result_ready。

这是当前最值得注意的技术债之一：这堆布尔标记的组合合法性靠人工维护。 文档说「后续重点是收紧 UI 状态 owner，而不是继续堆叠回调」。

7.7　四种 ID：一次外部调用为什么不能只用一个编号

ID代表什么为什么要分开
MCP rpc id把响应对应回外部 JSON-RPC 请求只属于协议层
RequestId一次内部提交负责调度过程，不等同于业务结果
OperationId可查询、可取消的一条操作记录保存状态与取消控制，不拥有图像
ResultIdResultStore 中的一张图像结果有自己的 scope、TTL 和 lease

外部真正看到的 result_id / operation_id 还是连接作用域内的不透明句柄，不是内部数字 ID。连接重建后，旧句柄不会跨 generation 继续生效。这样把“协议请求”“操作状态”“像素结果”三种生命周期拆开，Save / Copy / Pin 也必须明确指向一张结果，而不是猜测某个全局 current。

智能吸附：结题答辩只需要抓住两条主线

智能吸附的目标不是“从截图里猜一个框”，而是根据鼠标位置，尽快给出一个 可解释、可回退、不会误选大区域的候选矩形。核心入口是 SmartRegionDetector::detectAt()，实际悬停由 selection_overlay.cpp 驱动。

主线一：如何识别正确

多来源候选 → 语义筛选 → 统一评分

不同应用没有统一控件接口：浏览器可能提供 UIA / MSAA，Electron 工作台常常只有一个渲染窗口， 自绘区域则只能从截图边界判断。

  • UIA 优先识别 Button、TabItem、MenuItem、ListItem 等可操作控件。
  • UIA 没有有效局部结果时，后台用 MSAA 识别浏览器标签、书签、地址栏和工具栏。
  • 已知区域处理 Chrome 渲染区、记事本、资源管理器；视觉策略处理 VS Code 等 Electron 面板。
  • 最终保留 Client / Window 作为安全回退，不因局部识别失败而无结果。

主线二：如何做到轻量且不卡顿

快速路径 + 后台查询 + 有效性校验

UI 线程不等待跨进程 UIA / MSAA。先用窗口、已知区域和冻结截图得到初步候选， 再让后台线程补充结构化结果。

  • 首帧立即显示快速候选；UIA 查询由独立 worker 执行。
  • 鼠标移动按约 16ms 合并，UIA 结果约 8ms 轮询。
  • 请求采用 latest-wins，旧请求不与最新鼠标位置竞争。
  • 结果必须校验 Root、Owner、年龄和候选是否仍覆盖鼠标，避免迟到结果覆盖新区域。
  • 视觉结果和 UIA 结果都有限缓存；连续微动不重复执行完整扫描。

实际决策链：为什么不会“看到最小的就选最小的”

候选来源：UIA / MSAA / KnownContent / Visual / Client / Window
        ↓
基础校验：鼠标在矩形内、矩形属于 Owner、尺寸和置信度合格
        ↓
语义优先：ActionableControl  优先于  ContentSurface  优先于  Fallback
        ↓
评分选择：来源可靠性 + 控件语义 + 层级关系 + 边界证据
        ↓
稳定呈现：首个可信局部候选快速提升，普通候选切换约 48ms 稳定

代码中的关键保护是：UIA / MSAA 的可操作控件一旦有效，视觉和 Client / Window 回退不能抢走它； 视觉候选必须有连续边界证据，不能仅凭文字笔画或图片纹理成框。 候选模型、评分和稳定器集中在 include/qingying/window/smart_region_detector.hpp 与 src/window/smart_region_detector.cpp。

轻量化是怎么实现的

开销来源当前做法轻量化含义
窗口识别 WindowFromPoint + 顶层窗口过滤 只处理鼠标所在窗口，不扫描整张桌面
UIA / MSAA 后台线程、固定深度/节点/时间预算、latest-wins 不阻塞 UI，也不让无障碍树无限遍历
视觉识别 冻结截图 + 有限 ROI + 边界采样，不启用 OCR / 重型模型 默认悬停路径没有模型加载和逐帧推理成本
重复移动 视觉缓存、UIA 结果复用、16ms 输入合并 相同窗口和相近位置不重复做完整查询
内存和候选 候选数组固定容量，RAII 管理 COM / HANDLE 悬停热路径避免无界增长和资源泄漏

答辩一句话：轻量化不是降低识别能力，而是把不同成本的工作放到正确的位置： 本地、确定、快速的工作走 UI 线程；跨进程和不确定的工作走后台；视觉只做有限兜底； 所有路径都有固定预算和安全回退。

评委最可能追问的三个问题

  1. “为什么不用 OCR 或大模型直接识别？”——默认悬停要求低延迟和稳定性， 当前优先使用 UIA / MSAA 和局部边界；OCR / 视觉模型只能作为显式触发的增强模式。
  2. “UIA 返回慢或返回错了怎么办？”——首帧不等 UIA；结果回来后必须通过 Root、Owner、年龄和鼠标覆盖校验， 不合格就丢弃，快速候选继续作为回退。
  3. “怎么证明不是只在测试夹具里有效？”——答辩应区分自动化证据和真实应用证据， 至少展示 Chrome 外壳、VS Code 编辑器/终端，以及 UIA 失败时的回退日志；性能结论要用 P50/P95 数据支撑。

必须记住的边界：代码已经形成完整的候选、异步、缓存和稳定呈现链路； “所有应用都稳定”“性能已经显著提升”不能只靠单元测试下结论，必须有对应的真实应用复测和测量数据。

超时怎么办？

关键决策写在 application.cpp 里：

Application::~Application() {
  impl_->shutdown();
  if (impl_->requiresProcessReclaim()) {
    // A timed-out worker still owns callbacks and context. Keep the complete
    // application graph alive until process teardown instead of destroying a
    // live joinable thread's owner.
    (void)impl_.release();   // ← 故意泄漏，交给操作系统回收
    return;
  }
  impl_.reset();
}

宁可泄漏也不 detach / TerminateThread —— 这是正确的取舍，避免悬空回调和数据损坏。

取消不等于“线程此刻已经消失”

F9 的取消采用协作式语义：收到取消后先把操作标记为 cancelled / cancelling，再通过原来的调度链路通知真正执行者。对于保存文件、写剪贴板、创建 Pin 这类不可逆副作用，业务会在提交副作用前争抢 tryCommit()；如果取消已经取得优先权，就不再落盘或产生新的外部副作用。

因此取消之后，ResultLease、交互锁和 worker context 仍可能暂时存在，直到执行者真正收尾。这和四阶段 shutdown 是同一个思想：先停止产生新工作，再等待旧工作安全退出，最后才销毁它依赖的对象。

质量基线、当前状态与边界

理解项目不能只看“有哪些功能”，还要看它准备怎样证明这些功能可持续工作。中期阶段的测试思路是按边界分层，而不是只点一下截图按钮：Action / 类型契约、Workflow、ResultStore 与预算、PNG / 剪贴板、Pin、长截图拼接、插件 ABI、MCP session、wire codec、Pipe 身份与传输、进程集成以及关闭协调器都分别有自己的验证入口。

已经形成主链路

普通截图、框选、窗口吸附、标注动作、复制 / 保存、Pin、托盘热键等已经形成完整用户路径；Notepad、Explorer、Chromium 的长截图 profile 与通用引擎也已经接入。

已经接线，但还要做真实场景收口

F9 的 MCP protocol、stdio、Named Pipe、AutomationEndpoint，以及 Status / Capture / Copy / Save / Pin 等主链已经接通；真实客户端差异、安装包、断线、桌面关闭等场景仍需要继续验收。

指标是“验收目标”，不是自动成立的结论

项目提供测量脚本去检查发布目录、常驻内存、热键到首帧延迟，以及多轮操作后的句柄、线程、GDI / User 对象稳定性。目标包括包体 ≤ 20 MB、常驻工作集 ≤ 40 MB、首帧 P95 ≤ 300 ms；真正汇报时应以当天实测数据为准。

当前最值得记住的三个边界

  1. ABI 合法 ≠ 插件来源可信。结构体大小、版本、必需回调可以校验，但签名、哈希、目录 ACL 等发布信任策略仍需继续补强。
  2. 结构还有收口空间。AutomationEndpoint 对具体 Workflow 仍有反向依赖，Overlay target 也直接编译了部分 SmartRegion 源文件；这些不影响主链路，但说明“依赖方向”还不是完全结束的工作。
  3. 自动化测试 ≠ 真实应用结论。尤其智能吸附、跨 DPI、真实浏览器窗口和关闭/断线场景，需要用真实环境复测，性能最好用 P50 / P95 而不是主观“很快”来描述。

把整套设计压缩成五个词：小而原生、能力复用、扩展有边界、异步可回收、状态可验证。它们基本可以解释为什么项目要有 Action、Workflow、ResultStore、受控 ABI、Named Pipe、token 消息和四阶段 shutdown。

一句话总结

轻映是一个「以 Action 为原子、以 Workflow 为编排、以 static lib 为编译期边界、 以受控 ABI 为插件边界、以 Named Pipe + MCP 为对外边界」的 Windows 原生截图工具。

它的架构主干是 Application（组装）→ CaptureWorkflow（编排）→ ActionDispatcher（单步命令）→ 能力模块。 所有 GUI 多步流程被收口进 CaptureWorkflow 的非模态状态机， 所有结果被收口进带作用域与租约的 ResultStore， 所有生命周期被收口进四阶段关闭协调器。

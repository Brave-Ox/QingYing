# 架构如何调整

## 1. 调整目标与判断

本文基于当前代码基线：提交 a21f2ac4b4e04f8f777daccb4d355146fee9b069，日期 2026-09-14。详细问题证据见 [系统架构与耦合度分析](系统架构与耦合度分析.md)。

当前项目不需要推倒重来。它已经形成了“Win32 UI 外壳 + Action/Workflow 业务编排 + Named Pipe/MCP 外部接入 + 可插拔长截图引擎”的主干，功能边界基本能支撑当前产品。调整重点应放在三个方向：

1. 先消除插件信任、UI 线程阻塞、关闭阶段无限等待这三个高风险问题。
2. 再把 SmartRegion、Automation、能力描述和并发调度的实际边界补齐，减少实现边界与 CMake 边界不一致。
3. 最后整理兼容接口、状态模型、测试层次和文档，使后续功能沿着现有主干增长，而不是继续增加跨层特例。

以下方案按优先级分为 P0、P1、P2、P3。P0 应在继续扩大功能前完成；P1 是结构性收敛；P2、P3 可随迭代逐步落地。

## 2. P0：先处理安全、关闭和交互稳定性

### 2.2 建立有上限的统一关闭协议

严重程度：HIGH

问题位置：src/app/application.cpp；src/app/automation_runtime.cpp；src/app/export_executor.cpp；src/app/longshot_controller.cpp；src/window/uia_region_query_worker.cpp；src/ipc/pipe_server.cpp。

当前设计：Application 关闭时依次关闭 AutomationRuntime、计时器和热键；AutomationRuntime 再停止传输、停止接收、关闭 endpoint、等待生产者、停止 PipeServer。LongShotController、ExportExecutor、UIA 查询线程和 PipeServer 都以 stop/cancel 加 join 为主要退出方式。

存在的问题：多个拥有线程的对象分别实现 shutdown，没有统一的截止时间、阶段状态和超时诊断。只要某个插件回调、GDI/辅助功能调用、文件写入或外部 IO 不响应，UI 线程就可能永久卡在 join 或 drain。关闭路径也没有统一报告“哪个生产者、哪个请求、等待了多久”。

为什么是架构问题：线程停止顺序、请求拒绝、队列排空、结果清理和窗口销毁共同构成应用级生命周期协议，不能只由各类析构函数分别决定。当前对象局部正确，但全局关闭没有明确的拥有者和时间预算。

可能造成的后果：窗口关闭无响应、进程无法退出、CI 或自动化测试挂死；更危险的是开发者为了解决卡死而引入 detach、TerminateThread 或提前释放上下文，产生悬空回调和数据损坏。

推荐修改方案：

1. 增加 ApplicationShutdownCoordinator，明确四个阶段：停止接入、拒绝新任务、取消并等待业务生产者、排空 UI/IPC 回调后销毁窗口和资源。
2. 每个线程拥有者提供 stop、drain、joinUntil(deadline) 和诊断快照。先停止新输入，再通知取消，再等待；不要在仍可能产生回调时销毁接收对象。
3. 为普通关闭设置总预算，并为 LongShot、Export、UIA 查询和 Pipe worker 记录独立剩余时间。超时必须记录请求 ID、线程名、插件 ID、队列长度和最后进度。
4. 不能安全停止的线程不要 detach 后立即释放其上下文，也不要使用 TerminateThread。可将其所属服务对象转入应用级延迟回收区，保持上下文和回调存活，直到线程自然退出；若产品允许，可在明确的最后阶段让操作系统回收整个进程。
5. 将插件回调纳入同一关闭协议，给插件接口增加取消语义和最大操作时长；对无法中断的旧 ABI，至少禁止在 UI 线程执行并记录其不可中断性。

验收条件：构造阻塞式测试插件、阻塞式导出和未完成 UIA 查询，关闭流程能够在预算内返回或给出明确的“仍有后台线程”的诊断；所有 joinable thread 在对象销毁前都有确定的所有权和回收策略；重复调用 shutdown 不崩溃、不重复回调。

实施状态（2026-09-14，第一至第三阶段）：

- 已新增 `ApplicationShutdownCoordinator`，由 `Application` 组合根按 StopAdmission、RejectNewWork、CancelAndWait、DrainAndDestroy 四个阶段编排退出；
- `AutomationRuntime` 已拆分停止接入与停止 Pipe worker，`AutomationEndpoint` 已拆分拒绝新任务、停止业务生产者和最终回收回调；
- `CaptureWorkflow` 关闭时会显式停止 UIA 查询 worker；关闭参与者会记录阶段、名称、耗时、是否超过总预算和本地状态快照；重复关闭不会再次执行参与者；
- Export、LongShot、UIA 查询 worker 和 PipeServer 已提供 `joinUntil(deadline)`；协调器共享 5 秒总预算，某个参与者超时会返回未完成诊断并停止后续销毁步骤。
- 超时路径不使用 `detach` 或 `TerminateThread`：`Application` 会保留完整的对象图和回调上下文，交给进程结束时回收；正常路径仍由明确 owner 完成 join 后再销毁插件和窗口资源。
- 长截图插件 ABI 在尾部增加可选 `cancel` 信号，旧 DLL 没有该字段时继续兼容；阻塞式旧 ABI 插件、导出回调和 UIA 查询故障注入已覆盖，验证超时返回、上下文保留、解除阻塞后回收以及重复关闭。仍需补 WM_ENDSESSION 和真实桌面关闭验收。

### 2.3 将 SmartRegion 和捕获的重路径移出 UI 线程

严重程度：HIGH

问题位置：src/overlay/selection_overlay.cpp 的 updateHover/requestHoverUpdate/processUiaQueryResult；src/smart_region/smart_region_detector.cpp；src/smart_region/visual_region_locator.cpp；src/smart_region/msaa_region_locator.cpp；src/app/capture_service.cpp。

当前设计：选择框交互在 UI 线程维护；SmartRegionDetector 先同步执行 WindowDetector、KnownContentLocator 和视觉定位，再将 UIA/MSAA 查询交给一个后台 worker。捕获流程由 CaptureService 在 UI 线程调用 capture_invoker，并在捕获期间隐藏 pin/overlay。

存在的问题：设计虽然已经有 latest-wins、16ms hover 合并、UIA 后台查询和候选缓存，但普通 hover 路径仍可能同步执行跨进程查询、窗口枚举、视觉分析或大图处理；捕获也有同步调用和图像提交。局部预算不能保证整条端到端路径在 UI 线程内有上限。

为什么是架构问题：UI 线程既承担窗口消息、绘制和输入，又承担候选发现与图像采集，意味着任何一个底层 Win32、GDI、UIA/MSAA 或插件调用的延迟都会直接成为交互延迟。缓存只能降低平均成本，不能替代执行边界。

可能造成的后果：拖拽、悬停、热键和窗口重绘卡顿；辅助功能提供者异常时整个选择框失去响应；高 DPI 或大窗口下延迟抖动明显，用户会看到候选框跳动或过期结果覆盖新状态。

推荐修改方案：

1. UI 线程只负责采集输入、读取轻量窗口快照、发布请求和提交已验证结果。将视觉分析、UIA/MSAA、窗口内容探测和大图转换统一放入有界 RegionExecutor/CaptureExecutor。
2. 每个请求携带 generation、根窗口句柄及其进程标识、目标矩形和 deadline；结果提交前在 UI 线程再次验证 generation、窗口存在性、矩形和会话状态。
3. 保留快速 fallback，确保没有后台结果时仍能立即显示窗口级候选；后台结果只允许替换同一 generation 的候选，不得阻塞输入。
4. 捕获流程拆成 UI 快照、后台采集/编码、UI 提交三段。隐藏 overlay、确认 pin 状态等必须由 UI 线程完成，实际耗时捕获和 PNG 编码由专用执行器完成。
5. 给执行器设置有界队列、取消和拒绝策略；hover 采用最新请求覆盖旧请求，用户明确触发的 Capture/Save 则保留请求 ID 和可查询状态。
6. 对 UIA/MSAA/插件调用设置可观测超时和 provider 黑名单/冷却，不在 UI 线程上用同步调用“赌它通常很快”。

验收条件：交互测试中 UI 线程不直接进入视觉、UIA/MSAA 或插件重路径；在模拟 100ms、500ms 和永久阻塞 provider 时，窗口仍能拖动、取消和关闭；过期结果不会改变当前候选；Capture/Save 的延迟转化为 operation 状态，而不是阻塞窗口消息循环。

实施状态（2026-09-17）：

- Overlay 普通 hover 仅执行 `UiSnapshot`：最多读取 128 个顶层窗口的窗口管理器元数据，立即提供窗口/客户区回退，不进入内容探测、视觉或辅助功能重路径。诊断也不会在该策略下查询进程信息。
- `UiaRegionQueryWorker` 扩展为两条独立有界通道：Discovery 执行内容/视觉，Accessibility 执行 UIA/MSAA；每条通道各有一个运行请求、一个 latest-wins 等待请求和一个结果槽。慢 provider 不再阻塞视觉候选；视觉缓存由 Discovery worker 独占，背景采用不可变共享快照，取消时清理等待槽的图像引用。
- hover 请求/结果携带 request ID、generation、HWND、PID、矩形和 120ms deadline。提交（包括点击时提交延后结果）再次验证窗口身份、矩形和当前请求；generation 只随窗口身份、矩形或会话变化；同一上下文内仍命中当前鼠标的近期局部候选，在 worker 内重新绑定当前 request ID，保留原始年龄和 deadline。冻结截图相同才能复用视觉缓存。结果用完成消息直接唤醒 UI，timer 只作恢复；合并两条通道的候选，并保留局部候选与稳定计时，避免连续移动时退回窗口或重复等待。超过 deadline 后停止结果轮询，慢 provider 返回后按 HWND/PID 冷却 2 秒，诊断显示耗时和 deadline 是否超出。
- `CaptureService` 拥有专用 CaptureExecutor，复用有界执行器实现但与 PNG 导出实例独立。UI 保留准入、interaction guard、预算、pin 隐藏/恢复和 ResultStore 发布；窗口目录查询/复核、GDI 采集、图像转换与桌面预览合成都在后台。完成消息唤醒 UI，16ms timer 用于取消/deadline 检查和丢失唤醒恢复。
- Dispatcher CaptureRegion/CaptureWindow/CropCenter submit 与交互截图、编辑、结果预览已改为异步续接。GUI 每轮有 generation、cancellation 和 5 秒 deadline；弱生命周期 token 防止 workflow 关闭后的悬空回调。取消、deadline 或关闭在 provider 仍阻塞时释放 UI guard、丢弃晚到结果。同步方法只保留为兼容入口。
- GUI 保存对话框留在 UI，PNG 编码/文件提交由独立 ExportExecutor 执行并持有结果 lease，完成以 token 消息返回 UI。Pipe/MCP Capture/Save 沿用 operation ID、get_operation/cancel_operation 查询和取消。
- Capture worker 已纳入 ApplicationShutdownCoordinator 的共享关闭预算，超时保留完整对象图；Region/Export/LongShot 的 join 使用带谓词的等待，避免虚假唤醒后进入无限等待。
- 新增异步采集、100ms/500ms 延迟、持续阻塞、取消/deadline、窗口移动、PNG lease/线程边界回归；补齐 Region generation/PID/deadline、冷却和严格过期提交测试。

吸附延迟修复新增 7 项回归：连续移动接收近期局部结果、辅助功能阻塞不影响 Discovery、重绑身份/年龄/命中约束、冻结截图缓存身份、无 timer 完成通知、回退保留稳定计时，以及离开待切换区域后的点击选择。

自动验证结果：`./build.bat Release test` 已完成，Release 编译成功，完整 CTest **896/896 通过**。

验证边界：`./build.bat Release test` 执行 Release 编译及完整 CTest；持续阻塞测试通过显式解除阻塞验证最终回收。真实高 DPI、多显示器拖拽/关闭仍需人工验收。deadline 不会强行中断不响应的 Win32/COM provider，它仍可能占用对应 worker；UIA/MSAA 阻塞不会占用独立 Discovery 通道；UI 保持窗口级回退、取消和有预算的关闭。若需要强制恢复 provider 吞吐，需另行采用进程隔离。

## 3. P1：收敛真实模块边界和跨层接口

### 3.1 为 SmartRegion 建立实际的库边界

实施状态：已完成。新增 `qingying_smart_region` 静态库，统一拥有 detector、策略、视觉/已知内容/UIA/MSAA 定位器与异步执行器；overlay 仅私有链接该库，不再直接编译定位器源文件。

公共接口拆为 `smart_region_types.hpp`、`smart_region_detector.hpp`、`smart_region_diagnostics.hpp`，另由 `smart_region_query.hpp` 提供异步请求、结果与不透明执行器接口。定位器、视觉缓存和执行器线程实现保留在私有目录；overlay 不再持有视觉缓存或包含私有 worker 头。候选中保留用于排序的无障碍质量值，COM provider 与遍历实现不进入公共接口。

`SmartRegionProviders` 支持注入窗口快照、无障碍查询与视觉定位函数；注入窗口快照时跳过原生窗口与内容探测。新增独立 `qingying_smart_region_tests`，只链接 SmartRegion 和 GTest，通过 fake provider 验证候选合并、UI 快照禁止重查询、generation 与 deadline 过滤，无需创建真实 UI 窗口。

严重程度：MEDIUM

问题位置：src/overlay/CMakeLists.txt；include/qingying/window/smart_region_detector.hpp；src/smart_region/smart_region_detector.cpp、visual_region_locator.cpp、msaa_region_locator.cpp、uia_region_locator.cpp、uia_region_query_worker.cpp、known_content_locator.cpp。

当前设计：SmartRegion 的公开头文件和实现位于 window 目录，但 overlay 目标直接把多份 window 实现源文件编译进自身。公共头文件同时包含候选模型、UIA/MSAA 元数据、视觉缓存、策略、诊断、稳定器、渲染门和 detector。

存在的问题：目录名、头文件可见性和 CMake target 不一致；overlay 成为 SmartRegion 细节的编译和链接拥有者。公共头过大，修改候选模型或诊断字段会扩大重编译面，也容易让 overlay 直接依赖定位器内部类型。

为什么是架构问题：构建边界是依赖边界的可执行版本。当前代码虽然没有形成 CMake 环，但依赖方向被“谁编译源文件”隐式决定，后续很容易从 UI 调用内部定位器或让 window 模块反向感知 overlay。

可能造成的后果：编译时间增加、模块替换困难、测试需要带入窗口/UI 环境；SmartRegion 功能继续增加时，selection_overlay.cpp 和公共头会成为高耦合中心。

推荐修改方案：

1. 增加 qingying_smart_region 静态库，承载 detector、candidate model、policy、visual/UIA/MSAA locator 和 query worker；overlay 只链接其最小公共接口。
2. 将公共接口拆成 smart_region_types、smart_region_detector 和 smart_region_diagnostics 三个层次；UIA/MSAA provider 细节、缓存实现和线程 worker 放到 private 头。
3. 若暂时不想增加 target，至少在 overlay CMake 中保留私有源列表但禁止 overlay 业务代码包含各 locator 的内部头；这是过渡方案，不是最终边界。
4. 为 detector 注入 WindowSnapshot、AccessibilityQuery 和 VisualLocator 抽象或函数对象，使单元测试可以使用 fake provider。

验收条件：overlay CMake 不再直接编译 window 定位器实现；普通 overlay 修改不会触发所有定位器重编译；SmartRegion 的策略、候选合并和过期结果测试不需要创建真实 UI 窗口。

### 3.2 拆分 Automation 核心与应用工作流适配层

实施状态：已完成接口隔离与依赖倒置。`AutomationEndpoint` 仅通过 `AutomationOperationPort` 执行动作、查询 descriptor、关闭生产者，通过 `AutomationResultPort` 管理 scope、结果释放/过期及预算；不再持有或包含 `CaptureWorkflow`、`ActionDispatcher`、`ResultStore` 具体类型，`qingying_automation` 不再链接 `qingying_workflow`。

`AutomationWorkflowAdapter` 留在 app 层，由应用启动时组合 dispatcher、workflow 和 result store。动作能力名称及交互准入归属通过 descriptor 注册，Endpoint 不再硬编码 Capture/Save 的工作流分支。具体图像租约仍归应用结果存储与动作适配器所有，核心只使用结果生命周期接口。

新增独立 `qingying_automation_core_tests`，只链接 Automation 核心与 GTest，使用 fake port 覆盖会话 scope 隔离、幂等共享与重放、取消、关闭以及 descriptor 驱动的能力和准入；真实 workflow/result store 集成测试继续由完整测试套件验证。

验证：`./build.bat Release test` 完整通过 914/914；生成的独立核心测试工程没有 workflow、overlay 或 app handlers 依赖。重复关闭只调用一次端口，待执行操作在回收调度回调之前收到取消并完成清理。

严重程度：MEDIUM

问题位置：src/automation/automation_endpoint.cpp；include/qingying/automation/automation_endpoint.h；src/app/CMakeLists.txt；src/app/capture_workflow.cpp。

当前设计：qingying_automation_contract 依赖 action，qingying_automation 提供 registry、scheduler 和 endpoint；但 AutomationEndpoint 直接持有并调用 CaptureWorkflow，automation target 又链接 qingying_workflow。当前没有环，但 automation 的“核心层”实际知道具体应用工作流。

存在的问题：协议会话、幂等、取消、结果租约、准入控制和具体的 CaptureWorkflow 编排集中在同一个 endpoint；未来加入其他动作时，endpoint 会继续吸收应用特例。库名和目标依赖使调用方向不够直观。

为什么是架构问题：Automation 是接入与执行协调层，CaptureWorkflow 是应用用例层。前者依赖后者的具体类型，导致协议边界与产品用例边界绑定，削弱了复用和独立测试能力。

可能造成的后果：增加动作需要同时修改 endpoint、workflow 和 action contract；MCP、Pipe 和未来本地调用无法共享一个稳定的执行端口；改变捕获流程可能意外影响协议会话。

推荐修改方案：

1. 把 endpoint 中与具体捕获无关的部分抽成 AutomationSession/OperationCoordinator：认证、scope、幂等、取消、状态和 ResultLease 只依赖小接口。
2. 定义 ActionExecutor 或 OperationPort，按 ActionType 路由到 CaptureWorkflow、ExportService、PinService 等应用适配器；automation 核心只调用端口，不包含 CaptureWorkflow 头。
3. 将 workflow 继续留在 app 层，由 app 组合 executor adapter；把具体能力注册和应用启动也保留在 composition root。
4. 先以接口隔离和依赖倒置为主，不要把每个动作拆成一个动态库或引入容器式依赖注入。

验收条件：automation 单元测试可以在不链接 qingying_workflow 的情况下覆盖会话、幂等和取消；新增一个简单操作只需实现 adapter 和 descriptor，不需要在 endpoint 中加入新的具体 workflow 分支。

### 3.3 让能力、处理器和 MCP 工具使用一个事实源

严重程度：MEDIUM

问题位置：src/automation/automation_endpoint.cpp 的 capability/ready_actions；src/automation/action_handlers.cpp；src/mcp/tool_catalog.cpp；src/app/capture_workflow.cpp。

当前设计：动作处理器、Automation 的 ready action/status、CaptureWorkflow 的能力判断和 MCP tool catalog 分别维护可用能力、参数和状态。当前 MCP 已有 status、capture_window、crop_center、copy、save、pin、get_operation、cancel_operation、release_result 等工具。

存在的问题：同一动作的 ID、是否可用、参数校验、是否异步、取消语义和错误映射分散在多处。新增或下线能力时，容易出现 MCP 已暴露但 endpoint 不接受、ready 状态与实际 handler 不一致、文档描述过期等问题。

为什么是架构问题：能力声明本身就是产品契约，不应由多个接入层各自推导。多个事实源会把一个功能变更放大成跨层同步工作，并且很难通过编译器发现遗漏。

可能造成的后果：外部自动化收到不可执行的工具；客户端错误重试或错误提示不一致；测试覆盖每个接入层的排列组合，维护成本持续上升。

推荐修改方案：

1. 建立 ActionDescriptor，包含稳定 ID、输入 schema/解析器、可用性谓词、同步/异步类型、取消能力、结果类型和错误映射。
2. registry 以 descriptor 为唯一注册源；Automation ready_actions、status、MCP catalog 和 handler 路由均从 registry 生成。
3. capability 只描述产品能力，不把瞬时 busy、scope 或窗口状态伪装成静态能力；动态状态通过 operation/status 单独返回。
4. 为每个 descriptor 增加契约测试，验证“可发现、可路由、错误一致、取消一致”。

验收条件：添加或删除一个动作时，编译期或契约测试能发现 catalog、ready action、handler 和文档中的遗漏；同一个无效参数在 Pipe 和 MCP 上产生一致的错误码和字段。

### 3.4 用显式唤醒消息替代轮询式主路径

严重程度：MEDIUM

问题位置：src/app/application.cpp 的消息过滤、scheduler request/completion 消息和 250ms timer；src/automation/ui_action_scheduler.cpp。

当前设计：UI 消息过滤器处理 scheduler 请求和完成；Application 还以 250ms 定时器调用 runtime.tick，外部请求和后台结果通过 PostMessage 进入 UI 线程。

存在的问题：消息驱动和周期 tick 同时承担调度职责，运行状态可能在两条路径上推进；250ms 轮询放大了空闲唤醒，过短会浪费资源，过长又会增加响应延迟。队列积压、唤醒合并和关闭时的消息顺序缺少统一的状态机约束。

为什么是架构问题：调度的触发机制属于控制流设计。两套触发源同时修改同一批状态，容易让顺序、重入和 shutdown 语义依赖实现细节。

可能造成的后果：重复 tick、操作完成延迟、关闭期间收到旧消息、低功耗场景空转；出现偶发问题时难以复现真实的事件顺序。

推荐修改方案：

1. scheduler 入队、后台结果、取消和关闭均通过一个可合并的自定义唤醒消息通知 UI 线程；UI 线程每次唤醒批量 drain，且只处理当代 session/generation 的事件。
2. 将 timer 降级为低频 housekeeping，例如清理过期租约、检查超时和刷新诊断，不再作为普通请求的主要推进机制。
3. 在 scheduler 中明确 queued、running、settling、completed、cancelled、expired、rejected 状态转移，禁止完成回调与取消回调同时结算同一 operation。
4. shutdown 时先撤销唤醒来源，再标记 scheduler stopped，最后清理残留消息；窗口销毁后消息只允许安全丢弃。

验收条件：空闲进程不依赖 250ms 高频 tick 推进普通请求；高并发请求能批量处理且不重复结算；测试可以记录并重放 request、completion、cancel、shutdown 的事件序列。

### 3.5 明确 PipeAutomationClient 的线程所有权

严重程度：MEDIUM

问题位置：src/ipc/pipe_automation_client.cpp 的 connect/close；客户端共享状态和 reader thread。

当前设计：connect 创建 reader thread 后 detach，通过共享 state、done 事件和 close 协作；close 会取消 pipe，reader 自行结算并发出完成通知。

存在的问题：共享状态使当前实现大体可用，但线程不由 client 对象直接拥有，生命周期依赖隐含的 shared state 协议；回调目标、close 重入、reader 自终止和异常退出的规则不容易由类型系统表达。

为什么是架构问题：IPC 客户端的连接、读循环、回调和关闭是一个资源所有权单元。把线程 detach 后再用状态协议模拟 join，会把本应显式的生命周期转化为人工证明。

可能造成的后果：未来修改回调或 close 顺序时出现晚到回调、重复 done、关闭等待死锁或退出后仍有线程访问共享资源；问题通常只在进程退出和异常断管时出现。

推荐修改方案：

1. 使用明确拥有的 reader thread 或 std::jthread，由 PipeAutomationClient/ClientState 在 close 和析构时统一 join；保留 self-close 分支但禁止 self-join。
2. 回调只投递到受控的 callback executor 或显式的弱引用状态，不直接假设调用者对象仍存活。
3. 将连接状态、关闭原因、reader exception 和最后一帧信息做成可查询诊断；close 必须幂等。
4. 如果必须跨对象共享 state，要把 state 设计成独立的 ConnectionLifetime 对象，并在接口文档中明确谁拥有、谁释放、何时停止回调。

验收条件：多次 connect/close、服务端突然断开、客户端回调中再次 close、析构期间 reader 结束等场景均无 UAF、重复回调和 join 死锁；正常关闭不依赖进程退出兜底。

## 4. P2：整理状态、契约、异常和测试结构

### 4.1 把会话状态从 AutomationEndpoint 中抽出

严重程度：MEDIUM

问题位置：src/automation/automation_endpoint.cpp；连接建立、scope、认证、idempotency、pending operation、result lease 和 shutdown 逻辑。

当前设计：Endpoint 同时负责连接状态、身份与 scope、请求准入、动作分派、操作表、幂等结果、ResultStore 租约以及关闭。

存在的问题：单个类的控制流密度高，隐含状态分散在字段、registry、scheduler 和 ResultStore 之间。会话级错误、全局资源错误和单个 operation 错误的边界不够明显。

为什么是架构问题：会话是 IPC/MCP 资源隔离和权限判断的基本单位；如果会话状态没有实体化，所有分支都会继续堆在 endpoint，故障隔离和测试夹具也会越来越难。

可能造成的后果：一个连接的取消、断开或过期结果影响其他连接；重复请求、连接关闭和后台完成竞态难以验证；新增认证或配额时必须修改大量既有分支。

推荐修改方案：

1. 增加 AutomationSessionState，至少包含 protocol phase、peer identity、scope、pending operations、idempotency entries、owned result leases 和 close reason。
2. Endpoint 只负责把 Pipe/MCP 事件转换成 session command，并调用 OperationCoordinator；会话对象负责状态转移和连接级清理。
3. 全局 capture gate、ResultStore memory budget 和插件状态继续由应用级对象拥有，session 只能持有租约或句柄，不能拥有全局资源。
4. 为每个状态转移定义前置条件和幂等规则，尤其是 close、cancel、release_result 和 operation completion。

验收条件：可以单独构造两个会话测试互不影响；断开一个会话只释放其租约和请求；Endpoint 的单元测试不需要启动真实窗口或完整 Application。

### 4.2 拆分 action/types.hpp 的跨域契约

严重程度：MEDIUM

问题位置：include/qingying/action/types.hpp；ActionType、窗口候选、捕获请求/结果、操作状态、资源状态、LegacyActionRequest 和自动化请求混在同一公共头。

当前设计：action/types.hpp 作为多个静态库和接入层共享的总契约，集中定义了动作、错误、窗口、捕获、取消、状态、操作请求和兼容请求等类型。

存在的问题：一个领域的字段变化会触发多个目标重编译；IPC、UI、业务和测试都能看到不需要的类型；类型之间的依赖关系不能体现模块边界。

为什么是架构问题：公共头是最强的编译时耦合。它把“共享少量稳定值类型”扩大成“所有层共享全部业务模型”，让依赖方向和演进成本失去控制。

可能造成的后果：接口越来越难删；UI 或 IPC 为了一个类型依赖整个 action 领域；错误码、状态和旧接口互相污染；编译时间和理解成本上升。

推荐修改方案：

1. 逐步拆分为 action/common_types、window/window_types、capture/capture_types、operation/operation_types、automation/automation_types；每个头只保留稳定值类型。
2. 将 IPC wire DTO 与内部领域对象分离，边界处显式转换和校验，不让协议字段直接成为业务对象。
3. 将 LegacyActionRequest 放入 compatibility 头或适配器 target，新的模块不要继续依赖它。
4. 对外只暴露必要的 enum、ID、轻量 struct 和接口；大对象使用不透明句柄、共享只读快照或明确的所有权类型。

验收条件：修改窗口候选诊断字段不会触发 MCP/IPC 全量重编译；新代码可以不包含 LegacyActionRequest；协议 DTO 的非法值不会直接进入内部状态。

### 4.3 建立统一的错误边界与诊断链路

严重程度：MEDIUM

问题位置：src/app/application.cpp 的 TrayController/消息过滤；src/ipc/pipe_server.cpp 的 drain hook；src/longshot/longshot_plugin_host.cpp；各线程 worker 的回调边界。

当前设计：ActionDispatcher、Pipe worker、MCP session 等局部位置已有异常捕获和错误响应；但 UI 消息入口、部分 drain hook 和插件 ABI 回调没有统一的最外层保护与结构化诊断。

存在的问题：异常可能直接穿出 Windows 消息回调；PipeServer 在 UI 线程 drain 时调用 hook，单个 hook 异常的隔离规则不明显；插件加载或回调失败时缺少统一的 operation/session/request 关联信息。

为什么是架构问题：错误处理不仅是 try/catch 数量问题，还决定故障域。Windows 消息、IPC 会话、operation、插件和应用进程应有不同的恢复策略，当前策略分散在调用点。

可能造成的后果：一条外部请求或一个 provider 异常演变为 UI 线程崩溃；用户只能看到“失败”，无法区分超时、取消、权限、资源不足和 provider 故障；同类故障反复触发。

推荐修改方案：

1. 在 WndProc、消息过滤器、UI scheduler drain、Pipe drain hook 和插件入口建立最外层异常边界；边界内转换为稳定错误码并记录日志。
2. 统一 ErrorCode、retryability、origin、operation ID、session ID、provider/plugin ID 和 elapsed time 字段；日志和外部响应使用同一 correlation ID。
3. 将“单请求失败、单会话失败、单插件熔断、整个应用不可继续”定义为不同故障等级。
4. provider 超时/异常时采用冷却、降级到窗口候选或拒绝当前操作；不要在每次 hover 中无限重试。
5. 生产环境不要把敏感窗口标题、路径和图像内容写入普通日志；诊断需要脱敏和采样。

验收条件：人为抛出 handler、plugin、Pipe hook 和 UI 任务异常时，进程仍能按故障域存活；外部客户端收到稳定错误码；日志可以从 request ID 追到会话、队列和底层来源。

### 4.5 用统一预算核算图像峰值，而不是只限制 ResultStore

严重程度：MEDIUM

问题位置：src/app/result_store.cpp；src/app/capture_service.cpp；src/overlay/selection_overlay.cpp；src/app/longshot_controller.cpp；PNG 临时文件和图像复制路径。

当前设计：ResultStore 使用 Reservation 和容量预算限制 retained image，并通过 lease 管理外部结果；CaptureService 在提交前预留；overlay、longshot、导出和 get 结果仍可能各自持有 Image、缓存或临时副本。

存在的问题：持久结果预算与 in-flight capture、后台候选图、longshot preview、导出编码、get 的完整复制峰值没有完全统一计量。单个接口看似有界，组合执行时峰值可能明显高于配置预算。

为什么是架构问题：内存上限属于跨模块资源政策，不能由 ResultStore 单独保证。所有权和预算若不由同一个资源模型表达，新增缓存或异步队列就会绕过限制。

可能造成的后果：大屏、高 DPI、多帧长截图或多个并发客户端下内存尖峰；系统提交压力上升、编码失败、UI 抖动甚至进程被系统终止。

推荐修改方案：

1. 建立 ImageMemoryBudget，分别统计 retained、in-flight、preview、worker queue、encode scratch、wire copy 和 external lease。
2. CaptureService、LongShotController、ExportExecutor 和 ResultStore 均通过 budget token 申请容量；申请失败返回资源不足而不是继续分配。
3. 优先返回只读 lease/句柄或流式写出，避免 get 操作无条件复制完整 Image；必要复制必须计入预算。
4. 对 overlay 预览和 SmartRegion visual cache 设置独立数量、字节和 TTL 上限，并提供运行时指标。

验收条件：大图、长截图、同时 Save/Copy/Get、多个 session 和取消重试场景都能看到峰值预算；预算耗尽时行为可预测，取消后 token 必须归还。

## 5. P3：清理长期维护成本

### 5.1 隔离兼容接口并同步架构文档

严重程度：LOW

问题位置：include/qingying/action/compatibility/legacy_action_request.h；src/action/compatibility/legacy_action_dispatcher.cpp；docs/architecture.md；docs/PROGRESS.md；docs/项目理解.md。

当前设计：项目保留旧动作请求和兼容分派路径，同时架构文档、进度文档与当前 SmartRegion、MCP 和 target 结构存在时间差。

存在的问题：旧接口与新接口都出现在核心契约里，文档读者难以判断哪些是现行主路径、哪些只是兼容层。文档漂移会使后续改动依据错误的模块图和完成状态。

为什么是架构问题：兼容层如果没有明确隔离，就会反向塑造新代码；文档如果不是当前结构的事实源，就无法承担架构约束和交接职责。

可能造成的后果：新功能继续依赖 legacy 类型；开发者重复实现已经存在的 MCP/automation 能力；评审和测试遗漏真实的 SmartRegion、插件和 shutdown 风险。

推荐修改方案：

1. 将兼容请求、旧 dispatcher 和迁移说明放入 compatibility 目录/target；新业务代码禁止新增依赖。
2. 对每个 legacy API 标注保留原因、替代 API、删除条件和 owner；必要时加编译期 deprecation。
3. 以 CMake target graph、运行时数据流和本报告为文档事实源；每次跨模块变更同步 architecture.md、PROGRESS.md 和项目理解文档。
4. 在 CI 中增加文档中的 target/能力清单检查，至少阻止把已实现 MCP 误写成 Stub，或把已删除 target 写入图中。

验收条件：新代码不包含 legacy 头；文档能准确区分 Stub、已实现、部分验证和真实桌面待验收；新同事只看文档即可定位 composition root 和异步边界。

实施结果（2026-09-14）：

- `LegacyActionRequest` 与 `adaptLegacyActionRequest()` 已移出 `action/types.hpp` 和现行 Dispatcher，分别放入 `include/qingying/action/compatibility/`、`src/action/compatibility/`；
- 新增 `qingying_action_compatibility` 迁移 target，生产 EXE、workflow、automation、MCP 和插件 target 不依赖它；两个 legacy API 已添加编译期 deprecated，并在兼容头中记录保留原因、替代 API、删除条件和 owner；
- `docs/architecture.md`、`docs/PROGRESS.md` 和本 `docs/项目理解.md` 已同步 target 图、能力状态、composition root 与异步边界。

## 6. 推荐实施顺序

建议按以下顺序拆成小的、可回滚的变更：

1. P0-1：插件 manifest、路径/ACL/签名或哈希校验、加载诊断。
2. P0-2：shutdown coordinator、deadline-aware join、超时上下文保留、插件取消契约和阻塞测试夹具已完成；剩余 WM_ENDSESSION 与真实桌面关闭验收。
3. P0-3：普通 SmartRegion/Capture/PNG 主路径已移出 UI，generation/deadline、取消、关闭与阻塞回归已落地；真实高 DPI/多显示器交互仍待人工验收。
4. P1-1：建立 qingying_smart_region target，缩小 overlay 的可见接口。
5. P1-2：抽 AutomationSession/OperationCoordinator 和 ActionExecutor port，解除 automation 对 CaptureWorkflow 具体类型的依赖。
6. P1-3：以 ActionDescriptor 统一能力、handler 和 MCP catalog；补契约测试。
7. P1-4/P1-5：统一 UI 唤醒与 PipeAutomationClient 线程所有权。
8. P2：拆 action contract、错误诊断、内存预算和四层测试。
9. P3：隔离 legacy、更新文档、整理 Annotation/Toolbar 状态。

每一步都应保持可编译、可运行，并先增加针对旧行为的回归测试，再改变实现。不要把 P0 的安全和生命周期修复与大规模目录移动绑定在同一个提交中。

## 7. 暂不建议做的事情

1. 不要把当前项目整体改造成完整 Clean Architecture、DDD 或多进程微服务。现有桌面产品的边界和规模还不需要这些固定成本。
2. 不要为了“彻底异步”把所有 Win32 操作都搬离 UI 线程；窗口创建、消息、绘制和最终状态提交仍应由 UI 线程负责，目标是隔离可阻塞的重路径。
3. 不要新增 Service Locator、全局 singleton 或隐式事件总线来绕过当前的接口设计问题。
4. 不要把所有源文件拆成大量小 DLL；优先用清晰的静态库 target、private header 和适配器解决依赖。
5. 不要用 detach、TerminateThread、泄漏对象或强制进程终止掩盖关闭协议问题。
6. 不要为了统一 MCP 而让核心业务依赖 JSON；协议 DTO 与内部类型应在边界处转换。
7. 不要在没有真实指标前盲目增加缓存、线程池和预加载；先测 UI 延迟、启动时间、图像峰值和关闭耗时。

## 8. 最终验收门槛

完成本轮架构收敛后，至少应满足：

1. 发布版只能加载受信任、可验证的长截图插件。
2. UI 线程不执行无界的视觉、UIA/MSAA、插件、编码或文件 IO 重路径。
3. 每个后台线程都有明确 owner、stop/cancel 语义、join 策略和关闭诊断。
4. Pipe/MCP 的连接、会话、operation、结果租约和取消互不越权、互不串扰。
5. 能力发现、MCP 工具和 action handler 来自同一 descriptor/registry。
6. 图像 retained 与 in-flight 峰值均受统一预算约束。
7. CTest 在干净构建目录可以发现测试，且另有受控真实桌面验收。
8. architecture.md、PROGRESS.md、项目理解.md 与当前 CMake/代码状态一致。

结论：当前主架构方向合理，优先级不是“换架构”，而是把已存在的分层从约定变成可执行边界。完成 P0 后，产品可以继续迭代；完成 P1/P2 后，SmartRegion、MCP 和更多自动化动作才有较稳定的扩展基础。

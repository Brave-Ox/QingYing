# 轻映 QingYing — 架构调整计划

> 更新日期：2026-09-07（按 `master` / `40d22e21` 同步）
> 本文保留原有分阶段计划，同时标出已经由提交落地的阶段；后续任务以 F9 的外部契约为主。详细问题证据见 [系统架构与耦合度分析](系统架构与耦合度分析.md)。

## 1. 调整目标

保留当前“单 EXE + static lib + ActionDispatcher + Win32 顶层消息泵”的方向；长截图的 Notepad / Explorer / Chromium profile 通过受控 DLL ABI 部署。继续用小步、可回滚的方式收口边界，目标不是重写成 Qt、多进程或第二套截图引擎，而是让每个模块只依赖它真正需要的协议。

必须保持的规则：

1. `Application` 是 Composition Root，拥有顶层消息泵、对象组装和退出顺序。
2. 单步、可复用能力走 `ActionDispatcher`；选区、标注、交互式长截图走 `CaptureWorkflow`。
3. Overlay 只处理窗口、输入、渲染和 UI 意图，不直接 Capture、Export、Pin 或写 `ResultStore`。
4. AnnotationOverlay 只返回 `AnnotationFinishResult`，不调用 Dispatcher、Export、Capture 或 Pin。
5. LongShotEngine 只负责 profile、滚动、捕获、拼接和结果，不拥有 UI、`ResultStore` 或外部协议。
6. 外部 Command / MCP 只能进入 Dispatcher 或受控 Workflow 入口，不能直接调用 Engine 或全局结果槽位。

### 1.1 当前已落地的收口

截至 `40d22e21`，以下阶段性工作已由代码和提交完成：

- `ResultStore` / `ResultActionService` 已统一 Copy / Save / Pin，`CaptureSession` 只保留兼容门面；
- `UiMessageChannel` 已统一跨线程 payload 的 token、所有权和 drain；
- `AnnotationEditorHost` 已完成内部组件拆分；
- `ScreenPhysicalRect`、`OverlayClientRect`、`ImagePixelRect` 等中立坐标协议已接入；
- `ActionRequest` 已改为 `std::variant` 类型化 payload，并带 request / operation id、取消、超时和结果选择；
- `qingying_app_handlers` 已独立，F6 已形成通用 runtime + profile DLL 插件宿主；
- Selection / Annotation Overlay 已是非模态窗口，由 Application 顶层消息泵驱动。

因此，下面“阶段 1～6”的步骤是实施记录和剩余细化项，不应再理解为这些基础设施尚未存在。

## 2. 当前最需要解耦的地方

### P0：先处理运行时闭环和生命周期

1. `CaptureWorkflow` 仍同时编排流程状态、截图、标注、结果动作和 Pin 排除；它是当前 GUI 的流程边界，F9 需要在其外层增加稳定的 operation 接口，而不是让外部直接持有 Workflow。
2. `ResultStore` 目前只有一个 current 槽位；F9 需要作用域、ResultId、租约、过期和字节预算，不能把 GUI 的 current 语义直接暴露给外部。
3. `UiMessageChannel` 已解决 payload 所有权和 drain，但还没有连接代际、队列准入和自动化请求公平调度。
4. `McpBridge` 尚未接入 Named Pipe、JSON-RPC、主线程调度和 Tool 映射；`CaptureWindow` / `CropCenter` 仍是桩。
5. `AnnotationEditorHost` 已完成文件级拆分，但内部仍共享编辑状态；这属于 P2 平台/UI 整理，不阻塞 F9。

### P1：再处理协议和编译边界

1. 中立的选区、UI 意图、标注结果和命名坐标类型已落地；后续只需继续清理遗留适配层。
2. `ActionRequest` 的 `std::variant` payload、request/operation id、取消、超时和结果选择已落地；F9 仍需补类型化 `ActionResult` 输出和异步 operation。
3. Application 已使用 PIMPL，`qingying_app_handlers` 已独立，测试通过 target 使用生产 Handler；后续只处理真实复用带来的编译边界。

### P2：最后整理平台基础设施

1. 明确 `AnnotationRenderer` 的 GDI 文本栅格化边界。
2. 将 `ModernToolbar` 的 Toolbar Model 与 GDI / layered-window 绘制后端分开。
3. 将 Pin 的截图排除能力抽成 `CaptureExclusionService`，再评估是否拆 `qingying_window`。

## 3. 目标依赖方向

```text
Application（组合、消息泵、退出顺序）
  ├──> CaptureWorkflow（多步流程编排）
  ├──> ActionDispatcher（单步动作）
  └──> 具体服务与生命周期对象

CaptureWorkflow
  ├──> SelectionOverlay / AnnotationOverlay / PinWindow 等 UI
  └──> Capture / Export / LongShot / Result 服务

UI 与服务
  └──> 中立协议 / Image / Action / Domain 类型
```

Workflow 可以依赖具体服务进行编排，但具体功能模块不得反向依赖 Workflow。特别是：

- PinManager 不持有 Workflow 回调；保存对话框由上层提供独立的结果动作服务；
- Overlay 公共头只暴露选区和 UI 意图；纯逻辑模块不 include `selection_overlay.hpp`；
- AnnotationHost 通过窄接口调用 Chrome、InlineText、StrokePopup、ColorPicker 和 Paint；
- Worker 只向受控的 UI 消息通道投递事件，不能把裸指针生命周期散落在多个窗口过程中。

## 4. 分阶段实施顺序

### 阶段 0：冻结契约并补回归测试（基础已落地，环境回归仍在进行）

先不改变公开功能，补齐以下测试：

- 新截图开始时释放上一张结果；Capture 失败后不恢复旧结果；
- Save / Copy / Pin 均能明确选择“当前结果”或指定结果；
- Overlay 关闭、Workflow shutdown、worker join 后没有未消费 payload；
- Annotation 取消不覆盖 `ResultStore`，确认只提交一次。

完成标准：测试能够稳定描述当前失败语义和退出语义，后续重构不再依赖人工猜测。

### 阶段 1：拆结果流，解除 Pin 回调闭环（已完成）

已引入 `ResultStore` / `ResultActionService`，Copy、Save、Pin 已从“隐式读取 Session”收口到统一结果服务；当前仍只有一个 GUI current 槽位，F9 需要在其上增加外部租约。

迁移顺序：

1. 新截图开始时先清空旧结果，Capture 成功后再发布当前结果；失败后结果保持为空；
2. Workflow 的保存对话框移入独立的 Save flow；
3. PinManager 只接收 Image 和局部 UI 命令，不回调 Workflow；
4. GUI、Handler、PinWindow 的结果动作统一到一个服务。

完成标准：依赖图中不再出现 `PinManager → CaptureWorkflow`，Save 不再有三套实现语义。

### 阶段 2：收口窗口和消息所有权（基础已完成，F9 还需代际/准入）

已统一 SelectionOverlay、AnnotationOverlay 和 LongShotController 的消息协议；F9 还需在现有 channel 上增加连接代际、队列准入和自动化调度：

- `GWLP_USERDATA` 只保存观察指针，不承担删除职责；
- Host / Overlay 的唯一所有者始终是 `unique_ptr`；
- `PostMessage` 成功后的 payload 有明确 owner；
- `WM_DESTROY`、`WM_NCDESTROY` 和 `shutdown` 都能 drain 未消费消息；
- worker 停止并 join 后，才销毁窗口和卸载插件。

完成标准：源码中不再依靠 `release()` + WndProc 裸 `delete` 传递窗口状态；退出、创建失败和窗口提前销毁均有测试覆盖。

### 阶段 3：真正拆 AnnotationEditorHost（已完成基础拆分）

保持 `AnnotationOverlay` 的公开 API 不变，Host 已按以下组件拆分；内部共享状态的进一步窄接口化属于后续 P2：

组件只能通过窄接口读写所需状态；Paint 只读快照，不修改 Controller 或提交文档；Chrome、InlineText 和弹窗不得依赖 Dispatcher、Export、Capture 或 Pin。

完成标准：Host 不再暴露几十个跨文件自由函数和全部可变字段；`AnnotationOverlay` 持有 Host 的唯一 `unique_ptr`。

### 阶段 4：抽中立 Selection / Result / Coordinate 协议（已完成基础协议）

完成标准：SelectionController、MaskRenderer 和纯像素测试不需要 include Overlay 外观头；跨模块矩形的坐标空间在类型或接口名称中可见。

## 5. 不应做的事情

- 不重写 LongShot 插件 ABI，不把应用识别逻辑放回 LongShotEngine；
- 不为了目录整齐提前拆 `qingying_window`；
- 不用 `shared_ptr` 掩盖 HWND、worker 或插件的所有权；
- 不把所有 GUI 局部命令机械塞入 ActionDispatcher；
- 不在一次提交中同时重构 Annotation、消息循环、F8/F9 和插件协议。

## 6. 完成判断

当以下条件全部满足时，认为本轮解耦完成：

1. Workflow 不再被 PinManager 反向回调；
2. 新捕获开始和工作流结束都释放结果，Capture 失败后不恢复旧结果，结果动作使用明确上下文；
3. Overlay / Annotation Host 和跨线程 payload 的所有权可从代码直接追踪；
4. Selection、Annotation、LongShot 的公共协议不再互相携带无关数据；
5. F8/F9 不需要继续膨胀 `ActionRequest`；
6. 关键 UI 生命周期、退出和混合 DPI 路径有可重复测试。

## 8. 每次提交的固定验收流程

每个阶段完成后必须在仓库根目录执行：

```powershell
.\build.bat Release test
```

该脚本会完成 Release 配置、编译和 CTest。不要用手工 `cmake --build` 结果替代阶段验收。失败时先区分：

1. 环境权限或工具链问题；
2. CMake/编译错误；
3. 测试回归；
4. 测试发现但与本阶段无关的既有问题。

行为验收至少覆盖：普通截图、标注确认/取消、长截图暂停/停止、Copy、Save、Pin、窗口提前关闭和应用退出。

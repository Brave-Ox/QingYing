# 轻映 QingYing — 架构调整计划

> 更新日期：2026-09-03（实施细化版）
> 本文只保留后续调整计划，不再记录已经完成的提交历史。详细问题证据见 [系统架构与耦合度分析](系统架构与耦合度分析.md)。

## 1. 调整目标

保留当前“单 EXE + static lib + ActionDispatcher + Win32 顶层消息泵”的方向，继续用小步、可回滚的方式收口边界。目标不是重写成 Qt、多进程或第二套截图引擎，而是让每个模块只依赖它真正需要的协议。

必须保持的规则：

1. `Application` 是 Composition Root，拥有顶层消息泵、对象组装和退出顺序。
2. 单步、可复用能力走 `ActionDispatcher`；选区、标注、交互式长截图走 `CaptureWorkflow`。
3. Overlay 只处理窗口、输入、渲染和 UI 意图，不直接 Capture、Export、Pin 或写 Session。
4. AnnotationOverlay 只返回 `AnnotationFinishResult`，不调用 Dispatcher、Export、Capture 或 Pin。
5. LongShotEngine 只负责 profile、滚动、捕获、拼接和结果，不拥有 UI、Session 或外部协议。
6. 外部 Command / MCP 只能进入 Dispatcher 或受控 Workflow 入口，不能直接调用 Engine 或全局 Session。

## 2. 当前最需要解耦的地方

### P0：先处理运行时闭环和生命周期

1. `CaptureWorkflow` 同时承担流程状态、截图、标注、导出、错误提示、Session 和 Pin 排除；它依赖 7 个具体对象。见 [capture_workflow.hpp](../include/qingying/app/capture_workflow.hpp) 和 [capture_workflow.cpp](../src/app/capture_workflow.cpp)。
2. `PinManager` 保存回调指向 `CaptureWorkflow::saveImage()`，形成 `Workflow → PinManager → Workflow` 的反向运行时闭环。见 [application.cpp](../src/app/application.cpp) 和 [pin_manager.cpp](../src/pin/pin_manager.cpp)。
3. `CaptureSession` 是 Capture → Copy/Save/Pin 的隐式时序通道，捕获失败前清空 Session 还会丢失旧结果。见 [action_handlers.cpp](../src/app/action_handlers.cpp)。
4. SelectionOverlay、AnnotationOverlay 和 LongShotController 的 HWND / `PostMessage` payload 仍需要统一的所有权和退出回收协议。
5. Annotation 的多个 cpp 仍共享一个包含全部 UI 状态的 `AnnotationEditorHost`；文件拆分尚未形成真正的组件边界。

### P1：再处理协议和编译边界

1. 把 `SelectionResult` 拆成中立的选区、UI 意图和标注结果类型，移出 `annotated_image` 等跨功能字段。
2. 为屏幕物理坐标、Overlay 客户区、Image 像素和标注视图建立命名矩形类型。
3. 在 F8/F9 前将胖 `ActionRequest` 改为命名 payload 或 `std::variant`，增加 request/operation id、取消和超时。
4. 让 Application 的具体服务进入 PIMPL；测试通过独立 target 使用 Handler，不直接编译 `src/app/action_handlers.cpp`。

### P2：最后整理平台基础设施

1. 明确 `AnnotationRenderer` 的 GDI 文本栅格化边界。
2. 将 `ModernToolbar` 的 Toolbar Model 与 GDI / layered-window 绘制后端分开。
3. 将 Pin 的截图排除能力抽成 `CaptureExclusionService`，再评估是否拆 `qingying_window`。

## 3. 目标依赖方向

```text
Application（组合、消息泵、退出顺序）
  ├──> CaptureWorkflow（多步流程编排）
  ├──> ActionDispatcher（单步动作）
  └──> 具体服务与生命周期对象

CaptureWorkflow
  ├──> SelectionOverlay / AnnotationOverlay / PinWindow 等 UI
  └──> Capture / Export / LongShot / Result 服务

UI 与服务
  └──> 中立协议 / Image / Action / Domain 类型
```

Workflow 可以依赖具体服务进行编排，但具体功能模块不得反向依赖 Workflow。特别是：

- PinManager 不持有 Workflow 回调；保存对话框由上层提供独立的结果动作服务；
- Overlay 公共头只暴露选区和 UI 意图；纯逻辑模块不 include `selection_overlay.hpp`；
- AnnotationHost 通过窄接口调用 Chrome、InlineText、StrokePopup、ColorPicker 和 Paint；
- Worker 只向受控的 UI 消息通道投递事件，不能把裸指针生命周期散落在多个窗口过程中。

## 4. 分阶段实施顺序

### 阶段 0：冻结契约并补回归测试

先不改变公开功能，补齐以下测试：

- Capture 失败时保留上一张有效结果；
- Save / Copy / Pin 均能明确选择“当前结果”或指定结果；
- Overlay 关闭、Workflow shutdown、worker join 后没有未消费 payload；
- Annotation 取消不覆盖 Session，确认只提交一次。

完成标准：测试能够稳定描述当前失败语义和退出语义，后续重构不再依赖人工猜测。

### 阶段 1：拆结果流，解除 Pin 回调闭环

引入最小的 `ResultStore` / `ResultActionService`，将 Copy、Save、Pin 的输入从“隐式读取 Session”改为明确的结果对象或 result id。

迁移顺序：

1. Capture 成功后再写入当前结果；失败不清空旧结果；
2. Workflow 的保存对话框移入独立的 Save flow；
3. PinManager 只接收 Image 和局部 UI 命令，不回调 Workflow；
4. GUI、Handler、PinWindow 的结果动作统一到一个服务。

完成标准：依赖图中不再出现 `PinManager → CaptureWorkflow`，Save 不再有三套实现语义。

### 阶段 2：收口窗口和消息所有权

统一 SelectionOverlay、AnnotationOverlay 和 LongShotController 的消息协议：

- `GWLP_USERDATA` 只保存观察指针，不承担删除职责；
- Host / Overlay 的唯一所有者始终是 `unique_ptr`；
- `PostMessage` 成功后的 payload 有明确 owner；
- `WM_DESTROY`、`WM_NCDESTROY` 和 `shutdown` 都能 drain 未消费消息；
- worker 停止并 join 后，才销毁窗口和卸载插件。

完成标准：源码中不再依靠 `release()` + WndProc 裸 `delete` 传递窗口状态；退出、创建失败和窗口提前销毁均有测试覆盖。

### 阶段 3：真正拆 AnnotationEditorHost

保持 `AnnotationOverlay` 的公开 API 不变，将 Host 收敛为窗口生命周期和消息分发器：

```text
AnnotationOverlay
  └── AnnotationEditorHost
        ├── AnnotationEditorChrome
        ├── AnnotationInlineText
        ├── AnnotationStrokePopup
        ├── AnnotationColorPicker
        ├── AnnotationEditorPaint
        └── AnnotationEditorSession / InteractionController
```

组件只能通过窄接口读写所需状态；Paint 只读快照，不修改 Controller 或提交文档；Chrome、InlineText 和弹窗不得依赖 Dispatcher、Export、Capture 或 Pin。

完成标准：Host 不再暴露几十个跨文件自由函数和全部可变字段；`AnnotationOverlay` 持有 Host 的唯一 `unique_ptr`。

### 阶段 4：抽中立 Selection / Result / Coordinate 协议

建议新增或重命名为：

```text
ScreenPhysicalRect
OverlayClientRect
ImagePixelRect
SelectionIntent
AnnotationFinishResult
LongShotControl
```

`SelectionResult` 不再同时承载基础选区、标注图和所有结果动作。`SelectionAction` 与 `ActionType` 可以保留，但只能在 Workflow 中完成一次显式转换。

完成标准：SelectionController、MaskRenderer 和纯像素测试不需要 include Overlay 外观头；跨模块矩形的坐标空间在类型或接口名称中可见。

### 阶段 5：类型化 Action，准备 F8/F9

将 `ActionRequest` 改成命名 payload 或 `std::variant`，至少覆盖：

```text
StatusRequest
CaptureRegionRequest
CaptureWindowRequest
CropCenterRequest
SaveRequest
PinRequest
```

外部异步入口另加 request id、operation id、取消、超时、schema validation，以及“当前结果 / 指定结果”的选择。MCP 不直接持有 Session 指针。

完成标准：无效字段组合不能靠调用方记忆 `ActionType` 才避免；`LongShotRegion` 是否作为外部 Action 暴露要在异步契约确定后再决定。

### 阶段 6：收窄编译依赖和平台基础设施

最后处理：

- `Application::Impl` 隐藏具体服务，降低公共头传播；
- 建立独立的 App Handler library，测试不直接编译生产 cpp；
- 拆分 Toolbar Model 与 GDI 绘制后端；
- 明确 AnnotationRenderer 的 Windows 文本绘制依赖；
- 只有出现第二个真实消费者时才建立 `qingying_window`。

## 5. 不应做的事情

- 不重写 LongShot 插件 ABI，不把应用识别逻辑放回 LongShotEngine；
- 不为了目录整齐提前拆 `qingying_window`；
- 不用 `shared_ptr` 掩盖 HWND、worker 或插件的所有权；
- 不把所有 GUI 局部命令机械塞入 ActionDispatcher；
- 不在一次提交中同时重构 Annotation、消息循环、F8/F9 和插件协议。

## 6. 完成判断

当以下条件全部满足时，认为本轮解耦完成：

1. Workflow 不再被 PinManager 反向回调；
2. Capture 失败不会清空旧结果，结果动作使用明确上下文；
3. Overlay / Annotation Host 和跨线程 payload 的所有权可从代码直接追踪；
4. Selection、Annotation、LongShot 的公共协议不再互相携带无关数据；
5. F8/F9 不需要继续膨胀 `ActionRequest`；
6. 关键 UI 生命周期、退出和混合 DPI 路径有可重复测试。

涉及文件：

建议新增 `ResultId`、`ResultSnapshot`、`ResultStore` 和 `ResultActionService`。`ResultStore` 至少提供以下语义：

```text
publish(Image)              成功捕获后发布新结果并生成 result_id

```

迁移顺序：

### 7.3 阶段 2：统一 HWND 与跨线程消息所有权

涉及文件：

- `include/qingying/app/app_messages.hpp`
- `src/overlay/selection_overlay.cpp`
- `src/app/longshot_controller.cpp`
- `src/annotate/annotation_overlay.cpp`
- `tests/selection_overlay_test.cpp`
- `tests/longshot_controller_test.cpp`

实施步骤：

1. 将消息编号和消息负载类型集中管理，避免 Overlay 内部消息与 Application 消息各自维护同一组 `WM_APP` 偏移。
2. 新增内部 `UiMessageChannel` 或等价的 pending queue。worker 只向 queue 写入事件，`PostMessage` 只传 token，不传裸指针。
3. 消息投递成功后由 queue 持有 payload；消息消费时按 token 取出并销毁；投递失败、窗口销毁和应用退出时统一 `drain()`。
4. `GWLP_USERDATA` 只保存非拥有型观察指针；窗口状态由明确的 `unique_ptr` 所有者持有。
5. 固定退出顺序：停止 worker → `join()` → drain UI 事件 → 关闭 Overlay → 销毁 Controller → 卸载插件。

阶段验收：删除 `release()` 加 WndProc 裸 `delete` 的传递路径；覆盖创建失败、窗口先销毁、消息未消费和重复退出场景。

阶段验收：Host 不再暴露几十个跨文件自由函数和全部可变字段；取消和确认仍然只产生一次 `AnnotationFinishResult`。

## 8. 每次提交的固定验收流程

每个阶段完成后必须在仓库根目录执行：

```powershell
.\build.bat Release test
```

该脚本会完成 Release 配置、编译和 CTest。不要用手工 `cmake --build` 结果替代阶段验收。失败时先区分：

1. 环境权限或工具链问题；
2. CMake/编译错误；
3. 测试回归；
4. 测试发现但与本阶段无关的既有问题。

行为验收至少覆盖：普通截图、标注确认/取消、长截图暂停/停止、Copy、Save、Pin、窗口提前关闭和应用退出。

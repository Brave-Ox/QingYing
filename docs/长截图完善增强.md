# 长截图完善增强：目标、效果与 Commit 拆分

> 更新日期：2026-09-18。
> 状态：待实施方案；本文中的新增接口、状态和阈值策略是设计目标，不代表已实现。
> 核心目标：未知应用也能尝试，失败后还能继续操作，已可靠截取的内容不会白费。
> 本轮范围：优先完善自动长截图，不实现手动滚轮拼接或自动/手动模式切换。

## 1. 当前基线与问题

当前实现不是完全通用的滚动截图，而是应用 profile 驱动的固定区域捕获与图像拼接：

1. 用户框选，记录目标窗口和屏幕物理坐标矩形。
2. `LongShotEngine` 通过 profile registry 解析滚动目标；目前内置 Notepad、Explorer、Chromium 三类 profile DLL。这里是适配类别，不等于只支持三个可执行程序。
3. 捕获首帧，发送向下滚动输入，等待内容稳定，再捕获相同矩形。
4. `ImageStitcher` 检测累计图像底部与新帧顶部的重叠，追加非重叠部分。
5. 遇到到达底部、无新增内容、用户停止或安全限制时结束。

已具备的能力应保留：异步 worker、进度预览、暂停/继续/停止、取消与关闭预算、profile DLL、滚动状态查询、帧重试，以及输出高度 30000 像素等资源限制。帧数和滚轮输入次数不再单独设硬上限。

当前主要问题：

- profile 未命中直接返回 `kLongShotUnsupported`；没有通用尝试路径。
- 拼接中途失败直接返回错误，局部变量中的可靠累计图像没有作为最终结果交付。
- `CaptureWorkflow` 只在 `completion_result.ok` 时发布结果；失败进入 `pending_overlay_error`，最终通过 `MessageBoxW` 提示。
- 无法区分“没有滚动”“未到确定底部但没有新增内容”“部分完成”“达到限制”“真正无法捕获”。
- 剪贴板复制失败也会让已生成结果退出可用状态；结果生成和后续导出需要解耦。
- 现有拼接主要依赖同列像素重叠匹配；固定头尾、重复列表、动画和较大滚动步长容易影响匹配。

核对入口：

- [longshot_engine.cpp](../src/longshot/longshot_engine.cpp)：profile 校验、捕获循环、失败返回。
- [image_stitcher.cpp](../src/longshot/image_stitcher.cpp)：重叠检测和追加。
- [longshot_controller.cpp](../src/app/longshot_controller.cpp)：worker 和跨线程交付。
- [capture_workflow.cpp](../src/app/capture_workflow.cpp)：结果发布、复制、失败提示。
- [overlay_phase.hpp](../include/qingying/overlay/overlay_phase.hpp)：现有交互状态。

## 2. 参考 ShareX 的范围

以 ShareX 为主要产品与流程参考，不整体移植其实现：

- 参考它的通用滚动、连续采集和增量拼接方式。其源码包含滚轮、方向键、PageDown 和滚动消息等输入策略；不是依赖每个应用都提供专属插件。[源码](https://github.com/ShareX/ShareX/blob/develop/ShareX.ScreenCaptureLib/ScrollingCaptureManager.cs)
- 参考它区分成功、部分成功和失败的状态反馈，而不是把所有异常都当作需要退出的错误。[官方说明](https://getsharex.com/docs/scrolling-screenshot)
- 不照搬“无法精确匹配时使用最佳可用匹配”的产品取舍。轻映优先保证内容正确：低可信度帧不追加，保留已验证部分，并明确提示未完整截取。

注意：ShareX 的滚动消息发送对象是所选窗口句柄，不能据此认定它总是向顶层窗口或最深子窗口发送。本文后续的安全边界、交互文案和提交拆分是轻映自身的设计，不是对 ShareX 行为的复述。

具体源码版本、算法推导、采用边界和 commit 对照见第 9 节。实现时以固定提交的代码为准，不把 ShareX 提供的可选输入方式理解成自动回退链。

## 3. 详细目标及用户可见效果

### 3.1 从“应用准入”改为“能力优先、通用回退”

- 已知 profile 优先使用，保留其准确定位和到达底部检测能力。
- profile 未命中时进入通用目标解析与小步试滚，不直接显示“不支持”。
- profile 明确表示未发送输入、目标仍有效时，允许尝试通用策略；输入是否生效不确定时先观察画面，不盲目重复滚动。
- 通用模式无法自动滚动时，提供重试、调整选区或保留已有截图，不转入手动滚轮拼接。

预期效果：用户在普通编辑器、文档阅读器、自绘列表等非内置适配应用中，也能尝试长截图。判断依据从“应用名字是否认识”变为“能否安全滚动且可靠拼接”。

不承诺支持任意软件。受保护画面、权限隔离、持续动画、重排内容、没有重叠的跳转等仍可能无法完成。

### 3.2 失败可恢复，不强制结束截图

- 普通兼容性问题通过选区旁状态条或结果区提示，不弹阻塞错误框。
- 未发现滚动：提供“重试”“调整选区”“保留普通截图”。
- 中途匹配失败：保留可靠结果，提供“保存已有内容”“复制”“重新开始”。
- 调整选区意味着新会话，不将不同矩形的新帧拼到旧结果上。
- 重新开始默认从目标当前滚动位置开始，不静默发送 Home 或恢复滚动位置。

预期效果：一次失败不再让用户重新启动整个截图流程；状态说明问题，并给出下一步操作。

### 3.3 部分结果是一等结果

- 至少一帧可靠图像存在时，允许形成可预览的候选结果；只有首帧时明确标注“普通截图，未形成长图”。
- 已追加多帧后失败，只交付已确认的拼接部分，不包含失败帧。
- 部分结果不自动覆盖剪贴板；由用户明确选择复制或保存。
- 正常完成可保持既有自动复制习惯；复制失败仅提示重试，不撤销已发布图像。
- “停止并保留”与“取消并放弃”必须不同；取消和应用退出不自动导出或发布结果。

预期效果：截取到一半失败不再前功尽弃，也不会把不完整结果伪装成完整成功。

### 3.4 优先提高自动滚动与采集的稳定性

- 由程序完成目标定位、小步滚动、等待稳定、捕获与拼接，用户只需框选、启动并按需暂停或停止。
- 根据已验证的实际位移与剩余重叠调整后续滚动节奏；重叠偏少时减小后续步长，重绘较慢时延长有界等待。
- 优先完善目标命中、稳定帧判断、重试和拼接证据，不靠增加手动模式绕过自动流程问题。
- 暂停期间不追加帧；恢复时先验证与上一可靠帧的连续性。
- 向上滚动、横向移动、缩放或跳页造成不连续时暂停并提示，不直接追加。

预期效果：减少滚错控件、采到过渡帧、滚动过大和过早判断到底的问题。自动输入确实不兼容时明确提示，保留可靠结果，不承诺一定完成。

### 3.5 正确性优先于输出长度

- 保留重叠硬性要求，不通过关闭 `require_overlap` 来提高表面成功率。
- 不把“输入 API 返回成功”当作内容已滚动，也不把“画面变化”直接当作有效向下位移。
- 重复文本、空白和固定侧栏不能单独作为可靠拼接证据。
- 无新增内容只能报告“未检测到新增内容”；只有可信滚动状态等证据才显示“已到底部”。
- 保留输出高度限制，并补充总耗时、内存及重试预算；不按帧数或滚轮输入次数提前截断。

## 4. 设计约束与结果语义

### 4.1 分层职责

- `LongShotEngine`：捕获、稳定性检测、重叠决策、可靠结果、停止原因；不弹窗、不操作剪贴板。
- profile / 通用滚动驱动：目标解析、输入和可选滚动状态查询；不能向无关窗口广播输入。
- `LongShotController`：会话编号、worker、暂停/停止/取消、进度与完成交付。
- `CaptureWorkflow`：结果发布、恢复动作、复制/保存/Pin 接入。
- Overlay / Toolbar：非阻塞反馈和用户命令，不承载拼接算法。

优先添加内部 C++ 类型和适配层，不为本功能直接修改现有插件 C ABI，也不将长截图专属类型塞入通用 action 核心。若后续确需扩展 ABI，应单独版本化并测试旧 DLL。

### 4.2 建议采用“结果质量 + 停止原因”两维模型

不要继续只靠一个 `ok` 表达全部状态。建议内部完成对象包含：

- 结果质量：`None`、`SingleFrame`、`VerifiedComposite`。
- 停止原因：`ReachedBottom`、`NoProgress`、`UserStopped`、`LimitReached`、`MatchFailed`、`InputUnavailable`、`TargetInvalid`、`CaptureFailed`、`Cancelled`。
- 可靠图像、已接受帧数、输出尺寸、使用的策略、失败阶段，以及是否存在可导出结果。
- “完整完成”“部分完成”的展示由原因和证据共同决定；不能仅凭帧数判断完整性。

停止原因与图像是否可用相互独立。例如捕获失败可能仍有可靠长图，取消则即使内部有图也不得自动发布。具体类型名可在实现时调整，但这些语义必须有测试。

### 4.3 通用输入的安全规则

- 根据选区内锚点查找目标 owner 范围内的实际命中窗口；框选矩形不等于 HWND，也不一定对应独立控件。
- 排除自身 Overlay、工具条和预览窗。多窗格选区无法确定目标时请求调整，不遍历所有子窗口试滚。
- 每次输入前复核窗口、前台归属和目标几何；目标失效、移动或焦点切换时暂停。
- 初期只实现一种有界滚轮策略；消息式输入必须有超时，模拟输入必须检查目标和焦点。不强制点击、不自动提权、不向无关前台发送按键。
- 方向键、PageDown、`WM_VSCROLL` 是后续可选策略，不在无反馈时无序轮番发送。
- 自动移动鼠标若确有必要，须明确交互；用户已移动鼠标后不强行恢复旧位置。

### 4.4 重试与拼接规则

- 帧不稳定或匹配失败时，先在当前位置等待并重采，不能立即再次向下滚动。
- 已经滚过头且失去重叠时，减小“下一次”的步长无法补回缺失内容；应保留结果并结束，允许用户重新开始，不尝试手动回退后接续旧长图。
- 后续小步滚动、较长等待仅用于仍有连续性证据的状态。
- 匹配输出应逐步扩展为位移、有效匹配范围、分数/歧义信息及拒绝原因；分数不作为未经校准的概率。
- 忽略固定头尾或侧边进行匹配，不等于可以静默删除它们。输出裁切策略必须独立定义、预览并测试。
- 输入图像在追加成功前保持不变；失败不损坏上一份可靠累计结果。

### 9.2 目标选择与滚动输入：参考 C06、C07

**源码事实：** `SelectWindowAsync` 从选区结果取得矩形和 `WindowInfo`，启动时激活该窗口。manager 本身没有按应用名选择 profile 的准入表。滚动方式由一个 `ScrollMethod` 配置决定，不是在失败后依次试遍所有方式。[目标和循环源码][sx-manager]

- `MouseWheel`：滚轮增量为 `-120 × ScrollAmount`；`InputHelpers.SendMouseWheel` 构造鼠标输入，最终调用 `SendInput`，这条路径不向所选 HWND 定向发送 `WM_MOUSEWHEEL`。[滚轮封装][sx-input]、[输入队列][sx-input-manager]
- `DownArrow`：按配置次数发送向下键。
- `PageDown`：发送一次翻页键。
- `ScrollMessage`：按配置次数向 `selectedWindow.Handle` 发送 `WM_VSCROLL / SB_LINEDOWN`。[策略分支][sx-manager]

不能据此推断它会自动寻找最深可滚动子窗口，也不能把系统滚轮输入等同于对框选区域的精确命中。该 manager 的滚轮调用没有传入选区锚点，也没有使用返回值证明内容已经移动。

**轻映采用：** 借鉴“不依赖应用白名单也可以试滚”，但保留现有 profile 优先级。把目标解析、输入派发和图像进展验证分开；C06 负责可操作目标，C07 负责有界输入和验证。

轻映已有 [win32_scroll_helpers.cpp](../src/longshot/win32_scroll_helpers.cpp) 使用 `SendMessageTimeoutW(WM_MOUSEWHEEL)`，超时后还会 `PostMessageW`。通用回退不能在这个 helper 外简单再套一次 `SendInput`：前一次超时或排队不代表输入一定未处理，叠加可能造成双重滚动。这是根据本地发送路径推导的风险，需增加“迟到处理”测试。

实现约束：

1. 内部区分“确定未发送”“已发送待观察”“派发状态不确定”，不要仅用一个 bool 决定是否换策略。
2. 已发送或状态不确定时，只在当前位置等待并采集，不立即补发另一种输入。
3. C07 初版只启用一种明确的通用滚轮路径。选择消息式或 `SendInput` 时记录兼容性依据；若采用后者，必须完成锚点、前台和遮罩穿透验证。
4. `SendInput` 的注入成功、消息发送成功、目标真正滚动是三件不同的事，最终必须由滚动状态或图像证据确认。
5. 方向键、翻页和滚动消息保留为未来可选扩展，不因此扩大本轮自动回退范围。

### 9.3 自动采集循环、等待与终止：参考 C08

**源码事实：** ShareX 的实际循环次序值得注意：先抓取当前帧，与上一原始帧判同；若不同，先发出下一次滚动，再异步拼接刚抓到的帧，最后补足滚动间隔。拼接耗时从 `ScrollDelay` 中扣除。这样滚动重绘和拼接计算可以部分重叠，但不是稳定帧检测。[`StartCapture`][sx-manager]

`CompareImages` 检查两张同尺寸图像的 32 位像素内存是否完全一致，不带小面积动态容忍。[整帧比较][sx-images]

manager 虽定义了读取滚动条的 `IsScrollReachedBottom`，但该版本 `StartCapture` 没有调用它；不能把这个未接入循环的函数描述成主要到达底部机制。主循环直接使用相邻原始截图相等、用户停止和拼接失败等条件退出。[停止逻辑][sx-manager]

**风险推导：** 固定时间后采样可能抓到延迟刷新或滚动过渡帧；精确判同容易受光标、动画影响。先滚动再验证当前帧，也可能在发现拼接失败之前又向下移动了一步。

**轻映采用：** 不照搬上述时序。首帧确认后，每轮执行：复核目标 → 发送一次输入 → 有界等待并重采 → 检查稳定性和重叠 → 提交可靠追加 → 再决定是否发送下一次输入。

- 稳定性比较：同一次输入后的连续候选帧之间比较，回答“是否还在变化”。
- 连续性比较：候选帧与上一可靠帧/累计尾部比较，回答“是否能接上”。
- 到底判断：优先使用可信滚动状态；只有画面无进展时报告 `NoProgress`，不冒充 `ReachedBottom`。
- 将等待、稳定观测次数、重采次数和总 deadline 分开记录。不能无限等待动画完全停止，也不能只因局部画面稳定就接受整帧。
- 参数从可控帧源与真实应用样本校准，300 ms 和两格滚轮只作为对照基线，不直接作为产品保证。

### 9.4 结果生命周期与“部分成功”：参考 C01—C05

**源码事实：** 首帧作为初始结果；后续只有 `CombineImages` 返回新图才替换旧 `Result`。退出时 `Reset(true)` 清理临时帧但保留结果。Service 分别暴露结果图和状态，因此“结束状态”与“手里有没有图”并非同一个字段。[manager][sx-manager]、[service][sx-service]

ShareX 的 `PartiallySuccessful` 还具有特定含义：当前帧没有匹配时沿用历史匹配接缝继续拼接。这不是轻映计划中的“停止追加，只保留此前可靠部分”。该标记一旦出现，后续普通成功匹配不会立即把它清回成功；随后真正失败仍可将状态设为失败。[拼接结果处理][sx-manager]

**轻映采用：** 参考可靠图像独立持有、结束时不无条件丢弃的生命周期；不用一一映射它的状态枚举。采用第 4.2 节的质量和停止原因模型，C03 传递它，C04/C05 决定非阻塞提示及发布动作。

这里没有从 ShareX 推导“所有失败都不弹窗”或“失败图都会自动导出”。轻映的重试按钮、结果待确认、部分结果不自动复制均是本项目明确选择。

### 9.5 ShareX 拼接算法逐步解释：参考 C09、C10

以下是对 [`CombineImages`][sx-manager] 的数学化说明，不是建议直接翻译的代码。它属于**固定横向位置的像素行匹配与裁切追加**，该函数没有 ORB、RANSAC、OCR 或归一化互相关模板匹配。

#### 9.5.1 输入与搜索区域

用 `A` 表示累计长图，`B` 表示新截图；同宽为 `W`，新截图高度为 `H`，累计高度为 `HA`。首帧直接成为累计图。后续匹配主要在累计图尾部一个视口附近进行。

左右各排除宽度 `S = min(max(50, floor(W/20)), floor(W/3))`，只比较中间 `W - 2S` 像素宽的行。排除只影响匹配，最终输出仍使用整幅宽度，并不是裁掉左右侧栏。

#### 9.5.2 底部排除量

初始底部量 `b0 = max(50, floor(H/10))`，上限为 `floor(H/3)`。启用 `AutoIgnoreBottomEdge` 时，从两图各自底部向上比较同位置行，遇到第一条不同的行，将其距离加到基础排除量，再结合历史底部排除量，最后应用上限。

两个容易误解的点：

- 这是底部启发式，不是通用固定头尾识别；此函数没有对称的顶部检测流程。
- 关闭 `AutoIgnoreBottomEdge` 仍存在基础底部排除量，不代表 `b = 0`。不能把选项名直接解释为“关闭一切底部裁切”。

#### 9.5.3 连续行匹配与候选选择

固定累计图锚点行 `a = HA - b - 1`。依次枚举新截图候选行 `j`，从 `H-1` 向 0 搜索；对每个候选同时向上比较 `A[a-k]` 与 `B[j-k]` 的中央行段。

每行使用 `memcmp`，行段全部字节相等才算通过；第一次不等就结束这个候选。保存连续相等行数最大的候选，其 `j` 作为 `matchIndex`。

源码中的 `matchLimit = floor(H/2)` 是匹配计数和搜索的提前终止上限，**不是“至少重叠半屏才允许拼接”**。接受分支检查匹配行数大于零且新帧接缝后还有行；它没有轻映计划中的纹理充足性、次优候选差距或多区域一致性门槛。

风险推导：空白和重复列表可能产生多个貌似正确的接缝；精确逐行比较又可能因微小重绘差异拒绝正确位置。这也是不能简单用该实现替换轻映现有容差匹配的原因。

#### 9.5.4 拼接公式与例子

设找到的接缝行是 `j`，则取新截图的 `j+1` 行至末尾，行数为 `T = H-j-1`；先删除累计图底部的 `b` 行，再追加这 `T` 行：

- 新高度：`HA' = HA - b + T`。
- 净增长：`D = T - b`，不是 `T`。
- 累计保留区：`A[0, HA-b)`。
- 新帧追加区：`B[j+1, H)`。

例如 `HA=2000`、`H=1000`、`b=100`、`j=599`，追加 400 行、替换旧底部 100 行，最终高度 2300，净增长 300。可将这种索引算例做成独立测试，重点检查是否重复/漏掉接缝行。

ShareX 输出时复制完整宽度；底部旧画面由新帧底部替换。不能把 `matchCount` 直接当作重叠高度，也不能将此公式原样套到轻映目前 `HA + H - overlap_rows` 的无底部替换模型。

#### 9.5.5 历史接缝回退

当前匹配计数为零且历史存在匹配时，源码复用历史的计数、接缝索引和底部排除量，并标记部分成功。它相当于假设此前接缝仍适用，而不是重新证实当前帧连续性。

**轻映不采用这种追加回退。** 历史位移只能用于搜索排序和下一次步长预测；当前帧没有足够证据时必须拒绝追加。重采仍失败则交付此前可靠内容。

### 9.6 从当前 ImageStitcher 演进，而非整体替换

本地 [image_stitcher.cpp](../src/longshot/image_stitcher.cpp) 目前枚举重叠高度，优先最大的可通过候选，使用采样点、逐通道容差和最低匹配比例判断，再追加新图非重叠行。它已经具有抗少量像素变化能力；ShareX 的精确行比较不应被当作天然更高级的算法。

建议的落地过程属于轻映自身设计：

1. **C09 先增加证据，不先改裁切。** 候选返回位移、重叠范围、有效样本量、各匹配带得分、次优候选和拒绝原因。旧的无固定边缘场景保持输出一致。
2. **独立保存上一可靠原始视口。** 它用于位移和固定边缘分析；累计长图用于输出，不将反复裁切后的累计尾部误当作完整原始视口。
3. **多区域互证。** 在正文内选择多个有纹理的列带，要求同一位移有足够空间覆盖；整块固定侧栏、空白或单行文本不能独立决定接缝。
4. **预测只影响速度。** 可以优先搜索历史位移附近，但局部没找到时在预算内扩大搜索；不能将预测直接当作结果。重复内容出现近似等价候选时拒绝。
5. **检测与追加分离。** 生成不可变的接缝/裁切计划，验证所有范围、净增长和输出预算后分配新图，成功才提交替换。避免 `findOverlap` 后 `append` 再做一次独立搜索产生不同决策。
6. **C10 再加入边缘模型。** 明确识别的固定顶部只取首帧，固定底部由最后可靠帧提供；顶部、正文、底部的来源与范围分别记录。普通路径不能因为接入边缘模型而默认删除任意正文。

建议用于实现评审的不变量：

- 同一个追加计划只能用于生成它的那组帧和坐标版本；改变选区或边缘配置后作废。
- 正常新增内容要求净增长大于零；零位移归无进展，负位移或方向不明不能追加。
- 排除后必须仍有足够匹配区域；小选区不能因固定的 50 像素参数变成无效或越界。
- 每个源矩形均在图像范围内，乘法/加法和字节数先做溢出与预算检查。
- 固定边缘失败回退到调区或停止，不通过扩大排除区直到“碰巧匹配”来追求成功。

这条路线不要求先引入 OpenCV；若后续像素方法在实际样本上确有瓶颈，再单独评估梯度/特征法，不能把那类算法写成当前 ShareX 已采用的实现。

- **C09**：借鉴中央区域和尾部搜索以控制计算量，保留本地像素容差并增加歧义拒绝；不能把半屏提前终止条件当作可靠性阈值。
- **C10**：借鉴底部替换的输出思路，但使用明确边缘范围和接缝计划；固定顶部处理是轻映的新增设计。
- **C11**：验证资源上限、像素连续性和实际自动滚动兼容性；此 manager 的循环不能替代轻映自己的输出高度、内存、重试和时间限制。

### 9.8 从源码差异补充的回归样例

以下纳入对应 commit 测试，而不是新增手动模式或扩大功能范围：

- **迟到输入**：模拟同步派发超时、原消息稍后执行，确认不会再注入一份滚轮导致跨屏缺口（C07）。

- **历史步长变化**：前次有效位移 200 像素，下次 80 像素或无匹配；不得沿用前次接缝截断正文（C09）。
- **周期重复内容**：至少两个候选都高分时拒绝；添加唯一行号后能找到正确位移（C09）。
- **微小动态**：少量抗锯齿、光标变化可容忍，但动态遮挡占据主要正文时不能依靠空白带通过（C09）。

- **窄小区域**：边缘排除后没有足够信息时明确拒绝，不能发生负宽度、越界或空匹配通过（C09/C10）。

## 10. 借鉴 ShareX 放宽匹配边界的后续实施步骤

本节是 C01—C11 完成后的后续改造计划。目标是吸收 ShareX 在匹配区域和连续采集方面的实用经验，降低动态页面、重复列表、留白和固定底栏造成的提前终止，同时继续坚持“当前帧没有证据就不追加”。本节不采用 ShareX 的精确逐行 `memcmp`，也不采用匹配失败后复用历史接缝的 `PartiallySuccessful` 回退。

### 10.1 最终采用边界

保留现有基础匹配能力：

- `channel_tolerance = 2`，允许抗锯齿和轻微重绘产生的小幅通道差异。
- `minimum_match_per_mille = 960`，当前候选的全局有效采样点匹配率不得低于 96%。
- `min_overlap_rows = 16`，不接受过短重叠。
- 当前帧必须独立产生有效候选，历史位移只能参与搜索排序和同分候选排序，不能直接生成接缝。
- 追加前继续检查同宽、坐标范围、向下位移、净增长、输出高度和工作内存；只有完整计划通过后才替换上一可靠结果。

借鉴 ShareX 并作适配：

- 匹配时同时排除左右边缘，减少滚动条、窗口阴影、悬浮控件和固定侧边内容干扰；排除仅影响匹配，输出仍保留完整宽度。
- 自动识别有跨滚动位置证据的固定底部；匹配时排除，提交时用最新可靠帧的底部替换上一帧底部，不能直接裁掉最终结果。
- `NoCandidate`、`InsufficientTexture`、`InconsistentRegions` 和 `AmbiguousCandidates` 默认视为本次采样“不确定”，在同一次滚动位置继续有界重采，不因单次观察立即结束长截图。
- 纹理、多区域一致性、最优/次优差距从“一票否决”降为候选评分、诊断和重采依据；96% 全局匹配及当前帧真实证据仍是硬门槛。
- 连续稳定判定允许小范围位移抖动，不再要求两次重叠行数逐行完全相同。

明确不采用：

- 当前帧匹配失败后，不得复用上一次的重叠高度、接缝索引或底部排除量进行追加。
- 不把 ShareX 的 `matchLimit = H / 2` 误设为最低重叠比例。
- 不为追求成功率持续扩大左右或底部排除区；排除后信息不足时停止并保留上一可靠结果。
- 不把固定等待 300 ms 当作稳定保证；仍使用有界观察、可取消等待和总 deadline。

### 10.2 调整后的单轮状态流

每次滚轮输入只对应一个采样轮次，建议按以下次序执行：

1. 复核 owner、滚动目标、选区坐标和前台归属；不满足时不发送输入。
2. 发送一次滚动输入并记录“已发送待观察”，本轮重采期间不得补发第二次滚轮。
3. 在当前位置按退避间隔采样，分别计算左右排除、已确认底部排除和当前帧重叠证据。
4. 无有效候选、纹理不足、区域不一致或候选接近时记录不确定原因并继续重采；非法尺寸、目标变化、取消和预算溢出仍立即停止。
5. 将通过 96% 基础门槛的当前候选按位移聚类；连续两次候选位移落在允许误差内时，选择该簇内得分最高且净增长有效的当前接缝。
6. 生成一次性追加计划，完成范围和预算检查后提交；提交成功后才更新上一可靠原始视口、历史位移、底部模型、累计图和预览。
7. 本轮所有采样均不确定时，以 `MatchFailed` 或 `LimitReached` 停止并交付此前可靠结果；不更新任何接缝历史，也不再发送滚轮。

建议继续区分三类判定，避免所有失败都落入 `LostOverlap`：

- `Accepted`：当前帧证据充分，可以生成追加计划。
- `Retryable`：当前采样不确定，仍可在当前位置重采。
- `Fatal`：输入图像非法、宽度变化、排除区越界、目标失效或资源计算失败，继续重采没有意义。

### 10.3 R01 — `fix(longshot): retry inconclusive overlap observations`

目的：先解决一次临时失配就终止的问题，不同时改变像素阈值和裁切公式。

实现：

- 将 `VisualFrameDecision::LostOverlap` 拆成可重采和不可恢复两类，或为观察结果增加严重级别。
- `NoCandidate`、`InsufficientTexture`、`InconsistentRegions`、`AmbiguousCandidates` 进入 `Retryable`；继续使用现有 `max_frame_recaptures` 和总时限。
- `InvalidImage`、`WidthMismatch`、`InvalidEdgeExclusion` 进入 `Fatal`。
- 同一位置预算耗尽后返回最后一个稳定拒绝原因，同时保留累计图、输入次数、重采次数和失败帧号。
- 不修改 `channel_tolerance = 2`、96% 全局门槛和当前拼接输出公式。

测试与验收：

- 第一张候选无重叠、第二和第三张候选稳定时能够继续拼接。
- 连续歧义直到重采预算耗尽时只发送一次滚轮，并保留上一可靠结果。
- 非法尺寸和目标变化仍立即停止，不消耗无意义重采。
- 动态页面不再因单个过渡帧直接退回首帧。

实施结果（2026-09-20）：

- 已将视觉观察结果拆分为 `RetryableOverlap` 和 `FatalOverlap`。`NoCandidate`、`InsufficientTexture`、`InconsistentRegions`、`AmbiguousCandidates` 以及滚动过渡期的位移越界会在当前位置继续有界重采；`InvalidImage`、`WidthMismatch`、`InvalidEdgeExclusion` 立即结束。
- 可重采拒绝会清除此前的连续稳定计数，恢复后仍需连续两次得到相同有效位移，避免把拒绝前后的离散样本拼成一次稳定证据。
- 引擎在重采期间不再次发送滚轮；预算耗尽时保留最后一个重叠拒绝原因、上一可靠累计图和 `FrameRecaptures` 预算诊断。
- 新增“首个候选失配后恢复”“非法图像立即失败”“不确定观察打断稳定计数”回归，并同步多帧中断和歧义样例的重采计数。
- `./build.bat Release test` 通过，共 `1049/1049` 项，耗时 `47.36` 秒。R01 未修改通道容差、96% 全局匹配率、最少重叠行数和拼接裁切公式。

### 10.4 R02 — `feat(stitcher): exclude bounded side regions from matching`

目的：借鉴 ShareX 的中央区域匹配，减少左右固定内容和滚动条对重叠判断的影响。

实现：

- 新增纯函数根据选区宽度计算对称侧边排除建议值，以 ShareX 的 `min(max(50, floor(W/20)), floor(W/3))` 作为对照基线。
- 轻映必须再受“最小可用中央宽度”约束；窄选区无法保留足够中央样本时缩小排除量，而不是固定减去 50 像素。
- 将现有右侧 12 像素特殊排除并入统一策略，最终左右范围和有效采样宽度写入 `OverlapEvidence`。
- 排除只作用于候选评分；`append`、预览和导出继续使用用户框选的完整宽度。
- 排除策略以独立配置对象传入 `ImageStitcher`，便于样本校准和回滚，不散落魔法数字。

测试与验收：

- 左侧固定导航栏、右侧滚动条或两侧同时变化时仍能找到正文位移。
- 输出宽度和左右像素与原始选区一致。
- 窄区域不会出现负宽度、零样本、越界或仅靠一条空白带通过。
- 无侧边干扰的历史样例保持相同接缝和输出像素。

实施结果（2026-09-20）：

- 已新增独立的 `SideExclusionPolicy`、`SideExclusionRange` 和纯函数 `resolveSideExclusion`。自动模式默认使用 ShareX 的 `min(max(50, W/20), W/3)` 基线，同时保证中央有效区至少 24 像素；选区不足 24 像素时自动退回不排除，而不是产生负宽度或零样本。
- 基线最小值、宽度除数、最大占比除数和最小中央宽度均保存在策略对象中，显式模式继续支持确定的左右排除，便于后续样本校准和回滚。
- 引擎和默认视觉稳定器已从“仅排除右侧 12 像素”切换为自动对称排除。最终左右排除量和中央有效宽度写入 `OverlapEvidence`，供诊断和后续验收使用。
- 排除范围只参与重叠评分；追加仍复制完整宽度。新增双侧动态干扰、窄选区、非法显式范围和无干扰输出一致性回归。
- `./build.bat Release test` 通过，共 `1054/1054` 项，耗时 `47.69` 秒。R02 未修改固定顶部/底部模型、96% 全局匹配率和拼接裁切公式。

### 10.5 R03 — `feat(stitcher): detect and replace bounded fixed bottom edges`

目的：借鉴 ShareX 的底部排除与替换思路，处理状态栏、下载栏、固定操作栏等不随正文滚动的区域。

实现：

- 使用上一可靠原始视口和本轮候选，在中央有效区域从底部向上寻找同位置稳定行；单帧或单次滚动证据不得直接确认固定底部。
- 至少跨两个成功滚动位置得到相容范围后才启用自动底部模型；未确认前底部排除为 0。
- 自动底部高度设置上限，最高不超过视口高度的三分之一；超出、抖动过大或正文证据不足时撤销本轮更新。
- 匹配正文时排除已确认底部；提交时删除累计图中上一可靠底部，追加新正文和本轮最新底部。
- 历史底部范围只能作为下一轮检测先验；当前帧无法验证时沿用上一份已经提交的完整结果，但不得拿旧范围强行拼接新帧。

测试与验收：

- 固定底栏在最终长图中只出现一次，并来自最后一张可靠帧。
- 普通正文底部、连续留白和偶然相同行不会被单轮误判为固定底栏。
- 底栏高度变化时先重采或撤销模型，不产生正文缺口。
- 中途失败后保留上一可靠底部，预览与最终结果一致。

实施结果（2026-09-20）：

- 已新增 `FixedBottomDetectionOptions`、`FixedBottomEvidence` 和纯函数 `detectFixedBottomEdge`，仅在 R02 的中央有效区域内比较上一可靠原始视口与当前候选，并继续使用通道容差 2 和 96% 行匹配率。
- 自动检测要求底部连续同位置匹配、范围不超过视口高度三分之一且包含最低水平纹理；大面积未变化画面、纯色留白和不足两行的偶然相同区域不会启用底边。
- 引擎独立保存上一可靠原始视口并计入工作内存预算。单轮检测结果只生成当前帧对的一次性拼接配置；相同高度跨两个成功滚动位置后才确认为模型。
- 已确认模型在每个新候选上重新验证。当前帧无法证明相同底边时只在当前位置有界重采，不沿用旧高度追加；预算耗尽后交付上一可靠累计图。
- 提交时复用既有固定底边裁切计划：删除累计图上一份底边，追加新正文和当前可靠底边；预览和最终输出因此只保留一份底栏。显式固定底边配置保持原行为。
- 新增有纹理底栏识别、纯色留白/整帧静止拒绝、三帧连续正文与单份底栏，以及模型确认后底栏变化不追加等回归。
- `./build.bat Release test` 通过，共 `1058/1058` 项，耗时 `48.63` 秒。R03 未引入历史接缝或历史底边强制回退。

### 10.6 R04 — `refactor(stitcher): soften secondary overlap gates`

目的：保留 96% 当前帧证据，把容易造成误拒绝的辅助门槛改为排序和诊断信息。

实现：

- 全局匹配率不低于 96%、最少重叠 16 行、净增长大于零继续作为硬门槛。
- `vertical_texture_per_mille`、行带/列带一致性和最优/次优分差继续计算并写入证据，但不再单独立即拒绝一个已达到 96% 的候选。
- 当前帧有多个合格候选时，先按当前得分排序；分数接近时优先选择最接近上一可靠位移的当前候选，再以更大重叠作为确定性排序条件。
- 历史位移只能改变搜索顺序和同分排序。当前帧不存在合格候选时结果必须为 `Retryable` 或最终失败，绝不能生成历史接缝。
- 保留拒绝原因和候选分布统计，以便真实样本发现错拼后重新提升特定门槛。

测试与验收：

- 低纹理但具有唯一 96% 当前证据的页面能够拼接。
- 少量局部动态造成某个区域分数下降时不会立即终止。
- 周期重复列表的当前候选排序可重复、结果确定；完全没有当前候选时绝不追加。
- 构造历史位移 200、当前实际位移 80 的样例，必须选择当前 80，不能复用 200。

实施结果（2026-09-20）：

- 已保留全局匹配率、重叠范围和位移范围作为候选硬门槛；引擎仍固定使用通道容差 2、全局匹配率 96% 和最少重叠 16 行。纹理充足度、行带/列带一致性与最优/次优分差不再单独拒绝已通过全局门槛的当前候选。
- `OverlapEvidence` 继续记录纹理、区域一致性、最佳/次佳得分，并新增分差及是否使用历史位移排序的诊断字段。低纹理唯一候选和局部分区不一致候选可以被接受，但诊断信息不会丢失。
- 多个当前候选默认按得分优先、重叠更大优先确定性排序；存在上一可靠位移时，只在与最高分相差不超过配置分差的当前合格候选中选择距离最近者，再以更大重叠打破同距。历史位移不会创建候选，也不会绕过 96% 当前帧证据。
- 引擎只在追加成功后更新上一可靠位移，并将该先验同时传给稳定观察和最终追加复核，保证两次检测采用相同排序条件。当前帧无候选时仍进入有界重采或最终失败，不复用历史接缝。
- 已更新低纹理、局部分区变化、周期重复内容、历史位移排序、历史位移与当前实际位移不一致、无当前候选以及整帧无进展回归；周期静止页面仍需连续三次零位移才结束为 `NoProgress`。
- `./build.bat Release test` 通过，共 `1060/1060` 项，耗时 `50.10` 秒。R04 未降低 96% 引擎门槛，未修改固定边缘裁切公式，也未引入历史接缝回退。

### 10.7 R05 — `fix(longshot): tolerate small displacement jitter when settling`

目的：避免缩放、平滑滚动、捕获时序和采样舍入造成 1—2 行波动时永远无法得到“完全相同”的稳定位置。

实现：

- 将连续位移完全相等改为有界聚类，初始建议容差为 `±2` 行，并作为命名策略参数而不是散落常量。
- 连续两个合格候选进入同一位移簇后视为稳定；提交时使用簇内得分最高候选对应的真实接缝，不对像素做平均。
- 零位移继续单独累计，连续三次才判定 `NoProgress`；零位移不能与正位移聚为一类。
- 超过容差的候选开始新簇，但只消耗本轮重采预算，不发送额外滚轮。

测试与验收：

- 位移序列 `120, 121` 可以稳定，`120, 126` 不可稳定。
- `0, 1` 不得误判为新增内容，连续三个零位移仍结束为 `NoProgress`。
- 平滑滚动先经过多个位置、最后落在 `200±2` 时只追加最终稳定候选。
- 用户暂停、停止或取消能够立即唤醒聚类等待。

实施结果（2026-09-20）：

- 已新增 `VisualFrameSettlingPolicy`，将位移容差、移动确认样本数和无进展确认样本数集中为命名策略；默认分别为 `±2` 行、连续 2 次和连续 3 次，非法的负容差或非正计数会在稳定器构造时归一化为安全值。
- 稳定器改为按正向位移聚类：当前位移与本簇锚点相差不超过 2 行时累计稳定证据，超过容差则从当前候选建立新簇。整个过程只消耗当前滚轮位置的重采预算，不触发额外输入。
- 零位移继续使用独立计数；任意零位移会清除移动簇，任意正位移也会清除无进展计数，因此 `0, 1` 不会被合并为新增正文，只有连续三个零位移才结束为 `NoProgress`。
- `OverlapEvidence` 新增当前实际选中候选的得分。近邻位移只有在当前得分不低于簇内既有最佳得分时才累计；得分降低会从当前帧重新建立证据，保证最终提交的是当前帧自身验证过的真实接缝，不缓存图像、不平均位移，也不套用历史接缝。
- 已增加 `120, 121` 可稳定、`120, 126` 重建簇、零容差策略、`0, 1` 隔离、平滑滚动最终落入 `200±2`、较低得分重建簇及引擎一次滚轮内完成 `10, 11` 行抖动拼接的回归；持续移动和重采预算样例同步改用超过容差的位移间隔。
- 暂停、停止和取消仍沿用既有条件变量唤醒路径，本次聚类没有增加阻塞等待或新的滚轮发送点。`./build.bat Release test` 通过，共 `1067/1067` 项，耗时 `48.90` 秒。

### 10.8 R06 — `test(longshot): calibrate relaxed matching with desktop samples`

目的：用可复现样本确认“成功率提高但不引入历史猜测”，再决定是否调整 96%、侧边宽度、底部上限和位移容差。

自动化样例至少覆盖：

- 普通文本、低纹理留白、周期列表、左右侧栏、固定底栏、光标闪烁、局部动画、延迟重绘和平滑滚动。
- 第一次观察失败后恢复、整个重采周期均失败、已拼接多帧后失败和到达底部。

- 断言每轮最多一次输入，重采不增加输入计数，任何失败都不改变上一可靠累计图。
